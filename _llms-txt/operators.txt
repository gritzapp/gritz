# Backends

> The sandbox backends a runner can use, Docker and AWS Lambda MicroVMs, how each runs a task, and when to use which.

A runner starts every task’s sandbox through one backend, chosen with `--backend`. The backend creates the sandbox, starts and suspends it around each run, connects the runner to the driver inside it, and destroys it when the task is archived. | | Docker | Lambda MicroVMs | | ------------------------- | ------------------------------------------------ | ------------------------------------------------------------- | | `--backend` | `docker` (the default) | `lambda-microvm` | | Sandbox | A container on the runner’s Docker daemon | An AWS Lambda MicroVM | | Workspace section | `container:` | `lambda_microvm:` | | Image | Any Linux image; the runner copies the driver in | A MicroVM image with the driver as its entrypoint, ARM64 only | | Between runs | The container is stopped | The VM is suspended | | Runner reaches the driver | `docker exec` tunnel to `/gritz/driver.sock` | AWS’s managed proxy | | Capacity | The runner host’s | AWS’s, up to your account limits | **Use Docker** to get started, on a workstation or a dedicated host, or when tasks need Docker-specific setup: volumes, networks, other runtimes such as sysbox, or privileged containers. **Use Lambda MicroVMs** to run many tasks without sizing a host for them, with each task isolated in its own VM and nothing left running between runs. A workspace can have both a `container:` and a `lambda_microvm:` section, so one `workspaces.yaml` can serve runners on either backend. Each backend checks only its own section, when a task’s run starts, so a missing section fails that run rather than the runner’s start. ## Docker [Section titled “Docker”](#docker) The runner talks to the Docker daemon from its environment (`DOCKER_HOST`, or the local socket), so it needs access to it: run it as a user in the `docker` group, or mount `/var/run/docker.sock` into the runner’s container. For each task the runner: 1. Pulls the workspace’s `container.image` if it isn’t present, with the credentials from the runner user’s `~/.docker/config.json` for private registries. 2. Creates a container named `gritz-<task-id>` with the labels `gritz=true`, `gritz.task=<task-id>` and `gritz.runner=<runner-id>`, and copies the matching `gritz` binary into it as `/usr/local/bin/gritz` (see [Driver binaries](/operators/runner/#driver-binaries)). Its main process is `gritz driver`, listening on `/gritz/driver.sock`. 3. Starts the container for each run and stops it afterwards. The container’s filesystem survives between runs, so a woken task finds its checkout where it left it. 4. Removes the container when the task is archived. The `container:` section maps onto the container’s settings: `image`, `user`, `working_dir`, `environment`, `volumes`, `networks`, `network_mode`, `group_add`, `runtime` and `privileged`. See [`workspaces.yaml`](/operators/workspaces-yaml/#container). The driver inside the container connects to the server at the runner’s server URL. When that is `localhost`, as in local development, the container can’t reach it on the default bridge network: use `network_mode: host` on Linux, or a URL such as `http://host.docker.internal:6464`. ## Lambda MicroVMs [Section titled “Lambda MicroVMs”](#lambda-microvms) 
```bash
AWS_REGION=us-east-1 gritz runner --backend lambda-microvm
```
 The runner resolves AWS credentials and the region through the standard AWS SDK chain; `--lambda-microvm-region` overrides the region. The runner’s credentials make the MicroVM control-plane calls: `RunMicrovm`, `GetMicrovm`, `SuspendMicrovm`, `ResumeMicrovm`, `TerminateMicrovm` and `CreateMicrovmAuthToken`. Sandboxes never hold them. For each task the runner: 1. Launches a MicroVM from the workspace’s image (`run-microvm`) on the first run, and waits until it is running. 2. Starts each run over the managed proxy, on port 8080, with a proxy auth token scoped to that port. 3. Suspends the VM after every run (`suspend-microvm`) and resumes it for the next (`resume-microvm`). 4. Terminates the VM when the task is archived (`terminate-microvm`). A VM runs for at most `max_duration_seconds`, 8 hours by default and at most, so keep tasks that wake up over days on Docker. ### Workspace config [Section titled “Workspace config”](#workspace-config) 
```yaml
workspaces:
  example:
    secrets:
      CLAUDE_CODE_OAUTH_TOKEN: ${env:CLAUDE_CODE_OAUTH_TOKEN}
    lambda_microvm:
      image_identifier: arn:aws:lambda:us-east-1:123456789012:microvm-image/gritz-driver
      execution_role: arn:aws:iam::123456789012:role/gritz-microvm
      egress_connector: arn:aws:lambda:us-east-1:aws:network-connector:aws-network-connector:INTERNET_EGRESS
    agent:
      type: claude
      cwd: /root
```
 | Field | Required | | | ---------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | | `image_identifier` | yes | The MicroVM image’s ARN. | | `execution_role` | yes | The IAM role the VM runs as. It needs whatever the agent’s work needs, and no MicroVM permissions. | | `egress_connector` | yes | The network connector for outbound traffic, so the driver can reach the server: `INTERNET_EGRESS` or a VPC connector. | | `ingress_connector` | no | The network connector the runner’s proxy traffic comes in through. Defaults to the managed `ALL_INGRESS`; a connector scoped to port 8080 is tighter. | | `region` | no | Must match the runner’s region if set. One runner serves one region. | | `max_duration_seconds` | no | The VM’s maximum lifetime, up to `28800` (8 hours), the default. | | `environment` | no | Environment variables for every run. A VM has no environment of its own, so these are passed with each run. | ### Building the image [Section titled “Building the image”](#building-the-image) A MicroVM image is built by Lambda from a zip holding a `Dockerfile` and a `linux/arm64` `gritz` binary, with `gritz driver --aws-lambda-hooks` as its entrypoint. Install the agent CLIs and tools your workspaces need in the same `Dockerfile`. The [backend’s README](https://github.com/gritzapp/gritz/blob/master/internal/runner/backend/lambdamicrovm/README.md) has the full recipe: the example `microvm.Dockerfile`, the `create-microvm-image` call with its hooks, the build role, and warming the image with `--aws-lambda-validate` so cold VMs start their tools quickly. Unlike Docker, the driver is part of the image, so rebuild the image with the new binary whenever you upgrade the runner.

# Debugging

> Read a task's driver log, log raw agent output with verbose, open a shell in a task's sandbox, and find and clean up task containers.

## The task log [Section titled “The task log”](#the-task-log) Each task’s driver log holds the setup commands and their output, the agent CLI’s output and the driver’s own logging. The driver streams it to the server as the task runs, so it stays readable after the sandbox is gone and needs no access to the runner or Docker: 
```bash
gritz logs <task-id>     # print the whole log
gritz logs -f <task-id>  # follow it as the task runs
```
 The Web UI shows the same log on the task’s page. Declared [secrets](/operators/secrets/) are masked in it. `gritz logs` picks its organisation, key and server as every CLI command does (see [Configuration](/using/cli/#configuration)). `--interval` sets how often `-f` polls, `2s` by default. A setup command that fails ends the run with `setup command N failed`, where `N` counts from 0. Its output is just above that line. ## Raw agent output [Section titled “Raw agent output”](#raw-agent-output) By default the driver parses the agent CLI’s streamed output and logs a summary of each message and tool call. Set `verbose: true` on a workspace’s agent to log every raw line instead, when the summary hides what you need: errors, intermediate output, the full payload of a tool call. 
```yaml
agent:
  type: claude
  verbose: true
```
 `verbose` works for `claude`, `codex` and `cursor`. Restart the runner to pick up the change. Like the rest of the agent config, it applies to tasks created after that; see [changing a workspace](/operators/workspaces-yaml/#changing-a-workspace). ## A shell in the sandbox [Section titled “A shell in the sandbox”](#a-shell-in-the-sandbox) 
```bash
gritz shell <task-id>
```
 opens an interactive shell in a task’s sandbox, to inspect what a finished task left behind. The task must have finished: gritz won’t interrupt a running agent. The runner brings the sandbox back up with a shell run in place of the agent, on the same filesystem, and the task’s timeline records it as a restart. It works for every backend and for runners on other machines: the driver dials the server, and the server relays your terminal to it, so you need neither Docker access nor a route to the runner. Inside, `/gritz/log` is the driver’s raw log, with secrets unmasked, and `/tmp/gritz/<task-id>.json` is the agent config the runner wrote, including the MCP servers. ## Containers [Section titled “Containers”](#containers) On the Docker backend each task’s container is named `gritz-<task-id>` and labelled `gritz=true`, `gritz.task=<task-id>` and `gritz.runner=<runner-id>`. `gritz containers` lists them on the current Docker host, running and stopped: 
```bash
gritz containers
```
 A task’s container is stopped between runs and removed when the task is archived. Containers can be left behind when a runner loses its [state database](/operators/runner/#the-state-database), or when a container is created for a runner ID that no longer runs. To remove them: * `gritz containers --prune` removes every stopped gritz container on the host, including those of tasks that are only idle between runs, which then lose their sandbox’s files. Use it only when no runner on the host has tasks you want to keep. * `docker rm` a container by name, such as `docker rm gritz-1234`, to remove one. The runner logs each sandbox it creates, boots, suspends and destroys; run it with `--debug` for more detail.

# Deployment

> The published gritz server and runner images, running a runner as a Docker Compose service, and upgrading a deployment.

## Releases and images [Section titled “Releases and images”](#releases-and-images) Every gritz release publishes: * **Archives** for Linux and macOS, `gritz_<os>_<arch>.tar.gz` for `linux` and `darwin` on `amd64` and `arm64`, each holding the `gritz` binary, plus a `checksums.txt`, attached to the [GitHub release](https://github.com/gritzapp/gritz/releases). * **`ghcr.io/gritzapp/server`**, which runs `gritz server` and listens on port `6464`. The Web UI is built into the binary. * **`ghcr.io/gritzapp/runner`**, which runs `gritz runner`. It includes the Docker CLI and both [driver binaries](/operators/runner/#driver-binaries) (`GRITZ_PREBUILT_DIR=/app/prebuilt`). Images are built for `linux/amd64` and tagged with the version (`1.2.3`), the minor (`1.2`) and major (`1`) versions, and `latest`. Pin a version in production. ## Server [Section titled “Server”](#server) The server needs a PostgreSQL database and the settings described in [Server](/operators/server/). With Docker Compose: 
```yaml
services:
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: gritz
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: gritz
    volumes:
      - postgres_data:/var/lib/postgresql/data


  server:
    image: ghcr.io/gritzapp/server:1
    ports:
      - "6464:6464"
    environment:
      GRITZ_BASE_URL: https://gritz.example.com
      GRITZ_DATABASE_URL: postgres://gritz:${POSTGRES_PASSWORD}@postgres:5432/gritz
      GRITZ_AUTH_DOMAIN: instance.zitadel.cloud
      GRITZ_AUTH_CLIENT_ID: ${GRITZ_AUTH_CLIENT_ID}
      GRITZ_AUTH_CLIENT_SECRET: ${GRITZ_AUTH_CLIENT_SECRET}
      GRITZ_AUTH_ENCRYPTION_KEY: ${GRITZ_AUTH_ENCRYPTION_KEY}
      GRITZ_AUTH_APP_KEY: ${GRITZ_AUTH_APP_KEY}
      GRITZ_ARCHIVE_POLL: 1m
    depends_on:
      - postgres


volumes:
  postgres_data:
```
 Keep the credentials in an `.env` file next to `docker-compose.yml`, or in your platform’s secret store, rather than in the file itself. Put a TLS-terminating proxy in front of port `6464`, and point health checks at `/healthz`. ## Runner as a Docker Compose service [Section titled “Runner as a Docker Compose service”](#runner-as-a-docker-compose-service) The runner image drives the host’s Docker daemon through its socket, so task containers run next to the runner rather than inside it: 
```yaml
services:
  runner:
    image: ghcr.io/gritzapp/runner:1
    restart: unless-stopped
    environment:
      GRITZ_SERVER: https://gritz.example.com
      GRITZ_API_KEY: ${GRITZ_API_KEY}
      GRITZ_RUNNER_ID: example-runner
      GRITZ_CONFIG_DIR: /etc/gritz
      # Read by ${env:} references in workspaces.yaml.
      CLAUDE_CODE_OAUTH_TOKEN: ${CLAUDE_CODE_OAUTH_TOKEN}
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./config:/etc/gritz
      - runner_state:/var/lib/gritz


volumes:
  runner_state:
```
 * `./config/workspaces.yaml` is the [workspace config](/operators/workspaces-yaml/). `${env:}` references in it read the runner container’s environment, and `${sh:}` commands run inside the runner container. * `runner_state` keeps the runner’s [state database](/operators/runner/#the-state-database) across restarts and upgrades. * Task containers join Docker’s default bridge network unless a workspace sets `networks:` or `network_mode:`. [gritzapp/workspaces](https://github.com/gritzapp/workspaces/tree/main/runner) has a complete example with a pull-through registry cache, so task images aren’t downloaded again for every container, and the sysbox runtime, so agents can run Docker inside their sandbox. ## Upgrades [Section titled “Upgrades”](#upgrades) The server, runner and driver ship together and change together: a release makes no promise of compatibility with another release’s server, runner or driver. Upgrade them as one: 1. Upgrade the server. It applies its database migrations when it starts. 2. Upgrade every runner to the same release. A runner that installed driver binaries with `gritz download` needs to download them again; the runner image already has the matching ones. 3. For the Lambda MicroVMs backend, rebuild the MicroVM image with the new `gritz` binary and update the workspaces’ `image_identifier`. A sandbox keeps the driver it was created with: the Docker backend copies the binary in when it creates the container, and a MicroVM runs the one in its image. Tasks that were created before an upgrade keep their old driver until they are archived.

# Operators overview

> The parts of a gritz deployment (server, runner, driver and sandbox), who talks to whom, what each needs to reach, and the data model.

A gritz deployment has one server and any number of runners. Each runner starts a sandbox per task, and a driver inside each sandbox runs the agent. ![gritz architecture: the Web UI, MCP clients and GitHub and Jira webhooks talk to the gritz server, which stores everything in PostgreSQL. The runner fetches tasks from the server and manages sandboxes through its backend. In each sandbox the driver runs the agent and its gritz MCP server, and both connect to the server directly with the task token.](/_astro/architecture.BKqnZFpL_2oCYM1.svg) ## Components [Section titled “Components”](#components) **Server** (`gritz server`) is the control plane. It serves the API, the Web UI, the user-facing MCP endpoint and the webhooks for GitHub, Jira and custom events, and it stores tasks, events and logs in PostgreSQL. See [Server](/operators/server/). **Runner** (`gritz runner`) runs tasks. It authenticates to the server with an API key, registers the workspaces in its [`workspaces.yaml`](/operators/workspaces-yaml/), and picks up the tasks that users create for it. For each task it creates a sandbox through its [backend](/operators/backends/), starts the task’s runs, and destroys the sandbox when the task is archived. See [Runner](/operators/runner/). **Sandbox** is where a task’s agent runs: a Docker container named `gritz-<task-id>`, or an AWS Lambda MicroVM. A task keeps its sandbox from its first run until it is archived, so files the agent leaves behind are still there when an event wakes the task up. **Driver** (`gritz driver`) is the sandbox’s main process. The runner copies the gritz binary into the sandbox and starts each run over the driver protocol. The driver runs the workspace’s setup commands, then the agent CLI (Claude Code, Codex, Cursor or Copilot), and ships the run’s log to the server as it goes. **Agent MCP server** (`gritz tool agent-mcp`) is added to every agent’s MCP servers. It gives the agent the tools to read and update its own task, link resources to it and report progress. ## Who connects to whom [Section titled “Who connects to whom”](#who-connects-to-whom) | From | To | How | | -------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------- | | Browsers, the `gritz` CLI, MCP clients | Server | HTTPS: an SSO session, an API key or an OAuth token | | GitHub, Jira, other systems | Server | Webhooks | | Server | PostgreSQL | `--db` connection string | | Runner | Server | HTTPS with an API key: it holds a notification stream open for new work, and polls as a fallback | | Runner | Driver | Through the backend: a `docker exec` tunnel to `/gritz/driver.sock` for Docker, AWS’s managed proxy for Lambda MicroVMs | | Driver and agent MCP server | Server | HTTPS with the task’s own token | Two consequences for networking: * The server never connects to a runner, so a runner can sit behind NAT or a firewall as long as it can reach the server. * Sandboxes connect to the server themselves, at the runner’s server URL: its organisation’s `server`, or `--server` with `--key`. That URL has to resolve and be reachable from inside the sandbox, not just from the runner’s host. ## Versions [Section titled “Versions”](#versions) The server, runner and driver ship together, as one `gritz` binary and one release. The runner puts its own binary into each sandbox, so the driver always matches the runner. Upgrade the server and the runners to the same release; see [Deployment](/operators/deployment/#upgrades). Animated walkthroughs of how these parts interact, such as creating a task, are on the [diagrams site](/diagrams/). ## Data model [Section titled “Data model”](#data-model) The server keeps its state in PostgreSQL. Everything belongs to an **org** (`orgs`, with `users` joined through `org_members`). **Tasks** (`tasks`) carry the workspace and runner they run on, and their status. **Links** (`task_links`) attach external resources to a task, and a subscribed link routes **events** (`events`) to it. **Workspaces** (`workspaces`) are what runners register from their `workspaces.yaml`, and **API keys** (`keys`) authenticate runners and clients. ![gritz database schema: orgs, users and org_members; tasks with their task_links and events; workspaces and keys, each belonging to an org; and pending_integrations.](/_astro/schema.ClGhbr2n_Z1zxdsn.svg)

# Runner

> Run gritz runner on your own machine or server, with an API key, a workspaces.yaml and the driver binaries it copies into sandboxes.

`gritz runner` runs tasks on infrastructure you control. It connects to the server with an API key, offers the workspaces in its `workspaces.yaml`, and runs every task created for it in a sandbox of its own: a Docker container by default. ## Quick start [Section titled “Quick start”](#quick-start) These steps run a runner against gritz.dev on a machine with Docker. 1. **Install `gritz`:** 
   ```bash
   curl -fsSL https://docs.gritz.dev/install.sh | sh
   ```
 This installs the latest release into `~/.local/bin`. See [Install](/using/cli/#install) for the other ways to install it, with mise or from a release archive, and for how to update. 2. **Create an API key** on the **Keys** page (`https://gritz.dev/ui/keys/new`) and copy the `xat_…` token: it is shown only once. Log in with it: 
   ```bash
   gritz login --key xat_...
   ```
 This saves the key in `~/.config/gritz/.gritz.yml`; see [Logging in with an API key](/using/cli/#logging-in-with-an-api-key). On a server, pass it with `--key` or `GRITZ_API_KEY` instead. 3. **Write a `workspaces.yaml`** in `~/.config/gritz/`. This one clones a sample repository and runs Claude Code on it with your Claude Code OAuth token: 
   ```yaml
   workspaces:
     pets-workshop:
       description: Example Node.js pets workshop
       secrets:
         CLAUDE_CODE_OAUTH_TOKEN: ${env:CLAUDE_CODE_OAUTH_TOKEN}
       container:
         image: ghcr.io/gritzapp/workspace-debian:latest
         working_dir: /root
       commands:
         - git clone https://github.com/github-samples/pets-workshop
       agent:
         type: claude
         cwd: /root/pets-workshop
   ```
 See [`workspaces.yaml`](/operators/workspaces-yaml/) for every field. 4. **Start the runner:** 
   ```bash
   gritz runner --state-db ~/.local/state/gritz/runner.db
   ```
 5. **Create a task** in the Web UI at `https://gritz.dev/`, choosing your runner and the `pets-workshop` workspace. ## Flags [Section titled “Flags”](#flags) | Flag | Environment variable | Default | | | ------------------------- | ----------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `--server`, `-s` | `GRITZ_SERVER` | `https://gritz.dev` | The server URL to use with `--key`, which it requires; without `--key`, the organisation’s `server` is used. Sandboxes connect to the same URL, so it must be reachable from inside them too. | | `--key`, `-k` | `GRITZ_API_KEY` | | The API key. Set, the runner reads no `.gritz.yml` files, and `--org` is an error. | | `--org` | `GRITZ_ORG` | the `org` in the `.gritz.yml` files | The organisation to run tasks for, by its name in the `.gritz.yml` files. | | `--workspaces`, `-w` | | `~/.config/gritz/workspaces.yaml` | The [workspace config](/operators/workspaces-yaml/). | | `--id` | `GRITZ_RUNNER_ID` | the hostname | The runner’s ID, which users pick when they create a task. Letters and digits, no spaces. | | `--backend` | `GRITZ_BACKEND` | `docker` | The [sandbox backend](/operators/backends/): `docker` or `lambda-microvm`. | | `--concurrency` | `GRITZ_CONCURRENCY` | `5` | The most task runs at once; further runs wait for a slot. `0` means no limit. | | `--state-db` | `GRITZ_STATE_DB` | `/var/lib/gritz/runner.db` | The runner’s SQLite state. | | `--poll` | | `30s` | How often to poll the server when the notification stream is down. | | `--lambda-microvm-region` | `GRITZ_LAMBDA_MICROVM_REGION` | the AWS SDK’s region | The AWS region for the `lambda-microvm` backend. | | `--debug` | | off | Debug logging. | ### The config directory [Section titled “The config directory”](#the-config-directory) `.gritz.yml`, the default `workspaces.yaml` and downloaded driver binaries live in the gritz config directory: `GRITZ_CONFIG_DIR` if set, otherwise `gritz` under the user config directory (`~/.config/gritz` on Linux, `~/Library/Application Support/gritz` on macOS). ### The state database [Section titled “The state database”](#the-state-database) `--state-db` records which sandbox belongs to which task, the task changes the runner has received, and the reports it still has to send to the server. Keep it on persistent storage and give each runner its own: a runner that loses it no longer knows its sandboxes and leaves them behind (see [Debugging](/operators/debugging/#containers)). The runner creates the file and its directory; the default path usually needs root, so point it somewhere the runner’s user can write on a workstation. ### Runner IDs and workspaces [Section titled “Runner IDs and workspaces”](#runner-ids-and-workspaces) On start, the runner registers its workspace names and descriptions with the server under its ID. Users see them when they create a task, and a task stays with the runner and workspace it was created for. Give every runner a unique ID; change `workspaces.yaml` and restart the runner to change what it offers. ## Driver binaries [Section titled “Driver binaries”](#driver-binaries) The Docker backend copies a `gritz` binary into every container to run as the driver, picking the one that matches the image’s architecture: * When the runner itself is a static Linux binary for that architecture, which the binary in the release archives is, it copies itself. * Otherwise it reads `gritz-linux-amd64` or `gritz-linux-arm64` from the `prebuilt` directory: `GRITZ_PREBUILT_DIR` if set, otherwise `prebuilt` in the config directory. `gritz download` fetches both binaries from the latest GitHub release into that directory. You need it when the runner runs on macOS, or on a different architecture from your images. The driver has to match the runner’s release, so download again after upgrading. The `ghcr.io/gritzapp/runner` image already contains both. The Lambda MicroVMs backend doesn’t copy anything: the driver is built into the MicroVM image (see [Backends](/operators/backends/#lambda-microvms)).

# Secrets

> Declare credentials in a workspace's secrets map so gritz masks them in the task log it ships to the server, and what is masked where.

A task’s driver log is shipped to the server, where anyone in the organisation can read it with `gritz logs` and in the Web UI, long after the sandbox is gone. Credentials that reach that log would be stored with it. Declare them in the workspace’s `secrets:` map and gritz keeps them out of the shipped copy: 
```yaml
workspaces:
  pets-workshop:
    secrets:
      GH_TOKEN: ${sh:gh auth token}
    commands:
      - git clone https://x-access-token:${GH_TOKEN}@github.com/private/repo.git
```
 ## How secrets work [Section titled “How secrets work”](#how-secrets-work) * Each entry becomes an environment variable in the sandbox, exactly like a `container.environment` entry, for the setup commands and the agent. Values go through the same [`${env:}`/`${sh:}` expansion](/operators/workspaces-yaml/#variable-expansion) on the runner. To protect a credential that is in `environment:` today, move it to `secrets:`; nothing else about it changes. * Secrets work the same on every backend. They travel to the driver with each run, not in the sandbox’s own config, so a sandbox reused for a later run never holds stale values. * In the log shipped to the server, every occurrence of a declared value is replaced by `[gritz:masked NAME]`, such as `[gritz:masked GH_TOKEN]`. That includes values echoed by a setup command’s output, `set -x` traces or an `env` dump. * The task’s own token, `GRITZ_TOKEN`, is masked the same way, as `[gritz:masked token]`. ## Reference secrets by variable [Section titled “Reference secrets by variable”](#reference-secrets-by-variable) Reference secrets from `commands:` by variable, as `${GH_TOKEN}`. The runner only expands `${namespace:value}`, so it leaves `${GH_TOKEN}` for the sandbox’s shell to expand when the command runs. The command line the driver logs then carries the name rather than the value. Writing `${env:GH_TOKEN}` in a command would put the value into the command line itself. The mask still catches it, but the name is the clearer record. ## What is masked where [Section titled “What is masked where”](#what-is-masked-where) | Where | Masked | | ---------------------------------------------------------- | ------ | | The log shipped to the server: `gritz logs` and the Web UI | Yes | | `/gritz/log` inside the sandbox | No | | The sandbox’s stderr (`docker logs`) | No | The raw copies stay inside the boundary the secrets already live in: anyone who can read them can read the sandbox’s environment too. Full fidelity there is what makes post-mortems with [`gritz shell`](/operators/debugging/#a-shell-in-the-sandbox) useful. ## Limits [Section titled “Limits”](#limits) gritz doesn’t detect credentials: it masks exactly the values you declare. * An undeclared credential ships unmasked. * A secret that another tool shortens before it reaches the log, such as a long value cut off in a tool-call summary, arrives as a fragment the mask can’t match. * A value that is encoded on its way to the log, such as base64 in an HTTP header dump, no longer matches the declared value. Masking matches the longest declared value at each position, so a secret that is a prefix of another can’t leave part of the longer one exposed. A value split across two writes to the log is still masked.

# Server

> Run gritz server with PostgreSQL, single sign-on, the GitHub App and Atlassian integrations, and the endpoints it serves.

`gritz server` is the control plane: the API, the Web UI, the MCP endpoint and the webhooks, backed by PostgreSQL. Every flag can also be set with the environment variable next to it. 
```bash
gritz server \
  --db "$GRITZ_DATABASE_URL" \
  --base-url https://gritz.example.com
```
 ## Core settings [Section titled “Core settings”](#core-settings) | Flag | Environment variable | Default | | | -------------- | -------------------- | ------- | ------------------------------------------------------------------------------------------------- | | `--addr`, `-a` | | `:6464` | Address to listen on. | | `--db`, `-d` | `GRITZ_DATABASE_URL` | | PostgreSQL connection string, such as `postgres://gritz:…@db:5432/gritz`. | | `--base-url` | `GRITZ_BASE_URL` | | The URL users reach the server at, such as `https://gritz.example.com`, without a trailing slash. | | `--cors` | `GRITZ_CORS` | off | Permissive CORS headers, for development only. | The server applies its database migrations itself when it starts. `--base-url` builds every URL the server hands out or registers with a provider: the login callback (`/auth/callback`), the GitHub and Atlassian OAuth callbacks, and the MCP and custom webhook URLs shown on **Settings → Organisation**. The server exports OpenTelemetry traces when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. ## Authentication [Section titled “Authentication”](#authentication) Users sign in with OpenID Connect. The server is built against [ZITADEL](https://zitadel.com/) and works with other providers that follow the same code flow. | Flag | Environment variable | | | -------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------- | | `--auth-domain` | `GRITZ_AUTH_DOMAIN` | The OIDC issuer, without `https://`, such as `instance.zitadel.cloud`. | | `--auth-client-id` | `GRITZ_AUTH_CLIENT_ID` | The OIDC client ID. | | `--auth-client-secret` | `GRITZ_AUTH_CLIENT_SECRET` | The OIDC client secret. | | `--auth-scopes` | `GRITZ_AUTH_SCOPES` | Comma-separated scopes requested at login. Generate both keys with `openssl rand -hex 32`. Set `--auth-app-key` in production: without it the server generates a new key on every start, and the tokens of running tasks and connected MCP clients stop working at each restart. Amazon Cognito needs `--auth-scopes openid,email,profile`, and `--auth-skip-nonce-verify` when it federates to another identity provider. With `--no-auth`, every browser request is served as a single `dev` user, and the server provisions an admin API key, `xat_dev`, for a local runner. Never expose such a server. API keys (`xat_…`), created by users on the **Keys** page, authenticate the CLI, runners and webhook senders. They work the same with and without SSO. ## GitHub App [Section titled “GitHub App”](#github-app) The GitHub integration is enabled when `--github-client-id` is set. # workspaces.yaml

> Reference for the runner's workspace config, the container, setup commands, agent, MCP servers, capabilities and secrets of each workspace, and ${env:} and ${sh:} expansion.

A runner’s `workspaces.yaml` defines the workspaces it offers. A workspace is everything a task’s sandbox needs: the image, the setup commands that prepare it, the agent that runs, and the MCP servers and credentials that agent gets. The runner reads the file once, at start, from `--workspaces` (`~/.config/gritz/workspaces.yaml` by default). Restart the runner after changing it, and see [Changing a workspace](#changing-a-workspace) for which tasks see the change. 
```yaml
workspaces:
  pets-workshop:
    description: Example Node.js pets workshop
    secrets:
      CLAUDE_CODE_OAUTH_TOKEN: ${env:CLAUDE_CODE_OAUTH_TOKEN}
      GH_TOKEN: ${sh:gh auth token}
    container:
      image: ghcr.io/gritzapp/workspace-debian:latest
      working_dir: /root
    commands:
      - git clone https://x-access-token:${GH_TOKEN}@github.com/example/pets-workshop.git
    agent:
      type: claude
      cwd: /root/pets-workshop
      prompt: |
        Run the tests with `npm test` before you open a pull request.
```
 [gritzapp/workspaces](https://github.com/gritzapp/workspaces) has more examples, for each agent, MCP servers and private repositories, and builds the `ghcr.io/gritzapp/workspace-*` images they use. The images don’t contain gritz: the runner adds its driver to each sandbox. ## Workspace fields [Section titled “Workspace fields”](#workspace-fields) `workspaces` maps each workspace’s name to its config. The name is what users pick when they create a task. | Field | | | ---------------- | ----------------------------------------------------------------------------------------------------- | | `description` | Shown next to the name in the Web UI. | | `container` | The sandbox for the [Docker backend](#container). | | `lambda_microvm` | The sandbox for the [Lambda MicroVMs backend](/operators/backends/#workspace-config). | | `commands` | [Setup commands](#commands), run before the agent. | | `agent` | The [agent](#agent) and its MCP servers. | | `secrets` | Environment variables whose values are masked in the shipped log. See [Secrets](/operators/secrets/). | | `capabilities` | Extra [capabilities](#capabilities) for the task’s token. | ## `container` [Section titled “container”](#container) | Field | | | -------------- | ------------------------------------------------------------------------------ | | `image` | The image to run. Required by the Docker backend. Pulled if missing. | | `working_dir` | The container’s working directory, where setup commands run. | | `user` | The user the driver, setup commands and agent run as. Defaults to the image’s. | | `environment` | Environment variables, as a map. Put credentials under `secrets:` instead. | | `volumes` | Bind mounts and volumes, in Docker’s `source:target[:options]` form. | | `networks` | Docker networks to attach the container to. | | `network_mode` | Docker’s network mode, such as `host`. | | `group_add` | Extra groups for the container’s user. | | `runtime` | The container runtime, such as `sysbox-runc` for Docker inside the sandbox. | | `privileged` | Run the container privileged. | ## `commands` [Section titled “commands”](#commands) Setup commands prepare the sandbox: clone repositories, install dependencies, configure tools. Each is run with `sh -c`, in order, in the sandbox’s working directory, with the same environment as the agent. They run once per task, on its first run. A command that fails fails the run; the next run of the task starts again at the command that failed, so the ones before it aren’t repeated. Their output goes to the task’s log. Reference credentials by variable, as `${GH_TOKEN}` rather than `${env:GH_TOKEN}`: the sandbox’s shell expands it, so the command line the driver logs carries the name, not the value. ## `agent` [Section titled “agent”](#agent) | Field | | | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `type` | `claude` (the default), `codex`, `cursor`, `copilot` or `process`. `dummy` is a stand-in that runs no model, for testing a runner. | | `cwd` | The directory the agent starts in. `$VAR` references are expanded from the sandbox’s environment. | | `prompt` | Text added to the agent’s prompt on a task’s first run, after gritz’s own instructions: conventions for this repository, say. | | `verbose` | Log every raw line of the agent CLI’s output instead of parsing it. Supported by `claude`, `codex` and `cursor`. See [Debugging](/operators/debugging/#raw-agent-output). | | `mcp_servers` | MCP servers for the agent, by name. | | `claude`, `codex`, `cursor`, `copilot` | Options for that agent: `model`, and `bin`, the CLI to run if not the default (`claude`, `codex` and so on). | | `process` | For `type: process`: `command`, the program to run and its arguments, as a list. See [Custom agent process](#custom-agent-process). | The agent CLI has to be installed in the image. Claude Code runs with `--model opus` unless `claude.model` is set; the other agents use their CLI’s default model. 
```yaml
agent:
  type: claude
  cwd: /root/pets-workshop
  claude:
    model: sonnet
```
 ### Custom agent process [Section titled “Custom agent process”](#custom-agent-process) `type: process` runs your own program as the agent, for each prompt: * The prompt arrives on its standard input. * `GRITZ_RESUME` is `true` when the prompt continues an earlier session of the task, such as a wake for a new event. * `mcp_servers` don’t apply: the program gets no MCP configuration. * Its standard output and standard error go to the task’s log. * A non-zero exit status fails the run. * Without a `command`, the run ends as soon as it starts. 
```yaml
agent:
  type: process
  process:
    command: [/usr/local/bin/my-agent, --fast]
```
 ### `mcp_servers` [Section titled “mcp_servers”](#mcp_servers) Each entry is a stdio server, which the agent starts inside the sandbox, or a remote one it connects to over HTTP: | Field | | | ------------------------ | --------------------------------------------------------------------- | | `type` | `stdio`, `http` or `sse`. | | `command`, `args`, `env` | For `stdio`: the command to run, its arguments and extra environment. | | `url`, `headers` | For `http` and `sse`: the server’s URL and request headers. | 
```yaml
workspaces:
  pets-workshop:
    secrets:
      METAMCP_API_KEY: ${env:METAMCP_API_KEY}
    agent:
      mcp_servers:
        meta:
          type: http
          url: http://metamcp:12008/metamcp/Default/mcp
          headers:
            Authorization: Bearer ${env:METAMCP_API_KEY}
```
 gritz passes header values to the agent as written, so a credential in a header comes from `${env:}` or `${sh:}`. Declare the same value under `secrets:`, as above, so it is masked if it shows up in the log. The runner adds an MCP server named `gritz` to every agent, with the tools an agent uses to work with its task (see the [overview](/operators/overview/#components)). Don’t define one with that name. ## `capabilities` [Section titled “capabilities”](#capabilities) Capabilities let a task’s token do more than read and update its own task. One exists: * `github_token`: meant to let the task get GitHub App installation tokens for its organisation. The runner accepts it and the agent gets a [`get_github_token`](/using/agent-tools/#get_github_token) tool, but the server doesn’t issue these tokens yet: every request fails, and so do the `gritz tool git-credential` and `gritz tool github-mcp` helpers that use them. Give agents GitHub access with a token under `secrets:` instead, and reference it by variable: 
```yaml
workspaces:
  pets-workshop:
    secrets:
      GH_TOKEN: ${env:GH_TOKEN}
    commands:
      - git config --global credential.https://github.com.helper '!f() { echo username=x-access-token; echo "password=${GH_TOKEN}"; }; f'
      - git clone https://github.com/example/pets-workshop.git
    agent:
      mcp_servers:
        github:
          type: http
          url: https://api.githubcopilot.com/mcp/
          headers:
            Authorization: Bearer ${env:GH_TOKEN}
```
 The credential helper reads `GH_TOKEN` when git runs it, so the logged command carries only the name. The MCP header uses `${env:}` because header values reach the agent [as written](#mcp_servers). ## Variable expansion [Section titled “Variable expansion”](#variable-expansion) When it loads the file, the runner expands `${namespace:value}` in every string value: * `${env:NAME}` is the runner’s environment variable `NAME`, or empty if unset. * `${sh:command}` is the output of `sh -c command` on the runner’s host, with surrounding whitespace trimmed. A failing command fails the load. Any other namespace is an error. References without a namespace, such as `${GH_TOKEN}` or `$HOME`, are left alone, for the sandbox’s shell to expand. ## Environment [Section titled “Environment”](#environment) The setup commands and the agent see, in order of precedence: 1. The workspace’s `secrets`. 2. The variables gritz sets: `GRITZ_TASK_ID`, `GRITZ_SERVER` and `GRITZ_TOKEN`, the task’s own token. On Lambda MicroVMs, also `lambda_microvm.environment`. 3. The sandbox’s environment: the image’s, plus `container.environment` on Docker. ## Changing a workspace [Section titled “Changing a workspace”](#changing-a-workspace) A task’s sandbox is set up from its workspace once, when it is first created and run, and keeps that setup until the task is archived. After you change a workspace and restart the runner: * `container`, `lambda_microvm` (except `environment`), `commands`, `capabilities` and `agent`, including `prompt` and `mcp_servers`, apply to tasks created from then on. Existing tasks keep what they started with. * `secrets` and `lambda_microvm.environment` are sent with each run, so existing tasks get the new values from their next run. ## Checking a config [Section titled “Checking a config”](#checking-a-config) `gritz workspaces` loads a file the way the runner does and prints the result: 
```bash
gritz workspaces -c ~/.config/gritz/workspaces.yaml
```
 It checks the YAML, the agent’s MCP servers and the capabilities, but not the `container:` or `lambda_microvm:` section, which the backend checks when a run starts. The output is the config after expansion, so it contains your secrets’ values.
