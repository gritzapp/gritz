# What is gritz?

> gritz runs coding agents such as Claude Code and Codex in sandboxes, driven by tasks and events.

gritz is an orchestrator for coding agents. It runs agents such as Claude Code, Codex, Cursor and Copilot in parallel, each in its own sandbox, and keeps track of their work in one place. * **Tasks** are the unit of work. A task gives an agent its instructions and runs it in a sandbox built from a workspace: the image, repositories, agent and MCP servers it needs. * **Runners** start the sandboxes, on Docker or Lambda MicroVMs, and stream each agent’s log back to the gritz server, where the Web UI shows it live. * **Events** keep a task going after its first run. When an agent opens a pull request or comments on an issue, it links the resource to its task, and a review comment on that pull request wakes the task up with the new event. Agents and users drive gritz the same way: from the Web UI, the `gritz` CLI, or any MCP client.

# Events and links

> How tasks link to pull requests, issues and other resources, how a subscribed link lets an event on that resource wake the task, and where events show up.

Tasks don’t end when their agent stops. An agent that opens a pull request links it to its task, and a review comment on that pull request later wakes the task up to address it. ![A sequence diagram: the agent creates a pull request on GitHub and a subscribed link to it, and its task completes. A reviewer comments “gritz: fix the failing test” on the pull request, GitHub’s webhook restarts the agent, and the agent pushes a fix.](/pr/2063/_astro/events.yf17GTzA_1RLqTL.svg) ## Links [Section titled “Links”](#links) A link connects a task to an external resource: a pull request, an issue, a Jira ticket, a dashboard. It has: * a **URL**, ideally one a person can open; * a **relevance**, saying how the resource relates to the task, such as “PR implementing the fix”; * an optional **title** to display; * **subscribe**, whether events about the resource should reach the task. Agents create links with the [`create_link`](/pr/2063/using/agent-tools/#create_link) tool, and gritz tells every agent to create a subscribed link for each resource it creates, such as a pull request, an issue or a comment. A task created by a [routing rule](/pr/2063/concepts/routing-rules/) also gets a subscribed link to the URL of the event that created it. Links are listed in the task page’s sidebar and appear on its timeline. They can’t be removed: a task stays subscribed until it is archived. ## Subscriptions [Section titled “Subscriptions”](#subscriptions) A link created with `subscribe=true` is a subscription. When an event arrives about the same URL, gritz delivers it to every task subscribed to that URL in the organisation, rather than starting a new task. The URL has to match: * **GitHub and Jira URLs** are matched by the issue, pull request or Jira issue they point at. A comment’s URL, a pull request’s `/files` page and the API URL of the same pull request all match a link to the pull request. * **Any other URL** must match exactly, character for character. A different query string or a trailing slash is a different resource. See [The URL is the subscription key](/pr/2063/integrations/custom-events/#the-url-is-the-subscription-key). Archived tasks aren’t subscribed to anything. An event about a URL whose only subscriber is archived is treated as if nobody were subscribed. ## How an event reaches a task [Section titled “How an event reaches a task”](#how-an-event-reaches-a-task) Events come from the GitHub and Jira integrations and from your own systems through [custom events](/pr/2063/integrations/custom-events/). For each event, gritz: 1. **Finds a matching routing rule.** Each organisation’s [routing rules](/pr/2063/concepts/routing-rules/) decide what kinds of events it acts on. The first rule that matches wins; an event that matches no rule does nothing, even for subscribed tasks. 2. **Looks for subscribed tasks** for the event’s URL, in the matched rule’s [namespace](/pr/2063/concepts/namespaces/). 3. **Delivers or creates.** If there are subscribed tasks, the event is added to each of them, and the rule decides whether it also wakes them. If there are none and the rule creates tasks, it creates one, subscribed to the event’s URL, so the next event about the same resource goes to it. A woken task that has finished starts a new run. A running task isn’t interrupted: it runs again as soon as its current run ends. Either way the agent gets the event at the start of its next run. An event delivered without a wake waits on the task’s timeline until something else starts the task; the agent also sees it if it calls [`get_my_task`](/pr/2063/using/agent-tools/#get_my_task). ## Where events show up [Section titled “Where events show up”](#where-events-show-up) * **The task’s timeline** shows each event delivered to the task, with its source, description, URL and text, next to the instructions and the agent’s reports. * **Events → Recent Events** in the [Web UI](/pr/2063/using/web-ui/#events) lists the organisation’s latest delivered events, each linked to its task. Events that matched no rule, or reached no task, aren’t stored, so they don’t appear. * **The test event form** on **Events → Routing Rules** shows what an event would do before you rely on it. See [Testing rules](/pr/2063/concepts/routing-rules/#testing-rules).

# Namespaces

> How a task's namespace scopes which routing rules see its subscriptions, so separate workflows on the same resource don't wake or suppress each other's tasks.

A namespace is a label on a task that separates its subscriptions from other tasks’. Most organisations don’t need one: every task and rule without a namespace is in the default namespace, and routing works as described in [Routing rules](/pr/2063/concepts/routing-rules/). Namespaces matter when two workflows care about the same resource. Say a triage workflow creates a task for every Jira issue labelled `needs-triage`, while developers’ tasks subscribe to the issues they work on. Without namespaces, a developer’s task subscribed to an issue would stop the triage rule from creating its task: the rule would find a subscriber and deliver the event to it instead. ## How namespaces scope routing [Section titled “How namespaces scope routing”](#how-namespaces-scope-routing) * **A task’s namespace** is set when it is created and can’t be changed. Its links, and so its subscriptions, are in that namespace. * **A routing rule’s namespace** decides which subscriptions it sees. When the rule matches, gritz only looks for subscribed tasks in the rule’s namespace: it wakes those, and creates a task only if there are none there. A task the rule creates is in the rule’s namespace. In the example, put the triage rule in a `triage` namespace. Developers’ tasks in the default namespace no longer stop it creating triage tasks, and the triage tasks it creates aren’t woken by the default namespace’s rules. ## Namespaces don’t choose the rule [Section titled “Namespaces don’t choose the rule”](#namespaces-dont-choose-the-rule) Rules are still checked in order, and the first rule that matches the event acts, whatever its namespace. Two rules that match the same event never both act, even in different namespaces. Give the rules of each workflow conditions that tell its events apart, such as `label equals needs-triage` for the triage rule. ## Setting a namespace [Section titled “Setting a namespace”](#setting-a-namespace) A namespace is any name you choose. Leave the field empty for the default namespace. You can set it on: * a task, in the **Namespace** field of the new task form; * a routing rule, in its **Namespace** field, for the tasks it creates and the subscriptions it sees; * a [schedule](/pr/2063/concepts/schedules/), for the tasks it creates. The task page’s sidebar shows a task’s namespace, and agents see it in [`get_my_task`](/pr/2063/using/agent-tools/#get_my_task).

# Organisations, members and API keys

> How organisations own tasks, runners and rules, what members and the owner can do, and what API keys and task tokens can access.

## Organisations [Section titled “Organisations”](#organisations) An organisation owns everything in gritz: its tasks, the runners connected to it and their workspaces, routing rules, custom event types, schedules and API keys. Nothing is shared between organisations, and an event is routed by each organisation’s own [rules](/pr/2063/concepts/routing-rules/). The first time you sign in, gritz creates a personal organisation for you, your default. You can create more under **Settings → Account → My Organisations**, and switch between those you belong to with the selector at the top of the [Web UI](/pr/2063/using/web-ui/). The current organisation is in each page’s `?org=` parameter. ## Members [Section titled “Members”](#members) Every member of an organisation can do everything in it: create, run and archive any of its tasks, edit its routing rules and schedules, and create and delete its API keys. The one exception is managing the organisation itself, which only its owner can do. The owner is whoever created it. | | Members | Owner | | --------------------------------------------------- | ------- | ----- | | Tasks, schedules, routing rules, custom event types | ✓ | ✓ | | API keys, workspaces, integration settings | ✓ | ✓ | | Add and remove members | | ✓ | | Delete the organisation | | ✓ | The owner adds members on the **Members** page, by the email address they sign in with. A person has to have signed in to gritz once before they can be added. The owner can’t be removed. Membership also decides whose GitHub and Jira activity counts as the organisation’s: a member-only routing rule acts on events from members who have linked their GitHub or Atlassian account under **Settings → Account**. See [Public rules](/pr/2063/concepts/routing-rules/#public-rules). ### Deleting an organisation [Section titled “Deleting an organisation”](#deleting-an-organisation) The owner can delete an organisation from **My Organisations**, except their default one. Archive all of its tasks first, so their runners destroy the sandboxes: gritz refuses to delete an organisation with unarchived tasks. Deleting it disables its schedules and stops its API keys from working. ## API keys [Section titled “API keys”](#api-keys) An API key lets a program act for the organisation: a [runner](/pr/2063/concepts/runners/), the [CLI](/pr/2063/using/cli/), or a system sending [custom events](/pr/2063/integrations/custom-events/). Create one on the **Keys** page. The key, starting with `xat_`, is shown once, when it is created; store it then. * A key belongs to the organisation it was created in, not to the member who created it, and keeps working if they leave. * It can do what a member can, in that organisation only, apart from the owner’s actions. * Actions taken with it, such as creating a task, are recorded under the key’s name, so give each key a name that says what uses it. * Keys created in the Web UI don’t expire. Delete a key on the **Keys** page to revoke it. Send it as a bearer token, `Authorization: Bearer xat_…`. The CLI reads it from its [config file](/pr/2063/using/cli/#configuration). ## Task tokens [Section titled “Task tokens”](#task-tokens) Agents don’t use API keys. Each task gets a token of its own that can only read and update that task: fetch its instructions, rename it, add links and post reports, through the [agent tools](/pr/2063/using/agent-tools/). It can’t see or change other tasks. The token stops working when the task is archived. A workspace can give its tasks’ tokens one more permission: getting GitHub tokens through the organisation’s GitHub App (see [capabilities](/pr/2063/operators/workspaces-yaml/#capabilities)).

# Routing rules

> How an organisation's routing rules match events by type and conditions, why the first match wins, waking versus creating tasks, public rules, and testing rules with a test event.

Routing rules decide what an organisation does with incoming events: GitHub comments, Jira updates and [custom events](/pr/2063/integrations/custom-events/). Each rule matches a kind of event and says what to do with it: wake the tasks subscribed to the event’s resource, create a new task, or both. An organisation with no rules acts on no events. Even a task with a [subscribed link](/pr/2063/concepts/events-and-links/#subscriptions) is only woken by an event that some rule matches. Rules are on **Events → Routing Rules** in the [Web UI](/pr/2063/using/web-ui/#events). **+ Rule** adds one, and the arrows on each row change its position. ## Matching [Section titled “Matching”](#matching) A rule matches an event by: * **Event type**: the event’s source and type, such as a GitHub pull request review comment, a Jira issue comment, or one of the organisation’s custom types. * **Conditions**, each an attribute, an operator and a value. The attributes on offer depend on the event type. Every type has `body`, the event’s text, and `url`, the resource it is about; built-in types add others, such as the users mentioned in a comment, an issue’s new label or its new assignee. | Operator | Holds when the attribute’s value | | ---------- | -------------------------------- | | `equals` | is exactly the value | | `prefix` | starts with the value | | `contains` | contains the value anywhere | Comparisons are exact and case-sensitive. An attribute can have several values, such as the labels on an issue, and a condition holds when any of them satisfies it. A condition on an attribute the event doesn’t have never holds. A rule matches when every condition holds. A rule with no conditions matches every event of its type. ### The first match wins [Section titled “The first match wins”](#the-first-match-wins) Rules are checked from the top of the list down, and the first one that matches is the only one that acts. Put narrow rules above broad ones: a rule for `body contains "gritz:"` placed under a rule with no conditions for the same type never matches. Each organisation’s rules are checked on their own. If an event concerns two organisations, as when its author is a member of both, each organisation’s first matching rule acts. ## What a rule does [Section titled “What a rule does”](#what-a-rule-does) Once a rule matches, gritz looks for tasks subscribed to the event’s URL, in the rule’s [namespace](/pr/2063/concepts/namespaces/): * **Subscribed tasks found**: the event is added to each of them. With **Wake up linked tasks** on, they also start again to handle it. With it off, the event waits on their timelines until they next run. * **No subscribed task, and Create a task on**: gritz creates a task on the rule’s runner and workspace, subscribed to the event’s URL. The next event about the same resource wakes that task instead of creating another. * **No subscribed task, and Create a task off**: nothing happens. So a rule with both on starts one task per resource and keeps it up to date, and a rule with only **Wake up linked tasks** on acts only on resources a task has already linked. ### Creating tasks [Section titled “Creating tasks”](#creating-tasks) A rule that creates tasks sets their: * **Runner** and **Workspace**. * **Prompt**: the created task’s instruction. Left blank, the instruction only says that a routing rule created the task for the event. The task’s first event is the one that created it, so the agent gets the event’s text either way. * **Auto-archive**: the created task’s [auto-archive](/pr/2063/concepts/tasks/#auto-archive) delay. * **Namespace**: the rule’s namespace. ## Public rules [Section titled “Public rules”](#public-rules) By default a rule only acts on events from members of the organisation: a GitHub or Jira event counts as a member’s when its author has linked that account to a gritz user in the organisation. A **Public** rule also acts on events from anyone else, as long as the event belongs to the organisation: * a GitHub event from a repository where the organisation installed the gritz GitHub App; * a Jira event sent to the organisation’s Atlassian webhook; * a custom event sent with one of the organisation’s API keys. Make a rule public to let people outside the organisation, such as outside contributors or a team without gritz accounts, trigger it. Custom events have no author, so rules for custom types must be public: gritz refuses to save one that isn’t. See [Why custom event rules must be public](/pr/2063/integrations/custom-events/#why-custom-event-rules-must-be-public). ## Testing rules [Section titled “Testing rules”](#testing-rules) **Test** on the Routing Rules tab opens a form to compose an event: its type, an optional description, its attributes such as `body` and `url`, and details. * **Dry run** shows which rule would match the event and whether that rule would wake tasks or create one. It changes nothing. It reports the rule’s settings only: it doesn’t check whether a task is subscribed to the URL. * **Fire** routes the event for real, as if it had arrived from its source: it wakes or creates tasks and stores the event on them. It doesn’t post anything back to GitHub or Jira. Both run the event as yours, so your organisation’s member-only rules can match it, and only for the organisation you are in.

# Runners

> Where a task runs, how runners connect to an organisation, choosing a runner for a task, and what happens when a runner is offline.

A runner is the machine, or service, that runs tasks. It connects to the gritz server, offers a set of [workspaces](/pr/2063/concepts/workspaces/), and starts a sandbox for every task created for it: a Docker container or a Lambda MicroVM, depending on how it is set up. Runners run on infrastructure your team controls: a workstation, a server or a cloud account. That is where the agent’s code runs and where its sandbox’s files live. The gritz server only stores the tasks, events and logs. ## Runners and organisations [Section titled “Runners and organisations”](#runners-and-organisations) A runner connects with an [API key](/pr/2063/concepts/orgs-members-keys/#api-keys), and runs tasks for the organisation that key belongs to. Each runner has an ID, the runner’s hostname unless its operator sets one. That ID is what you pick under **Runner** when you create a task, or in a routing rule or schedule that creates tasks. The Web UI doesn’t list runners on their own: a runner appears through the workspaces it registers, on the **Workspaces** page and in the runner pickers. **Clear** on the **Workspaces** page removes the registered workspaces, of one runner or all of them, for example after a runner is retired. A running runner registers its workspaces again the next time it starts. ## Choosing a runner [Section titled “Choosing a runner”](#choosing-a-runner) Pick the runner that offers the workspace you need. When several do, pick by where the work should happen: a runner with access to an internal network, a bigger machine, or your own workstation while you try out a workspace. A task stays on the runner it was created for. Each of its runs happens there, in the same sandbox. ## When a runner is offline [Section titled “When a runner is offline”](#when-a-runner-is-offline) A task whose runner isn’t connected stays `pending`. The runner picks up its tasks when it connects again, and starts the runs they are waiting for. A task whose run ended while its runner was down without the runner seeing the result is marked `failed` when the runner comes back. To set up a runner, see [Runner](/pr/2063/operators/runner/) in the operator docs.

# Schedules

> Create tasks on a cron schedule, in a timezone, and run a schedule's task on demand with run now.

A schedule creates a task on a cron schedule: a nightly dependency bump, a weekly report, an hourly check. Each time it fires it creates a new task from its template, the same as one you create by hand, and the task starts at once. Schedules belong to the organisation, not to the member who created them. They are on the **Schedules** page of the [Web UI](/pr/2063/using/web-ui/#schedules). ## Creating a schedule [Section titled “Creating a schedule”](#creating-a-schedule) **Schedules → + Schedule** asks for: * **Name**: the name of every task it creates. Optional. * **Runner** and **Workspace** for its tasks. * **Instructions**: the instruction every task starts with. * **Cron expression**: when to fire. See below. * **Timezone**: the timezone the cron expression is read in. Defaults to your browser’s. * **Namespace**: the [namespace](/pr/2063/concepts/namespaces/) of its tasks. Optional. * **Auto-archive**: its tasks’ [auto-archive](/pr/2063/concepts/tasks/#auto-archive) delay. Scheduled tasks often have no one watching them, so a short delay keeps them from piling up. * **Enabled**: a disabled schedule is saved but doesn’t fire. ## Cron expressions [Section titled “Cron expressions”](#cron-expressions) A schedule takes a standard five-field cron expression: minute, hour, day of month, month, day of week. There is no seconds field. These shorthands work too: `@yearly`, `@monthly`, `@weekly`, `@daily` and `@hourly`. | Expression | Fires | | -------------- | ----------------------------- | | `0 9 * * *` | Every day at 09:00 | | `30 6 * * 1-5` | Weekdays at 06:30 | | `0 */4 * * *` | Every four hours, on the hour | | `@weekly` | Sundays at midnight | The expression is evaluated in the schedule’s timezone, so `0 9 * * *` in `Europe/Paris` fires at 09:00 Paris time on both sides of a daylight saving change. An expression or timezone gritz can’t parse is rejected when you save. Times are minute-precise: a schedule fires within a few seconds of the minute it is due. If the server is down when a schedule is due, it fires once when the server is back, however many times it was due in between, and then carries on from the next due time. ## Each run is a new task [Section titled “Each run is a new task”](#each-run-is-a-new-task) Every time a schedule fires it creates a new task. It doesn’t reuse or wait for the previous one, so if the last run is still going, the two run side by side. The **Schedules** list shows each schedule’s next run, and links to the task it created the last time it fired. ## Run now [Section titled “Run now”](#run-now) The run button on a schedule’s row creates a task from the schedule straight away, the same task it would create when it fires. It works on disabled schedules too, and it doesn’t change the schedule’s next run or its last run. ## Editing, disabling and deleting [Section titled “Editing, disabling and deleting”](#editing-disabling-and-deleting) Changes to a schedule apply to the tasks it creates from then on; tasks it already created keep their settings. Changing the cron expression or timezone moves its next run. Turning a schedule off clears its next run; turning it back on schedules the next due time from now, without catching up on the runs it missed. Deleting a schedule doesn’t touch the tasks it created.

# Tasks

> What a task is, how instructions and events start its runs, the task statuses, restarting and cancelling, archiving and auto-archive, and the task log.

A task is one piece of work for one agent. It names a [runner](/pr/2063/concepts/runners/) and a [workspace](/pr/2063/concepts/workspaces/), and holds the instructions and events the agent works from. Each task gets a sandbox of its own, which it keeps until it is archived. Tasks are created from the [Web UI](/pr/2063/using/web-ui/), the [CLI](/pr/2063/using/cli/), an MCP client, a [routing rule](/pr/2063/concepts/routing-rules/) or a [schedule](/pr/2063/concepts/schedules/). A task created any of these ways is the same kind of task. ## Instructions and runs [Section titled “Instructions and runs”](#instructions-and-runs) A task does its work in **runs**. A run starts the agent in the task’s sandbox, gives it what is new since the last run, and ends when the agent exits. * **The first run** gets the whole task: its instructions, the events that reached it and its links, after gritz’s own instructions on [the tools it can use](/pr/2063/using/agent-tools/). The workspace’s setup commands run before it, once per sandbox. * **Later runs** get only the instructions and events added since the previous run, and the agent continues the session it had: it remembers what it did before. Two things start a run: * **An instruction.** Sending one from the task page, `gritz task update -i`, or an MCP client starts the task again. If the task is running, the instruction doesn’t interrupt it: the task runs again as soon as the current run ends. * **An event.** An event on a resource the task is [subscribed to](/pr/2063/concepts/events-and-links/), such as a review comment on its pull request, starts it the same way, if the [routing rule](/pr/2063/concepts/routing-rules/) that matched the event wakes tasks. Agents don’t stop by themselves to ask for input. A task that needs an answer from you completes, and the agent says what it needs in its report or on the pull request or issue it is working on. Your next instruction, or a reply on a resource the task is subscribed to, starts the next run. ## Statuses [Section titled “Statuses”](#statuses) | Status | | | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | | `draft` | Created without starting. Tasks created in the Web UI start as drafts, until you send the first instruction. | | `pending` | Waiting for its runner to start the run. A task stays pending while its runner is offline. | | `running` | The agent is running. | | `restarting` | A restart was requested; the runner is stopping the current run to start a new one. | | `cancelling` | A cancel was requested; the runner is stopping the run. | | `completed` | The last run ended normally. | | `failed` | The last run failed: a setup command failed, the agent exited with an error, or the sandbox stopped unexpectedly. The reason is on the timeline. | | `cancelled` | The last run was cancelled. | `completed`, `failed` and `cancelled` are the finished statuses. A finished task isn’t over: an instruction or an event starts it again, from where it left off. Next to the status, the Web UI shows the task’s pending **command**, if any: `command:start`, `command:restart` or `command:stop`. It is what the runner has been asked to do and hasn’t done yet. A `command:start` on a running task is an instruction or event waiting for the current run to end. ## Restarting and cancelling [Section titled “Restarting and cancelling”](#restarting-and-cancelling) * **Restart** runs the task again. The agent continues its session, and is told to carry on if nothing new has arrived. On a running task it stops the current run first, so use it when an agent is stuck. It is available on running and finished tasks. * **Cancel** stops the task. A pending task is cancelled at once; a running or restarting one goes through `cancelling` while the runner stops the agent. The sandbox is kept, so the task can still be started again. ## Archiving [Section titled “Archiving”](#archiving) Archive a task when you are done with it. Archiving: * destroys its sandbox, and with it any files the agent left there; * removes it from the task list (turn on **Show archived** to see it); * stops events from reaching it: an event on one of its links no longer wakes it, and a routing rule that creates tasks creates a new one instead. A task can be archived when it is finished or a draft, and has no pending command. **Unarchive** brings it back to the task list, but not its sandbox. ### Auto-archive [Section titled “Auto-archive”](#auto-archive) A task’s auto-archive delay archives it automatically once it has been finished for that long. The default is never. **Immediately** archives it as soon as it finishes, which suits tasks whose result lives elsewhere, such as a pull request. The delay counts from the task’s last change, so a task that is woken up again starts over. The server checks for due tasks about once a minute. Set it when you create the task, in the task page’s sidebar, with `--auto-archive` on the [CLI](/pr/2063/using/cli/), on a routing rule that creates tasks, or on a schedule. Unarchiving a task sets its delay back to never. Agents can’t change their own task’s delay. ## The timeline and the log [Section titled “The timeline and the log”](#the-timeline-and-the-log) Each task has two records, both on its page in the [Web UI](/pr/2063/using/web-ui/): * **The timeline** is what happened to the task: instructions, events, the agent’s reports, links, status changes and who caused them. Agents read the same instructions and events with [`get_my_task`](/pr/2063/using/agent-tools/#get_my_task). * **The log** is the sandbox’s output: setup commands, the agent’s messages and tool calls, and gritz’s own logging. It stays readable after the sandbox is gone, in the Web UI and with [`gritz logs`](/pr/2063/using/cli/#gritz-logs). Credentials declared as [secrets](/pr/2063/operators/secrets/) are masked in it.

# Workspaces

> What a workspace gives a task (the image, repositories, agent and tools), how to pick one, and who defines them.

A workspace is the recipe for a task’s sandbox. When you create a task you pick one, and it decides everything the agent starts with: * **The image** the sandbox runs, with the agent’s CLI and the tools the work needs. * **Setup commands**, such as cloning the repositories the task works on. They run once, before the task’s first run. * **The agent**: Claude Code, Codex, Cursor or Copilot, its model, the directory it starts in, and any standing instructions for that repository. * **MCP servers** the agent can use, in addition to the [gritz tools](/pr/2063/using/agent-tools/) every agent gets. * **Credentials**, such as a GitHub or model provider token, passed in as secrets. ## Picking a workspace [Section titled “Picking a workspace”](#picking-a-workspace) Workspaces belong to [runners](/pr/2063/concepts/runners/): each runner offers its own set, by name and with a short description. **Workspaces** in the [Web UI](/pr/2063/using/web-ui/#workspaces) lists them all, and the new task form shows the workspaces of the runner you pick. Two runners can offer a workspace with the same name and a different setup. Pick the workspace for the repository or system the task is about. A task keeps its workspace for its whole life; to run the same work in another workspace, create another task. ## Who defines them [Section titled “Who defines them”](#who-defines-them) Workspaces aren’t created in the Web UI. The operator of each runner defines its workspaces in a `workspaces.yaml` file, and the runner registers their names and descriptions with the server when it starts. To add a workspace or change one, ask whoever runs the runner, or see [`workspaces.yaml`](/pr/2063/operators/workspaces-yaml/) if that is you. A change to a workspace applies to tasks created after the runner restarts with it; existing tasks keep the setup they started with. See [Changing a workspace](/pr/2063/operators/workspaces-yaml/#changing-a-workspace).

# Getting started

> Sign in to gritz, pick an organisation, create a task in the Web UI, watch it run, send a follow-up instruction and archive it.

This page walks through a first task on a gritz deployment such as [gritz.dev](https://gritz.dev). It assumes a runner is already connected to your organisation. If none is, ask whoever runs gritz for you, or set one up yourself with [Runner](/pr/2063/operators/runner/). ## 1. Sign in [Section titled “1. Sign in”](#1-sign-in) Open the deployment, for example `https://gritz.dev`, and sign in. The first time you sign in, gritz creates your user and a personal organisation named after you, such as “Ada Lovelace’s Org”. ## 2. Pick an organisation [Section titled “2. Pick an organisation”](#2-pick-an-organisation) Everything in gritz (tasks, runners, routing rules, keys) belongs to an [organisation](/pr/2063/concepts/orgs-members-keys/). The selector at the top right of the Web UI switches between the organisations you are a member of, and the current one is kept in the page’s `?org=` parameter, so links you share open in the right one. To work in a team’s organisation, ask its owner to add you on the **Members** page. They add you by email, so sign in once first. ## 3. Check for a runner [Section titled “3. Check for a runner”](#3-check-for-a-runner) Open **Workspaces**. It lists every [workspace](/pr/2063/concepts/workspaces/) the organisation’s [runners](/pr/2063/concepts/runners/) offer, with the runner that offers it. If the list is empty, no runner has connected to this organisation yet. ## 4. Create a task [Section titled “4. Create a task”](#4-create-a-task) Open **Tasks** and click **+ Task**: * **Name** is optional. The agent names the task itself if you leave it blank. * **Runner** and **Workspace** decide where the task runs and what it gets: the image, repositories, agent and tools. Pick a runner first; the workspace list shows only that runner’s workspaces. * **Namespace** is optional. Leave it empty unless your routing rules use [namespaces](/pr/2063/concepts/namespaces/). * **Auto-archive** archives the task some time after it finishes. Leave it on **Never** for now. **Create Task** opens the task’s page. The task is a draft: nothing runs yet. ## 5. Send the first instruction [Section titled “5. Send the first instruction”](#5-send-the-first-instruction) Type what you want the agent to do in the box at the bottom of the page and press Enter (Shift+Enter adds a new line): > Add a `--json` flag to the `list` command and open a pull request. The task moves to **pending** while the runner prepares its sandbox, then to **running** when the agent starts. ## 6. Watch it run [Section titled “6. Watch it run”](#6-watch-it-run) The task page has three views, in the sidebar on the left: * **Timeline**: your instructions, the agent’s reports, the links it creates (such as the pull request it opened), events from GitHub, Jira and other systems, and status changes, in order. * **Logs**: the sandbox’s log as it runs: setup commands, the agent’s messages and tool calls. * **Shell**: a terminal in the task’s sandbox, once the task has finished. When the agent is done, the task moves to **completed**, or to **failed** if a setup command, the agent or the sandbox failed. The [task lifecycle](/pr/2063/concepts/tasks/#statuses) lists every status. ## 7. Follow up [Section titled “7. Follow up”](#7-follow-up) Send another instruction from the same box: “Also update the README”. A finished task starts again, in the same sandbox, and the agent continues the same session, so it remembers what it did. If the task is still running, the instruction waits and the task runs again as soon as the current run ends. Tasks also come back by themselves. When the agent opens a pull request, it links it to the task with a subscription, and a review comment on that pull request wakes the task up. See [Events and links](/pr/2063/concepts/events-and-links/). ## 8. Archive it [Section titled “8. Archive it”](#8-archive-it) When you are done with the task, click **Archive** in the sidebar. The runner destroys the task’s sandbox and the task leaves the task list; turn on **Show archived** to see it again. A task can only be archived once it has finished. ## Next steps [Section titled “Next steps”](#next-steps) * [Tasks](/pr/2063/concepts/tasks/) covers statuses, restarts, cancelling and auto-archive. * [Routing rules](/pr/2063/concepts/routing-rules/) create and wake tasks from GitHub, Jira and [custom events](/pr/2063/integrations/custom-events/). * [Schedules](/pr/2063/concepts/schedules/) create tasks on a cron schedule. * [The CLI](/pr/2063/using/cli/) creates and follows tasks from a terminal.

# Custom events

> Send events from any system, such as an alerting tool or a deploy pipeline, to gritz so they create or wake up tasks.

GitHub and Jira events reach gritz through their own integrations. Any other system can send events too: you define a custom event type, and the system `POST`s events of that type to the custom events webhook with an API key. Routing rules then decide what each event does, as they do for built-in events: create a task, wake a task that’s already working on the same resource, or both. This page uses an alerting system as its example. It posts an `alert` event when an alert fires, and gritz creates a task to investigate it. ## 1. Define a custom event type [Section titled “1. Define a custom event type”](#1-define-a-custom-event-type) Open **Events → Custom Schemas** and add a type with **+ Type**: * **Type**: the name senders put in the envelope’s `type` field, for example `alert`. It must start with a lowercase letter, followed by up to 63 lowercase letters, digits and underscores (`^[a-z][a-z0-9_]{0,63}$`). It must be unique among your organisation’s custom types, and it can’t be renamed later: remove the type and add a new one instead. * **Label**: shown in the routing rule editor and on the task’s timeline, for example `Alert`. It can’t be empty. * **Attributes**: the values routing rules can match on. Every type has `body` and `url`; the form adds both and doesn’t let you remove them. Add one row per extra attribute, with a key that follows the same rules as the type name. The example declares `severity` and `service`. An attribute’s label, help and placeholder are only for display, in the rule editor and the JSON Schema. The **JSON Schema** button next to each type shows the request body the webhook accepts for it. ## 2. Create an API key [Section titled “2. Create an API key”](#2-create-an-api-key) Senders authenticate with an API key. Create one on the **Keys** page (`https://gritz.dev/ui/keys/new`) and copy the token: it starts with `xat_` and is shown only once. The key belongs to the organisation you create it in, and so does every event sent with it. Store the key as a secret in the sending system and send it as a bearer token: 
```plaintext
Authorization: Bearer xat_…
```
 The webhook URL is on **Settings → Organisation**, in the **Custom Events** card. For gritz.dev it is `https://gritz.dev/webhook/custom`. ## 3. Send an event [Section titled “3. Send an event”](#3-send-an-event) `POST` a JSON envelope to the webhook URL: 
```bash
curl https://gritz.dev/webhook/custom \
  -H "Authorization: Bearer $GRITZ_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "alert",
    "url": "https://alerts.example.com/alerts/4211",
    "body": "checkout-api error rate above 5% for 10 minutes",
    "attrs": {"severity": ["critical"], "service": ["checkout-api"]},
    "details": {"runbook": "https://wiki.example.com/runbooks/checkout-api"}
  }'
```
 The command reads the key from a variable, so it can be shared or logged without the key’s value. * `type` names the custom type. * `url` identifies the resource the event is about; see [The URL is the subscription key](#the-url-is-the-subscription-key). * `body` is the event’s text. The agent reads it, and rules can match on it. * `attrs` holds the values of the type’s other attributes. Each value is a list of strings, even when there is only one. * `details` holds extra key/value context that is shown with the event but that rules can’t match on. Unknown fields are rejected. The [envelope reference](/pr/2063/reference/custom-event-envelope/) lists every field and its validation. A valid event gets a `200` response with the number of tasks it created or woke: 
```json
{"routed": 1}
```
 `{"routed": 0}` is still a success: the event was valid, but nothing acted on it (see [Troubleshooting](#troubleshooting)). ## 4. Add a routing rule [Section titled “4. Add a routing rule”](#4-add-a-routing-rule) An event does nothing until a routing rule matches it. Open **Events → Routing Rules** and add a rule with **+ Rule**: * **Event type**: the type’s label, here `Alert`. * **Conditions**: `severity` `equals` `critical`. A condition matches when any of the attribute’s values satisfies it, and the rule matches when every condition does. * **Public**: on. Custom event rules must be public; see below. * **Wake up linked tasks**: on. * **Create a task**: on, with a runner, a workspace, and a prompt such as “Investigate this alert and report the likely cause.” A task created by a rule is subscribed to the event’s `url`. The next event with the same `url` wakes that task instead of creating another one. ### Why custom event rules must be public [Section titled “Why custom event rules must be public”](#why-custom-event-rules-must-be-public) A rule that isn’t public only fires for events whose actor is a member of the organisation, such as a GitHub comment by a member. A custom event has no actor: it belongs to the API key’s organisation, and only that organisation’s public rules are considered for it. A member-only rule for a custom type could never fire, so gritz rejects it when you save it. ### Follow-up events [Section titled “Follow-up events”](#follow-up-events) For each event, rules are checked in the order shown on the Routing Rules tab (the arrows reorder them), and the first rule that matches wins. The rule above only matches critical alerts, so when the alerting system later posts a `resolved` event for the same alert, it matches nothing and never reaches the task. Add a second rule below the first: the same type, no conditions, public, **Wake up linked tasks** on and **Create a task** off. The resolved event matches it and wakes the task subscribed to its `url`. An event for an alert gritz never saw fire has no subscribed task, so this rule does nothing for it rather than create a task. ## The URL is the subscription key [Section titled “The URL is the subscription key”](#the-url-is-the-subscription-key) gritz decides which task an event belongs to by its `url`: an event wakes the tasks subscribed to that URL. A task is subscribed to the `url` of the event that created it, and to any link an agent creates with `subscribe=true`. For most URLs, gritz uses the URL exactly as sent, so every event about the same resource must send the same URL, byte for byte. A different query string, a trailing slash or a different host name is a different resource, and the event won’t wake the task the first event created. GitHub and Jira URLs are the exception: gritz normalises them as it does for their native events, so a custom event about a GitHub pull request or a Jira issue wakes the task subscribed to it, whichever form of the URL each side used. The [envelope reference](/pr/2063/reference/custom-event-envelope/#url) lists the forms. Pick a URL that a person can open, such as the alert’s page in the alerting system, and send exactly that string in every event about the alert. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) | Status | Response body | Cause | | ------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `400` | `invalid envelope: …` | The body isn’t valid JSON, has a field the envelope doesn’t define, has a field of the wrong type (for example an attr value that is a string rather than a list), or is larger than 1 MiB. | | `400` | `unknown event type "…"` | `type` is empty or doesn’t name one of the organisation’s custom types. Check **Events → Custom Schemas**. | | `400` | `url is required` | `url` is missing or empty. | | `400` | `url "…" must be an absolute http or https URL` | `url` is relative, has no host, or uses another scheme. | | `400` | `attr "body" must be sent as the envelope's "body" field` | `body` or `url` was sent inside `attrs`. Send it as the top-level field. | | `400` | `attr "…" not declared by event type "…"` | `attrs` has a key the type doesn’t declare. Add the attribute to the type, or drop it from the envelope. | | `401` | `bearer token required` | No `Authorization: Bearer …` header. A browser session cookie isn’t accepted. | | `401` | `invalid or expired token` | The key is wrong, deleted or expired. | | `403` | `permission denied` | The token can’t create events, for example a task’s own token. Use an API key. | | `200` | `{"routed": 0}` | No public rule for the type matched the event, or a rule matched but no task is subscribed to the `url` and the rule doesn’t create tasks. |

# Custom event envelope

> The request and response of POST /webhook/custom, with every field, its validation, authentication and status codes.

The custom events webhook accepts one event per request. The [custom events guide](/pr/2063/integrations/custom-events/) shows how to set it up; this page is the precise contract. ## Request [Section titled “Request”](#request) 
```plaintext
POST /webhook/custom
Authorization: Bearer xat_…
Content-Type: application/json
```
 The full URL is on **Settings → Organisation**, in the **Custom Events** card; for gritz.dev it is `https://gritz.dev/webhook/custom`. The webhook only handles `POST`. ### Authentication [Section titled “Authentication”](#authentication) * The request must carry `Authorization: Bearer <token>`. A request without it gets `401 bearer token required`, even from a browser with a signed-in session: the webhook doesn’t accept session cookies. * The token is an API key (`xat_…`) from the **Keys** page. A wrong, deleted or expired key gets `401 invalid or expired token`. * The token must hold the `event:create` scope, or the request gets `403 permission denied`. API keys hold every scope. A task’s own token does not hold `event:create`. * The event belongs to the key’s organisation and is checked against that organisation’s custom event types. It has no actor, so only the organisation’s public routing rules can match it. ### Body [Section titled “Body”](#body) A JSON object of at most 1 MiB: 
```json
{
  "type": "alert",
  "url": "https://alerts.example.com/alerts/4211",
  "body": "checkout-api error rate above 5% for 10 minutes",
  "attrs": {"severity": ["critical"], "service": ["checkout-api"]},
  "details": {"runbook": "https://wiki.example.com/runbooks/checkout-api"}
}
```
 Fields other than the five below are rejected, as are fields of the wrong JSON type. | Field | Type | Required | Validation | | --------- | ----------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `type` | string | yes | Must name one of the organisation’s custom event types, as defined on **Events → Custom Schemas**. A type named like a built-in GitHub or Jira type still only resolves to the custom one. | | `url` | string | yes | Must be non-empty and an absolute `http` or `https` URL with a host. Only GitHub and Jira URLs are normalised: see [`url`](#url). | | `body` | string | no | The event’s text. Defaults to the empty string. | | `attrs` | object of string → array of strings | no | Every key must be an attribute the type declares, other than `body` and `url`. | | `details` | object of string → string | no | Not validated. | #### `type` [Section titled “type”](#type) The custom type’s name, which matches `^[a-z][a-z0-9_]{0,63}$`. The type’s label becomes the event’s description on the task’s timeline. #### `url` [Section titled “url”](#url) The resource the event is about, and the key that routes it: an event wakes the tasks subscribed to its `url`, and a task created by the event is subscribed to it. gritz normalises GitHub and Jira issue URLs to one key per issue, as it does for their native events, so a custom event about a GitHub pull request or a Jira issue wakes the task subscribed to it: | `url` | Key | | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | | `https://github.com/{owner}/{repo}/issues/{n}` or `/pull/{n}`, with any further path segments, query or fragment | `https://github.com/{owner}/{repo}/issues/{n}` or `/pull/{n}` | | `https://api.github.com/repos/{owner}/{repo}/issues/{n}` or `/pulls/{n}`, with any further path segments, query or fragment | `https://github.com/{owner}/{repo}/issues/{n}` or `/pull/{n}` | | `https://{site}.atlassian.net/browse/{KEY}`, with any further path segments, query or fragment | `https://{site}.atlassian.net/browse/{KEY}` | | `https://{site}.atlassian.net/rest/api/{version}/issue/{KEY}`, with any further path segments, query or fragment | `https://{site}.atlassian.net/browse/{KEY}` | The host must match exactly (`github.com`, not `www.github.com`), and the key always uses `https`. A Jira REST URL with a numeric issue id instead of a key, and a GitHub API comment URL (`/repos/{owner}/{repo}/issues/comments/{id}`), are not normalised. Every other URL is used exactly as sent, so events about the same resource must send the same URL byte for byte. #### `body` [Section titled “body”](#body-1) The event’s text, passed to the agent. Rules match on it through the `body` attribute every custom type declares. #### `attrs` [Section titled “attrs”](#attrs) The values routing rule conditions match on, keyed by attribute. Each value is a list of strings; a condition matches when any value in the list satisfies it. An attribute the type declares may be omitted, in which case conditions on it don’t match. Sending `body` or `url` here is an error: send them as the top-level fields, from which their attributes are derived. #### `details` [Section titled “details”](#details) Free-form key/value strings stored with the event and shown with it to the agent and in the Web UI. Rules can’t match on them. ## Response [Section titled “Response”](#response) A valid event gets `200 OK` with a JSON body: 
```json
{"routed": 1}
```
 `routed` is the number of tasks the event was delivered to: tasks created by the matching rule, or existing tasks subscribed to the event’s `url`. It is `0` when no public rule for the type matches, or when a rule matches but no task is subscribed to the `url` and the rule doesn’t create tasks. Errors are plain text. ## Status codes [Section titled “Status codes”](#status-codes) | Status | Body | Cause | | ------ | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | | `200` | `{"routed": n}` | The event was valid and routed to `n` tasks, possibly none. | | `400` | `invalid envelope: …` | The body is not a JSON object matching the envelope: invalid JSON, an unknown field, a field of the wrong type, or more than 1 MiB. | | `400` | `unknown event type "…"` | `type` is empty or not one of the organisation’s custom types. | | `400` | `url is required` | `url` is missing or empty. | | `400` | `url "…" must be an absolute http or https URL` | `url` is relative, has no host, or has another scheme. | | `400` | `attr "…" must be sent as the envelope's "…" field` | `attrs` has a `body` or `url` key. | | `400` | `attr "…" not declared by event type "…"` | `attrs` has a key the type doesn’t declare. | | `401` | `bearer token required` | No `Authorization: Bearer` header. | | `401` | `invalid or expired token` | The bearer token is not a valid, unexpired API key or gritz token. | | `403` | `permission denied` | The token lacks the `event:create` scope. | | `500` | `internal error` | The server failed to load the custom types or to route the event. |

# Agent tools

> The gritz tools every agent gets (get_my_task, update_my_task, create_link, report and get_github_token), what gritz tells agents to do with them, and how to write instructions that use them.

gritz adds an MCP server named `gritz` to every agent it runs, alongside the MCP servers in the task’s [workspace](/pr/2063/concepts/workspaces/). Its tools let the agent read and update its own task, and nothing else: they work with a token that only grants access to that task (see [Task tokens](/pr/2063/concepts/orgs-members-keys/#task-tokens)). ## What agents are told [Section titled “What agents are told”](#what-agents-are-told) On a task’s first run, before your instructions, gritz tells the agent to: * name the task with `update_my_task` if it has no name; * create a link with `subscribe=true` for each resource it creates, such as a pull request, an issue or a comment, so replies reach the task even after it finishes, and `subscribe=false` for reference links it didn’t create; * prefer URLs a person can open over API URLs; * use `report` for anything you should see, since its text replies aren’t shown; * answer questions or problems on the platform the latest instruction or event came from, such as the pull request, and say which task it is from; * call `get_my_task` if it needs to check for updates mid-run. Then it gives the agent the task: its instructions, events and links, so it doesn’t need a tool call to start. On later runs the agent gets only what is new. See [Instructions and runs](/pr/2063/concepts/tasks/#instructions-and-runs). ## Tools [Section titled “Tools”](#tools) ### `get_my_task` [Section titled “get_my_task”](#get_my_task) Returns the task: its ID, name, status, workspace, [namespace](/pr/2063/concepts/namespaces/) and URL, its links, and its instructions and events in order. Reports and status changes aren’t included. ### `update_my_task` [Section titled “update_my_task”](#update_my_task) Renames the task. It takes `name`, the new name. Agents can’t change anything else about their task, including its auto-archive delay. ### `create_link` [Section titled “create_link”](#create_link) Links the task to an external resource, and appears on the task’s timeline and in its sidebar. | Parameter | | | ----------- | ------------------------------------------------------------------------- | | `url` | The resource’s URL. | | `relevance` | How the resource relates to the task, such as “PR implementing the fix”. | | `title` | Optional. A title to show for the link. | | `subscribe` | Optional. `true` to have events about the resource delivered to the task. | A subscribed link is how a task hears about review comments on its pull request, or replies on its Jira issue. Which events wake it is up to the organisation’s [routing rules](/pr/2063/concepts/routing-rules/). See [Events and links](/pr/2063/concepts/events-and-links/). ### `report` [Section titled “report”](#report) Posts `message` to the task’s timeline. This is how an agent tells you what it did, what it found or what is blocking it: the agent’s own replies only appear in the task’s log. ### `get_github_token` [Section titled “get_github_token”](#get_github_token) Returns a short-lived GitHub token for the organisation’s GitHub App installation. Only tasks whose workspace has the `github_token` [capability](/pr/2063/operators/workspaces-yaml/#capabilities) get this tool. It is meant for one-off commands that need a raw token: a workspace can set up git and the GitHub MCP server to get their tokens on their own, as the capabilities example shows. ## Writing instructions that use them [Section titled “Writing instructions that use them”](#writing-instructions-that-use-them) The agent already uses these tools as above without being asked. Mention them when you want something specific: * **To get a summary where you’ll see it**: “When you’re done, report a summary of the changes and anything you couldn’t do.” * **To keep a task listening**: “Open a draft pull request and link it with subscribe=true.” The task finishes, and a review comment on the pull request wakes it if a routing rule matches. * **To link context you gave it**: “Link the incident page as a reference, not subscribed.” * **To name it predictably**: “Name this task `deps: bump <package>`.” The agent’s other tools, such as for GitHub or Jira, come from the MCP servers and credentials in its workspace. Ask your operator what a workspace provides, or see [`workspaces.yaml`](/pr/2063/operators/workspaces-yaml/).

# CLI

> Use the gritz CLI to create, list and update tasks, read a task's log, open a shell in its sandbox and get desktop notifications, and configure its server and API key.

The `gritz` binary is the CLI as well as the runner and server. Release binaries for Linux are attached to each [GitHub release](https://github.com/gritzapp/gritz/releases); to build it from a checkout, run `mise run install`. ## Configuration [Section titled “Configuration”](#configuration) The CLI authenticates with an [API key](/pr/2063/concepts/orgs-members-keys/#api-keys), and acts in the organisation the key belongs to. Create one on the **Keys** page and save it in `config.json` in the gritz config directory: 
```json
{
  "token": "xat_..."
}
```
 The config directory is `GRITZ_CONFIG_DIR` if set, otherwise `gritz` under your user config directory: `~/.config/gritz` on Linux, `~/Library/Application Support/gritz` on macOS. A [runner](/pr/2063/operators/runner/) on the same machine reads the same file. Every command talks to `https://gritz.dev` unless `--server` (`-s`) or the `GRITZ_SERVER` environment variable names another server: 
```bash
export GRITZ_SERVER=https://gritz.example.com
```
 `gritz notify` and `gritz mcp` are different: they take the key from `--token` or `GRITZ_TOKEN` rather than `config.json`, and the server only from `--server`. ## Tasks [Section titled “Tasks”](#tasks) ### `gritz task create` [Section titled “gritz task create”](#gritz-task-create) Creates a task and starts it straight away, then prints it as JSON. 
```bash
gritz task create -r my-runner -w pets-workshop \
  -i "Add a --json flag to the list command and open a pull request."
```
 | Flag | | | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `--runner`, `-r` | The [runner](/pr/2063/concepts/runners/) to run on. Required. | | `--workspace`, `-w` | The [workspace](/pr/2063/concepts/workspaces/). Defaults to `default`. | | `--instruction`, `-i` | An instruction. Repeat it for several. | | `--name`, `-n` | The task’s name. The agent names it if you don’t. | | `--auto-archive` | The [auto-archive](/pr/2063/concepts/tasks/#auto-archive) delay, such as `1h` or `24h`. `0`, the default, is never; a negative value archives the task as soon as it finishes. | The **Workspaces** page in the Web UI lists runner IDs and their workspaces. ### `gritz task list` [Section titled “gritz task list”](#gritz-task-list) Prints the organisation’s 50 newest unarchived tasks as JSON, with their status, runner, workspace and URL. ### `gritz task update` [Section titled “gritz task update”](#gritz-task-update) Changes a task. 
```bash
gritz task update 1234 --start -i "Also update the README."
```
 | Flag | | | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | | `--add-instruction`, `-i` | Add an instruction. Repeat it for several. | | `--start`, `-r` | Start the task, as the Web UI does when you send an instruction. A running task isn’t interrupted: it runs again when its current run ends. | | `--name`, `-n` | Rename the task. | | `--auto-archive` | Set the auto-archive delay. | An instruction added without `--start` waits on the task until something else starts it, such as an event or a later `--start`. Every `gritz task update` also sets the task’s auto-archive delay: to `--auto-archive` when it is given, and otherwise to never. Pass `--auto-archive` again to keep a delay the task already had. Cancelling, restarting and archiving tasks are done in the [Web UI](/pr/2063/using/web-ui/#the-task-page). ## `gritz logs` [Section titled “gritz logs”](#gritz-logs) Prints a task’s log: the setup commands, the agent’s output and gritz’s own lines, as the Web UI’s **Logs** view shows them. It works for any task in the organisation, including tasks whose sandbox is gone. 
```bash
gritz logs 1234     # print the log so far
gritz logs -f 1234  # and keep following it
```
 `--interval` sets how often `-f` checks for new output, `2s` by default. ## `gritz shell` [Section titled “gritz shell”](#gritz-shell) Opens an interactive shell in a finished task’s sandbox, to look at what the agent left behind: 
```bash
gritz shell 1234
```
 The runner starts the sandbox again with a shell in place of the agent. It works whatever the runner’s backend and wherever it runs: the server relays the session, so you need no access to the runner. See [A shell in the sandbox](/pr/2063/operators/debugging/#a-shell-in-the-sandbox). ## `gritz notify` [Section titled “gritz notify”](#gritz-notify) Stays running and shows a desktop notification each time one of the organisation’s tasks completes, fails or is cancelled. 
```bash
GRITZ_TOKEN=xat_... gritz notify
```
 `--title` sets the notifications’ title, `gritz` by default. It uses `notify-send` on Linux and the system notifications on macOS and Windows. ## Other commands [Section titled “Other commands”](#other-commands) * `gritz mcp` runs a local MCP server that lets Claude Code, Cursor and other MCP clients create and manage tasks. * `gritz runner`, `gritz download`, `gritz workspaces` and `gritz containers` are for running a runner; see [Runner](/pr/2063/operators/runner/) and [Debugging](/pr/2063/operators/debugging/). * `gritz version` prints the CLI’s version.

# Web UI

> A tour of the gritz Web UI, the task list and task page, schedules, events and routing rules, workspaces, members, keys and settings.

The Web UI is served by the gritz server under `/ui/`, for example `https://gritz.dev/ui/`. It updates live: task statuses, timelines and logs change as they happen, without reloading. The dot next to the organisation selector shows whether the live connection is up. The bar at the top links to every page, and holds the organisation selector, the light and dark theme toggle, **Settings** and **Logout**. Press Ctrl+K (⌘K on a Mac) anywhere to jump to a task by name. ## Tasks [Section titled “Tasks”](#tasks) **Tasks** lists the organisation’s tasks, newest first, with their runner, workspace and [status](/pr/2063/concepts/tasks/#statuses). A `command:` badge next to the status is an action the runner hasn’t carried out yet. Turn on **Show archived** to include archived tasks, and archive or unarchive a task from its row. **+ Task** creates a task. Pick a runner, then one of its workspaces; the name, [namespace](/pr/2063/concepts/namespaces/) and [auto-archive](/pr/2063/concepts/tasks/#auto-archive) delay are optional. The form remembers the last runner and workspace you used. The task is created as a draft, and starts when you send its first instruction. ## The task page [Section titled “The task page”](#the-task-page) The sidebar on the left holds the task’s status and name, its three views, its details (runner, workspace, namespace, created and updated times), its links, and its actions: * **Archive** or **Unarchive**. When an auto-archive delay is counting down, the time left shows next to it. * **Cancel**, while the task is pending or running. * **Restart**, once it is running or finished. * **Auto-archive**, to change the delay: never, immediately, 1 hour, 6 hours, 24 hours or 7 days. The arrow at the top collapses the sidebar to icons. ### Timeline [Section titled “Timeline”](#timeline) The timeline is everything that happened to the task, in order: your instructions, events from GitHub, Jira and custom sources, the agent’s reports, links it created, and status changes with who caused them. It opens at the latest entry and loads older ones as you scroll up. The box at the bottom sends an instruction: Enter sends it, Shift+Enter adds a new line. A finished task starts again with it; a running task picks it up when its current run ends. See [Instructions and runs](/pr/2063/concepts/tasks/#instructions-and-runs). ### Logs [Section titled “Logs”](#logs) The task’s log, as the sandbox writes it: setup commands, the agent’s messages and tool calls, and gritz’s own lines. It follows new output while the task runs. Declared [secrets](/pr/2063/operators/secrets/) are masked. ### Shell [Section titled “Shell”](#shell) A terminal in the task’s sandbox, for looking at what the agent left behind. It can be opened once the task has finished, and works like [`gritz shell`](/pr/2063/using/cli/#gritz-shell): the runner starts the sandbox again with a shell in place of the agent. ## Schedules [Section titled “Schedules”](#schedules) **Schedules** lists the organisation’s [schedules](/pr/2063/concepts/schedules/) with their cron expression, timezone, next run and workspace, and the task each created last. From each row you can turn a schedule on or off, run it now, edit it or delete it. **+ Schedule** creates one. ## Events [Section titled “Events”](#events) **Events** has three tabs: * **Routing Rules**: the organisation’s [routing rules](/pr/2063/concepts/routing-rules/), in the order they are checked, with their event type, conditions and action. Reorder them with the arrows, edit or remove them, add one with **+ Rule**, or try an event against them with **Test**. * **Recent Events**: the latest events delivered to the organisation’s tasks. Open one to see its description, URL, data and the task it reached. * **Custom Schemas**: the organisation’s custom event types. See [Custom events](/pr/2063/integrations/custom-events/). ## Workspaces [Section titled “Workspaces”](#workspaces) **Workspaces** lists the [workspaces](/pr/2063/concepts/workspaces/) the organisation’s [runners](/pr/2063/concepts/runners/) have registered, with their description, runner and when they were last registered. Filter by runner, and **Clear** to remove the listed runner’s workspaces, or every runner’s. ## Members and Keys [Section titled “Members and Keys”](#members-and-keys) **Members** lists the organisation’s members and their role. The owner adds members by email here and removes them. **Keys** lists the organisation’s API keys and creates and deletes them. See [Organisations, members and API keys](/pr/2063/concepts/orgs-members-keys/). ## Settings [Section titled “Settings”](#settings) **Settings** has two tabs: * **Account**: the organisations you own, where you create new ones and delete them, and your linked Atlassian and GitHub accounts. Linking them lets [routing rules](/pr/2063/concepts/routing-rules/#public-rules) recognise your comments as a member’s. * **Organisation**: the URLs and settings that connect the organisation to other systems: the MCP server URL for MCP clients, the custom events webhook URL, the GitHub App installation, and the Atlassian webhook URL and secret. The server’s version is at the bottom of the page.
