# What is gritz?

> gritz runs coding agents such as Claude Code and Codex in sandboxes, driven by tasks and events.

gritz is an orchestrator for coding agents. It runs agents such as Claude Code, Codex, Cursor and Copilot in parallel, each in its own sandbox, and keeps track of their work in one place. * **Tasks** are the unit of work. A task gives an agent its instructions and runs it in a sandbox built from a workspace: the image, repositories, agent and MCP servers it needs. * **Runners** start the sandboxes, on Docker or Lambda MicroVMs, and stream each agent’s log back to the gritz server, where the Web UI shows it live. * **Events** keep a task going after its first run. When an agent opens a pull request or comments on an issue, it links the resource to its task, and a review comment on that pull request wakes the task up with the new event. Agents and users drive gritz the same way: from the Web UI, the [`gritz` CLI](/pr/2460/using/cli/), or [any MCP client](/pr/2460/integrations/mcp/).

# Agents

> How an agent defines a kind of task, how its triggers create tasks from events, how its link kinds decide which events reach its tasks, how claims stop two agents working on the same resource, and testing agents with a test event.

An agent is one kind of task in an organisation, such as “implement a Jira issue” or “answer `@gritz` on pull requests”. Every task belongs to exactly one agent, and the agent decides four things about its tasks: * **The template** every task of the agent starts from: where it runs and with what. * **Triggers**, which create a new task of the agent when a matching event arrives: a [GitHub](/pr/2460/integrations/github/) comment, a [Jira](/pr/2460/integrations/jira/) label, a [custom event](/pr/2460/integrations/custom-events/). * **[Schedules](/pr/2460/concepts/schedules/)**, which create a new task of the agent on a cron schedule. * **Link kinds**, the only links its tasks may subscribe to, and the events each one delivers to the task. The coding agent that runs in a task’s sandbox, such as Claude Code or Codex, is set by the task’s [workspace](/pr/2460/concepts/workspaces/), or by one of the [features](#the-template) the agent picks, not here. Agents are on the **Agents** page of the [Web UI](/pr/2460/using/web-ui/#agents). **+ Agent** creates one, clicking an agent’s name opens it for editing, and its **Run** button opens a new task of the agent with its prompt filled in. MCP clients manage them with [`put_agent`](/pr/2460/integrations/mcp/#agents) and the other agent tools. An organisation needs an agent before it can create any task, by hand, from a [schedule](/pr/2460/concepts/schedules/) or from an event. An agent with no triggers and no link kinds is just a template for tasks you create yourself. ## The template [Section titled “The template”](#the-template) * **Name**: unique in the organisation. * **Runner** and **Workspace**: where its tasks run. Pick a runner first; the workspace list shows only that runner’s workspaces. * **Variables**: one field per [variable](/pr/2460/operators/workspaces-yaml/#variables) the workspace declares. They are fixed values: every task gets the same ones, and nothing from an event is copied into them. Leave an optional variable empty to use the workspace’s default when each task starts. * **Features**: a switch for each [feature](/pr/2460/operators/workspaces-yaml/#features) the workspace declares, with its description. Each feature that is on adds its environment, secrets, MCP servers and setup commands to the workspace’s, and can replace its coding agent. Their order matters: where two set the same thing, the later one wins, and their setup commands run in that order. The order is the one you turn them on in, and each feature that is on shows its position. To move a feature to the end, turn it off and on again. Changing the runner or workspace clears the features, as it clears the variables. * **Prompt**: the first instruction of the tasks its triggers and [schedules](/pr/2460/concepts/schedules/) create. A trigger or schedule can add [its own prompt](#the-triggers-prompt) as a second instruction. Left blank, the tasks start with only the trigger’s or schedule’s prompt, or with no instruction when that is blank too. A triggered task’s first event is the one that created it, so the agent gets the event’s text either way. Tasks you create by hand get their own instructions instead. * **Auto-archive**: the [auto-archive](/pr/2460/concepts/tasks/#auto-archive) delay of its tasks. The workspace, variables and features are checked when you save the agent, and it isn’t saved if the workspace isn’t registered on the runner, doesn’t accept the variables, or doesn’t declare one of the features. A saved feature the workspace no longer declares is flagged in the editor: turn it off to save the agent. A task copies its runner, workspace, auto-archive delay, variables and features from the agent when it is created. Editing the agent changes the tasks it creates from then on; tasks it already created keep theirs. The runner checks a task’s variables again when it starts the task. If the workspace’s `variables:` changed after you saved the agent, and no longer accepts its values (a new required variable, or one the agent sets that the workspace no longer declares), its triggers still create tasks, and each task fails with the reason on its timeline. The same goes for a feature the workspace no longer declares, and creating a task by hand fails until the agent is fixed. Edit the agent to fix it. ## Triggers [Section titled “Triggers”](#triggers) A trigger creates a task of its agent when an event matches it. It never wakes an existing task: that is what [link kinds](#link-kinds) do. ### Matching [Section titled “Matching”](#matching) A trigger matches an event by: * **Event type**: the event’s source and type, such as a GitHub pull request review comment, a Jira issue comment, or one of the organisation’s custom types. * **Conditions**, each an attribute, an operator and a value. The attributes on offer depend on the event type. Every type has `body`, the event’s text, and `url`, the event’s own URL (a comment’s URL rather than its issue’s); built-in types add others, such as the users mentioned in a comment, an issue’s new label or its new assignee. See [Event types](/pr/2460/reference/event-types/) for every built-in type and its attributes. | Operator | Holds when the attribute’s value | | ---------- | -------------------------------------------------------------------------- | | `equals` | is exactly the value | | `prefix` | starts with the value | | `contains` | contains the value anywhere | | `glob` | matches the value as a pattern, such as `internal/store/**` or `release/*` | A `glob` pattern must match the whole value: | Pattern | Matches | | ------------------------ | --------------------------------------------------------------- | | `*` | any run of characters except `/` | | `**` | as a whole path segment, any number of segments, including none | | `?` | any one character except `/` | | `[abc]`, `[a-z]`, `[^a]` | one character from the class | | `{a,b}` | either alternative | | `\x` | a literal `x` | So `**/*.sql` matches every `.sql` file at any depth and `{go.mod,go.sum}` matches either file. Because `*` stops at `/`, use `prefix` or `contains` for URLs and text. An agent with a malformed pattern can’t be saved. Comparisons are exact and case-sensitive. An attribute can have several values, such as the labels on an issue, and a condition holds when any of them satisfies it. A condition on an attribute the event doesn’t have never holds. A trigger matches when every condition holds. A trigger with no conditions matches every event of its type. ### One task per agent [Section titled “One task per agent”](#one-task-per-agent) An agent’s triggers are checked from the top of its list down, and the first one that matches is the only one that acts: an event creates at most one task per agent. Put narrow triggers above broad ones. The arrows on each trigger change its position. Agents don’t affect each other. Every agent whose trigger matches creates its own task, so a reviewer agent and an implementer agent can both act on the same event. To have one agent stay out of the way of another’s tasks, use [claims](#claims). ### The trigger’s link [Section titled “The trigger’s link”](#the-triggers-link) A trigger can name one of its agent’s link kinds as its **Link**. The task it creates then gets a subscribed link of that kind to the event’s resource, so the next events about the same pull request or issue reach that task, if the kind lists them. Only kinds whose link type the event type can name are offered. An event whose URL isn’t a resource of the kind’s type, such as a check run outside GitHub Actions for a workflow run kind, still creates the task, without the link. Without a link, the created task isn’t subscribed to anything unless its agent creates links itself. ### The trigger’s prompt [Section titled “The trigger’s prompt”](#the-triggers-prompt) A trigger can have its own **Prompt**, an instruction for the tasks it creates only. The task gets it after the agent’s prompt, as a second instruction, or as its only one when the agent has none. Use it when an agent’s triggers need different instructions, such as “Review the pull request” on one and “Answer the comment” on another, while the agent’s prompt holds what they share. ## Link kinds [Section titled “Link kinds”](#link-kinds) A link kind is a kind of subscribed link the agent’s tasks may create. An agent creates links with the [`create_link`](/pr/2460/using/agent-tools/#create_link) tool, and passes a kind to subscribe; gritz tells it the kinds its agent has. A link with no kind is a plain reference: it receives no events. See [Events and links](/pr/2460/concepts/events-and-links/). Each link kind has: * **Link type**: the kind of resource its links name, such as a GitHub pull request or a Jira issue. See [Link types](/pr/2460/reference/event-types/#link-types). * **Kind**: its name, which agents pass to `create_link`. Defaults to the link type’s name, such as `github.pr`; give one only when the agent has two kinds of the same type, such as `owned-pr` for the pull requests its tasks open and `github.pr` for the ones they only watch. * **Claim**: an optional name the links of this kind hold. See [Claims](#claims). * **Events**: the event types a link of this kind delivers, each with optional conditions on the event’s attributes, as a [trigger’s](#triggers). Only event types that can name the link type are offered. A kind with no events checked delivers nothing; its links still hold its claim. Each event type also has: * **Wake**: delivering one of its events wakes the task. On for a new event type. * **Public**: also deliver its events from people who aren’t members of the organisation. See [Members and public](#members-and-public). An event on a subscribed link’s resource is delivered to the task when the link’s kind lists the event’s type and the event meets every condition on that type. When that event type has **Wake**, delivery wakes the task: a finished task starts a new run, and a running one runs again when its current run ends. Without it, the event is only added to the task, which is left as it is: the agent sees it the next time something else wakes the task, such as an instruction or an event that wakes. Use that for events worth knowing about but not worth a run, such as successful checks. A task with several links to the same resource gets each event once. Delivery doesn’t depend on any trigger: an event can be delivered to one task and create another through a trigger, of the same agent or another one. Which events a link receives is read from its kind on the agent each time an event arrives, so editing a kind’s events or their conditions applies to existing links too. Removing a kind stops delivery to the links created with it. ## Claims [Section titled “Claims”](#claims) A claim is a name, such as `pr-owner`, that a link kind gives its links. A task holds the claim on its link’s resource while the task is unarchived. A trigger’s **Yield to claims** lists claims: the trigger creates no task while any unarchived task in the organisation holds one of them on the event’s resource. The event isn’t passed to the holder by the trigger; the holder gets it only if its own link kind lists the event type. Claims are free-form names shared across the organisation: a trigger can yield to a claim held by another agent’s tasks. Nothing checks that a claim you yield to is given by some link kind, so a misspelled name yields to nothing. A test event shows which triggers yield. A link keeps the claim it was created with: changing a kind’s claim only applies to links created after the change. A task holds its claims until it is archived. For example, an implementer agent’s tasks link the pull requests they open with an `owned-pr` kind that has the claim `pr-owner`. A responder agent answers `@gritz` mentions on pull requests, with a trigger for **GitHub: PR Comment** that has the condition `mention equals gritz`, yields to `pr-owner`, and links the pull request. A mention on a pull request an implementer task opened creates no responder task, and reaches the implementer task if its `owned-pr` kind lists comments. A mention anywhere else creates a responder task. For the next mention on that pull request to wake the responder task rather than create another, give the responder’s link kind a claim too, such as `responding`, and add it to the trigger’s yield list. ## Members and public [Section titled “Members and public”](#members-and-public) By default an agent only acts on events from members of the organisation: a GitHub or Jira event counts as a member’s when its author has linked that account to a gritz user in the organisation. A **Public** trigger also creates tasks for events from anyone else, and a link kind delivers them for each event type it marks **Public**, as long as the event belongs to the organisation: * a GitHub event from a repository where the organisation installed the gritz GitHub App; * a Jira event sent to the organisation’s Atlassian webhook; * a custom event sent with one of the organisation’s API keys. Make a trigger or a link kind’s event type public to let people outside the organisation, such as outside contributors or a team without gritz accounts, reach it. A link kind can deliver failed checks from anyone, say, while keeping comments to members. Custom events have no author, so triggers for custom types must be public: gritz refuses to save an agent with one that isn’t, and a link kind only delivers custom events of a type it marks public. See [Why custom event triggers must be public](/pr/2460/integrations/custom-events/#why-custom-event-triggers-must-be-public). ## Testing with a test event [Section titled “Testing with a test event”](#testing-with-a-test-event) **Test event** on the **Agents** page opens a form to compose an event: its type, an optional description, its attributes such as `body` and `url`, and details. * **Dry run** shows, for each agent, which trigger would match the event and whether it would create a task or yield, and to which tasks, and which tasks the event would be delivered to, through which link kind, and whether it would wake each one. It changes nothing. * **Fire** routes the event for real, as if it had arrived from its source: it delivers the event to tasks, waking them where it would, and creates tasks. It doesn’t post anything back to GitHub or Jira. Both run the event only for the organisation you are in, and both reject an event that doesn’t fit its type: the URL must be an absolute `http` or `https` URL, and every attribute must be one the type declares. An event without a description gets its type’s label. A GitHub or Jira event runs as yours, so member-only triggers and link kinds admit it. A [custom event](/pr/2460/integrations/custom-events/) is routed like one posted to the webhook: it has no actor, so only public triggers and the public event types of link kinds admit it. ## Deleting an agent [Section titled “Deleting an agent”](#deleting-an-agent) An agent can’t be deleted while it has an unarchived task: archive its tasks first. Deleting it also deletes its [schedules](/pr/2460/concepts/schedules/). Its archived tasks keep their history.

# Events and links

> How tasks link to pull requests, issues and other resources, how a subscribed link lets an event on that resource wake the task, and where events show up.

Tasks don’t end when their agent stops. An agent that opens a pull request links it to its task, and a review comment on that pull request later wakes the task up to address it. ![A sequence diagram: the agent creates a pull request on GitHub and a subscribed link to it, and its task completes. A reviewer comments “gritz: fix the failing test” on the pull request, GitHub’s webhook restarts the agent, and the agent pushes a fix.](/pr/2460/_astro/events.yf17GTzA_1RLqTL.svg) ## Links [Section titled “Links”](#links) A link connects a task to an external resource: a pull request, an issue, a Jira ticket, a dashboard. It has: * a **URL**, ideally one a person can open; * a **relevance**, saying how the resource relates to the task, such as “PR implementing the fix”; * an optional **title** to display; * an optional **kind**, one of the [link kinds](/pr/2460/concepts/agents/#link-kinds) of the task’s agent. A link with a kind is subscribed: events about the resource reach the task. A link without one is a plain reference. Agents create links with the [`create_link`](/pr/2460/using/agent-tools/#create_link) tool, and gritz tells every agent to create a subscribed link for each resource it creates, such as a pull request, an issue or a comment, with one of its agent’s link kinds. A task created by an agent’s [trigger](/pr/2460/concepts/agents/#the-triggers-link) can also get a subscribed link to the resource of the event that created it. Links are listed in the task page’s sidebar, with their kind and [claim](/pr/2460/concepts/agents/#claims), and appear on its timeline. They can’t be removed: a task stays subscribed until it is archived. ## Subscriptions [Section titled “Subscriptions”](#subscriptions) A subscribed link names a resource of its kind’s link type: a GitHub pull request or issue, a GitHub Actions workflow run, a Jira issue, or a custom event’s URL. When an event arrives about the same resource, gritz delivers it to every task with a subscribed link to it whose kind lists the event’s type, rather than starting a new task. The resource has to match: * **GitHub and Jira URLs** are matched by the issue, pull request, workflow run or Jira issue they point at. A comment’s URL, a pull request’s `/files` page and the API URL of the same pull request all match a link to the pull request, and every job of a workflow run matches the run. A subscribed link is stored with the resource’s own URL, and creating one with a URL that isn’t a resource of its kind’s type fails. * **Custom events’ URLs** must match exactly, character for character. A different query string or a trailing slash is a different resource. See [The URL is the subscription key](/pr/2460/integrations/custom-events/#the-url-is-the-subscription-key). Archived tasks aren’t subscribed to anything. An event about a resource whose only subscriber is archived is treated as if nobody were subscribed. ## How an event reaches a task [Section titled “How an event reaches a task”](#how-an-event-reaches-a-task) Events come from the [GitHub](/pr/2460/integrations/github/) and [Jira](/pr/2460/integrations/jira/) integrations and from your own systems through [custom events](/pr/2460/integrations/custom-events/). For each event, in each organisation it belongs to, gritz: 1. **Delivers it to subscribed tasks.** Every task with a subscribed link to the event’s resource gets the event, if the link’s kind lists the event’s type, the event meets that type’s conditions, and the event’s author is a member or the kind marks that type [public](/pr/2460/concepts/agents/#members-and-public). Delivery wakes the task if the kind marks that type **Wake**; otherwise the event waits on the task until something else wakes it. 2. **Runs every agent’s triggers.** Each [agent](/pr/2460/concepts/agents/) whose trigger matches the event creates a task of its own, with the event as its first event, unless the trigger [yields](/pr/2460/concepts/agents/#claims) to a task that holds a claim on the resource. The two steps are independent: an event can wake one task and create another. An event that no link kind delivers and no trigger matches does nothing. A woken task that has finished starts a new run. A running task isn’t interrupted: it runs again as soon as its current run ends. Either way the agent gets the event at the start of its next run. ## Where events show up [Section titled “Where events show up”](#where-events-show-up) * **The task’s timeline** shows each event delivered to the task, with its source, description, URL and text, next to the instructions and the agent’s reports. * **Events → Recent** in the [Web UI](/pr/2460/using/web-ui/#events) lists the organisation’s latest delivered events. Each one’s page shows the task it was delivered to. Events that reached no task aren’t stored, so they don’t appear. * **The test event form** on the **Agents** page shows what an event would do before you rely on it. See [Testing with a test event](/pr/2460/concepts/agents/#testing-with-a-test-event).

# Organisations, members and API keys

> How organisations own tasks, runners and agents, what members and the owner can do, and what CLI logins, API keys and task tokens can access.

## Organisations [Section titled “Organisations”](#organisations) An organisation owns everything in gritz: its tasks, the runners connected to it and their workspaces, agents, custom event types, schedules and API keys. Nothing is shared between organisations, and an event is routed by each organisation’s own [agents](/pr/2460/concepts/agents/). The first time you sign in, gritz creates a personal organisation for you, your default. You can create more under **Settings → Account → My Organisations**, and switch between those you belong to with the selector at the top of the [Web UI](/pr/2460/using/web-ui/). The current organisation is in each page’s `?org=` parameter. A person can belong to at most 20 organisations, counting those they created and those they were added to; deleted organisations don’t count. The server’s operator can change the limit with [`--max-orgs-per-user`](/pr/2460/operators/server/#limits). ## Members [Section titled “Members”](#members) Every member of an organisation can do everything in it: create, run and archive any of its tasks, edit its agents and schedules, and create and delete its API keys. The one exception is managing the organisation itself, which only its owner can do. The owner is whoever created it. | | Members | Owner | | -------------------------------------------- | ------- | ----- | | Tasks, agents, schedules, custom event types | ✓ | ✓ | | API keys, workspaces, integration settings | ✓ | ✓ | | Add and remove members | | ✓ | | Delete the organisation | | ✓ | The owner adds members on the **Members** page, by the email address they sign in with. A person has to have signed in to gritz once before they can be added, and can’t be added once they belong to the maximum number of organisations. The owner can’t be removed. Membership also decides whose GitHub and Jira activity counts as the organisation’s: a trigger or a link kind’s event type that isn’t public acts on events from members who have linked their [GitHub](/pr/2460/integrations/github/#link-your-github-account) or [Atlassian](/pr/2460/integrations/jira/#link-your-atlassian-account) account under **Settings → Account**. See [Members and public](/pr/2460/concepts/agents/#members-and-public). ### Deleting an organisation [Section titled “Deleting an organisation”](#deleting-an-organisation) The owner can delete an organisation from **My Organisations**, except their default one. Archive all of its tasks first, so their runners destroy the sandboxes: gritz refuses to delete an organisation with unarchived tasks. Deleting it disables its schedules and stops its API keys from working. ## API keys [Section titled “API keys”](#api-keys) An API key lets a program act for the organisation: a [runner](/pr/2460/concepts/runners/), the [CLI](/pr/2460/using/cli/) in CI, or a system sending [custom events](/pr/2460/integrations/custom-events/). Create one on the **Keys** page. The key, starting with `xat_`, is shown once, when it is created; store it then. People using the CLI on their own machine don’t need a key: [`gritz login`](/pr/2460/using/cli/#configuration) logs them in with the browser, and the CLI then acts as them, like the Web UI. That login stops working when they leave the organisation, or after 30 days without use. Keys are for what runs unattended, such as CI and deployed runners. * A key belongs to the organisation it was created in, not to the member who created it, and keeps working if they leave. * It can do what a member can, in that organisation only, apart from the owner’s actions. * Actions taken with it, such as creating a task, are recorded under the key’s name, so give each key a name that says what uses it. * Keys created in the Web UI don’t expire. Delete a key on the **Keys** page to revoke it. Send it as a bearer token, `Authorization: Bearer xat_…`. The CLI reads it from `--key`, `GRITZ_API_KEY` or its [config file](/pr/2460/using/cli/#logging-in-with-an-api-key); a program calling the [API](/pr/2460/reference/api/) sends it on every request. ## Task tokens [Section titled “Task tokens”](#task-tokens) Agents don’t use API keys. Each task gets a token of its own that can only read and update that task: fetch its instructions, rename it, add links and post reports, through the [agent tools](/pr/2460/using/agent-tools/). It can’t see or change other tasks. The token stops working when the task is archived. A workspace can ask for one more permission for its tasks’ tokens, getting GitHub tokens through the organisation’s GitHub App, with the `github_token` [capability](/pr/2460/operators/workspaces-yaml/#capabilities). The server doesn’t issue these tokens yet, so agents get GitHub access from a token in their workspace’s `secrets:` instead, such as `GH_TOKEN`.

# Runners

> Where a task runs, how runners connect to an organisation, choosing a runner for a task, and what happens when a runner is offline.

A runner is the machine, or service, that runs tasks. It connects to the gritz server, offers a set of [workspaces](/pr/2460/concepts/workspaces/), and starts a sandbox for every task created for it: a Docker container or a Lambda MicroVM, depending on how it is set up. Runners run on infrastructure your team controls: a workstation, a server or a cloud account. That is where the agent’s code runs and where its sandbox’s files live. The gritz server only stores the tasks, events and logs. ## Runners and organisations [Section titled “Runners and organisations”](#runners-and-organisations) A runner connects with an [API key](/pr/2460/concepts/orgs-members-keys/#api-keys), and runs tasks for the organisation that key belongs to. Each runner has an ID, the runner’s hostname unless its operator sets one. That ID is what you pick under **Runner** in an [agent](/pr/2460/concepts/agents/#the-template), for the tasks it creates. The Web UI doesn’t list runners on their own: a runner appears through the workspaces it registers, on the **Workspaces** page and in the runner pickers. **Clear** on the **Workspaces** page removes the registered workspaces, of one runner or all of them, for example after a runner is retired. A running runner registers its workspaces again the next time it starts. ## Choosing a runner [Section titled “Choosing a runner”](#choosing-a-runner) Pick the runner that offers the workspace you need. When several do, pick by where the work should happen: a runner with access to an internal network, a bigger machine, or your own workstation while you try out a workspace. A task stays on the runner it was created for. Each of its runs happens there, in the same sandbox. ## When a runner is offline [Section titled “When a runner is offline”](#when-a-runner-is-offline) A task whose runner isn’t connected stays `pending`. The runner picks up its tasks when it connects again, and starts the runs they are waiting for. A task whose run ended while its runner was down without the runner seeing the result is marked `failed` when the runner comes back. To set up a runner, see [Runner](/pr/2460/operators/runner/) in the operator docs.

# Schedules

> Create tasks of an agent on a cron schedule, in a timezone.

A schedule creates a task on a cron schedule: a nightly dependency bump, a weekly report, an hourly check. Each time it fires it creates a new task of the [agent](/pr/2460/concepts/agents/) it names, starting with the agent’s prompt and then the schedule’s own, and the task starts at once. A schedule belongs to its agent, and is edited with it: under **Starts on** in the agent form on the [Web UI](/pr/2460/using/web-ui/#agents)’s **Agents** page, or with [`put_agent`](/pr/2460/integrations/mcp/#agents). ## Creating a schedule [Section titled “Creating a schedule”](#creating-a-schedule) **Add schedule** under the agent form’s **Starts on** adds one, saved with the agent. Each schedule has: * **Name**: the name of every task it creates. Optional. * **Cron expression**: when to fire. See below. * **Timezone**: the timezone the cron expression is read in. Defaults to your browser’s. * **Prompt**: an instruction for the tasks this schedule creates, after the agent’s prompt. Optional. * **On/off**: the switch on the schedule’s header. A schedule that is off is saved but doesn’t fire. ## The agent [Section titled “The agent”](#the-agent) A schedule names one [agent](/pr/2460/concepts/agents/), and each task it creates takes the agent’s runner, workspace, [auto-archive](/pr/2460/concepts/tasks/#auto-archive) delay, variables and features. Its instructions are the agent’s prompt, then the schedule’s, each only when it is set. A task whose agent and schedule both have no prompt starts with no instruction. The agent is read each time the schedule fires, so a change to the agent applies to the schedule’s next task. Deleting the agent deletes its schedules. The runner checks a task’s variables when it starts the task. If the workspace’s `variables:` changed after the agent was saved, and no longer accepts its values (a new required variable, or one the agent sets that the workspace no longer declares), the schedule still fires, and the task fails with the reason on its timeline. Fix the agent’s variables to fix it. ## Cron expressions [Section titled “Cron expressions”](#cron-expressions) A schedule takes a standard five-field cron expression: minute, hour, day of month, month, day of week. There is no seconds field. These shorthands work too: `@yearly`, `@monthly`, `@weekly`, `@daily` and `@hourly`. | Expression | Fires | | -------------- | ----------------------------- | | `0 9 * * *` | Every day at 09:00 | | `30 6 * * 1-5` | Weekdays at 06:30 | | `0 */4 * * *` | Every four hours, on the hour | | `@weekly` | Sundays at midnight | The expression is evaluated in the schedule’s timezone, so `0 9 * * *` in `Europe/Paris` fires at 09:00 Paris time on both sides of a daylight saving change. An expression or timezone gritz can’t parse is rejected when you save. Times are minute-precise: a schedule fires within a few seconds of the minute it is due. If the server is down when a schedule is due, it fires once when the server is back, however many times it was due in between, and then carries on from the next due time. ## Each run is a new task [Section titled “Each run is a new task”](#each-run-is-a-new-task) Every time a schedule fires it creates a new task. It doesn’t reuse or wait for the previous one, so if the last run is still going, the two run side by side. The agent form shows each saved schedule’s next run, and links to the task it created the last time it fired. The **Agents** list shows an agent’s schedules, with their next runs, under **Starts on**. ## Run now [Section titled “Run now”](#run-now) To run a schedule’s agent without waiting for the schedule, use the agent’s **Run** button, on the **Agents** page or the agent’s page in the Web UI: it opens a new task of the agent with its prompt filled in. The schedule’s next run and last run don’t change. ## Editing, disabling and deleting [Section titled “Editing, disabling and deleting”](#editing-disabling-and-deleting) Changes to a schedule, or to its agent, apply to the tasks it creates from then on; tasks it already created keep their settings. Changing the cron expression or timezone moves its next run. Turning a schedule off clears its next run; turning it back on schedules the next due time from now, without catching up on the runs it missed. Deleting a schedule doesn’t touch the tasks it created.

# Tasks

> What a task is, how instructions and events start its runs, the task statuses, restarting and cancelling, resetting the sandbox, archiving and auto-archive, and the task log.

A task is one piece of work for one agent. It belongs to an [agent](/pr/2460/concepts/agents/), which gives it a [runner](/pr/2460/concepts/runners/) and a [workspace](/pr/2460/concepts/workspaces/), and it holds the instructions and events the agent works from. Each task gets a sandbox of its own, which it keeps until it is archived or its sandbox is [reset](#resetting-the-sandbox). Tasks are created from the [Web UI](/pr/2460/using/web-ui/), the [CLI](/pr/2460/using/cli/), an MCP client, an agent’s [trigger](/pr/2460/concepts/agents/#triggers) or a [schedule](/pr/2460/concepts/schedules/). A task created any of these ways is the same kind of task. ## Instructions and runs [Section titled “Instructions and runs”](#instructions-and-runs) A task does its work in **runs**. A run starts the agent in the task’s sandbox, gives it what is new since the last run, and ends when the agent exits. * **The first run** gets the whole task: its instructions, the events that reached it and its links, after gritz’s own instructions on [the tools it can use](/pr/2460/using/agent-tools/). The workspace’s setup commands run before it, once per sandbox. * **Later runs** get only the instructions and events added since the previous run, and the agent continues the session it had: it remembers what it did before. Two things start a run: * **An instruction.** Sending one from the task page, `gritz task update -i`, or an MCP client starts the task again. If the task is running, the instruction doesn’t interrupt it: the task runs again as soon as the current run ends. * **An event.** An event on a resource the task is [subscribed to](/pr/2460/concepts/events-and-links/), such as a review comment on its pull request, starts it the same way, if the link’s [kind](/pr/2460/concepts/agents/#link-kinds) lists the event’s type. Agents don’t stop by themselves to ask for input. A task that needs an answer from you completes, and the agent says what it needs in its report or on the pull request or issue it is working on. Your next instruction, or a reply on a resource the task is subscribed to, starts the next run. The diagram follows a task on a Docker runner from its creation to the end of its first run: the runner picks it up and starts its sandbox, and the driver there runs the agent and reports the run’s status to the server. [Open the create-task diagram](/pr/2460/diagrams/create-task/) ## Statuses [Section titled “Statuses”](#statuses) | Status | | | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | | `draft` | Created without starting. A draft starts when it is sent its first instruction. | | `pending` | Waiting for its runner to start the run. A task stays pending while its runner is offline. | | `running` | The agent is running. | | `restarting` | A restart was requested; the runner is stopping the current run to start a new one. | | `cancelling` | A cancel was requested; the runner is stopping the run. | | `completed` | The last run ended normally. | | `failed` | The last run failed: a setup command failed, the agent exited with an error, or the sandbox stopped unexpectedly. The reason is on the timeline. | | `cancelled` | The last run was cancelled. | `completed`, `failed` and `cancelled` are the finished statuses. A finished task isn’t over: an instruction or an event starts it again, from where it left off. Next to the status, the Web UI shows the task’s pending **command**, if any: `command:start`, `command:restart`, `command:stop` or `command:reset`. It is what the runner has been asked to do and hasn’t done yet. A `command:start` on a running task is an instruction or event waiting for the current run to end. ## Restarting and cancelling [Section titled “Restarting and cancelling”](#restarting-and-cancelling) * **Restart** runs the task again. The agent continues its session, and is told to carry on if nothing new has arrived. On a running task it stops the current run first, so use it when an agent is stuck. It is available on running and finished tasks. * **Cancel** stops the task. A pending task is cancelled at once; a running or restarting one goes through `cancelling` while the runner stops the agent. The sandbox is kept, so the task can still be started again. ## Resetting the sandbox [Section titled “Resetting the sandbox”](#resetting-the-sandbox) **Reset sandbox** deletes a finished task’s sandbox, and with it any files the agent left there. Use it when the sandbox can no longer start, so every run fails the same way, or when its contents have gone bad: a broken checkout, a confused agent session, an outdated image. A reset doesn’t start the task, and its status stays what it was. The task keeps its instructions, events, links and subscriptions. Its next run, started by an instruction, an event or **Restart**, gets a new sandbox set up from the workspace as it is then, and is run like a first run: the setup commands run again, and the agent starts a new session with the whole task. A reset is available on a finished task with no pending command. To reset a running task, cancel it first. The timeline records the request, and the reset itself once the runner has deleted the sandbox. ### A gone sandbox [Section titled “A gone sandbox”](#a-gone-sandbox) A sandbox can disappear without a reset: a Lambda MicroVM is terminated at the end of its [lifetime](/pr/2460/operators/backends/#lambda-microvms), and a container can be removed outside gritz. The task’s next run can’t start in it: * By default, the run fails with the reason on the timeline, and the run after it gets a new sandbox. * In a workspace with [`auto_reset: true`](/pr/2460/operators/workspaces-yaml/#workspace-fields), the run starts in a new sandbox instead, and the timeline shows “Sandbox reset: previous sandbox gone: …” before it. Either way, the new sandbox is set up as after a reset: the setup commands run again, and the agent starts a new session with the whole task. A sandbox that disappears during a run fails that run, with or without `auto_reset`. ## Archiving [Section titled “Archiving”](#archiving) Archive a task when you are done with it. Archiving: * destroys its sandbox, and with it any files the agent left there; * removes it from the task list (turn on **Show archived** to see it); * stops events from reaching it: an event on one of its links no longer wakes it, and it releases its [claims](/pr/2460/concepts/agents/#claims), so a trigger that yielded to it creates a new task instead. A task can be archived when it is finished or a draft, and has no pending command. **Unarchive** brings it back to the task list, but not its sandbox. ### Auto-archive [Section titled “Auto-archive”](#auto-archive) A task’s auto-archive delay archives it automatically once it has been finished for that long. The default is never. **Immediately** archives it as soon as it finishes, which suits tasks whose result lives elsewhere, such as a pull request. The delay counts from the task’s last change, so a task that is woken up again starts over. The server checks for due tasks about once a minute. Set it on the task’s [agent](/pr/2460/concepts/agents/#the-template), which every task of the agent starts with, or in the task page’s sidebar. Unarchiving a task sets its delay back to never. Agents can’t change their own task’s delay. ## The timeline and the log [Section titled “The timeline and the log”](#the-timeline-and-the-log) Each task has two records, both on its page in the [Web UI](/pr/2460/using/web-ui/): * **The timeline** is what happened to the task: instructions, events, the agent’s reports, links, status changes and who caused them. Agents read the same instructions and events with [`get_my_task`](/pr/2460/using/agent-tools/#get_my_task). * **The log** is the sandbox’s output: setup commands, the agent’s messages and tool calls, and gritz’s own logging. It stays readable after the sandbox is gone, in the Web UI and with [`gritz logs`](/pr/2460/using/cli/#gritz-logs). Credentials declared as [secrets](/pr/2460/operators/secrets/) are masked in it.

# Workspaces

> What a workspace gives a task (the image, repositories, agent and tools), how to pick one, and who defines them.

A workspace is the recipe for a task’s sandbox. When you create a task you pick one, and it decides everything the agent starts with: * **The image** the sandbox runs, with the agent’s CLI and the tools the work needs. * **Setup commands**, such as cloning the repositories the task works on. They run once, before the task’s first run. * **The agent**: Claude Code, Codex, Cursor or Copilot, its model, the directory it starts in, and any standing instructions for that repository. * **MCP servers** the agent can use, in addition to the [gritz tools](/pr/2460/using/agent-tools/) every agent gets. * **Credentials**, such as a GitHub or model provider token, passed in as secrets. A workspace can also declare **features**, optional extras such as an MCP server and its token, or a different agent. The task’s [agent](/pr/2460/concepts/agents/#the-template) decides which of them it gets. ## Picking a workspace [Section titled “Picking a workspace”](#picking-a-workspace) Workspaces belong to [runners](/pr/2460/concepts/runners/): each runner offers its own set, by name and with a short description. **Workspaces** in the [Web UI](/pr/2460/using/web-ui/#workspaces) lists them all, and the new task form shows the workspaces of the runner you pick. Two runners can offer a workspace with the same name and a different setup. Pick the workspace for the repository or system the task is about. A task keeps its workspace for its whole life; to run the same work in another workspace, create another task. ## Who defines them [Section titled “Who defines them”](#who-defines-them) Workspaces aren’t created in the Web UI. The operator of each runner defines its workspaces in a `workspaces.yaml` file, and the runner registers their names and descriptions with the server when it starts. To add a workspace or change one, ask whoever runs the runner, or see [`workspaces.yaml`](/pr/2460/operators/workspaces-yaml/) if that is you. A change to a workspace applies to tasks created after the runner restarts with it; existing tasks keep the setup they started with. See [Changing a workspace](/pr/2460/operators/workspaces-yaml/#changing-a-workspace).

# Getting started

> Sign in to gritz, pick an organisation, create a task in the Web UI, watch it run, send a follow-up instruction and archive it.

This page walks through a first task on a gritz deployment such as [gritz.dev](https://gritz.dev). It assumes a runner is already connected to your organisation. If none is, ask whoever runs gritz for you, or set one up yourself with [Runner](/pr/2460/operators/runner/). ## 1. Sign in [Section titled “1. Sign in”](#1-sign-in) Open the deployment, for example `https://gritz.dev`, and sign in. The first time you sign in, gritz creates your user and a personal organisation named after you, such as “Ada Lovelace’s Org”. ## 2. Pick an organisation [Section titled “2. Pick an organisation”](#2-pick-an-organisation) Everything in gritz (tasks, agents, runners, keys) belongs to an [organisation](/pr/2460/concepts/orgs-members-keys/). The selector at the top right of the Web UI switches between the organisations you are a member of, and the current one is kept in the page’s `?org=` parameter, so links you share open in the right one. To work in a team’s organisation, ask its owner to add you on the **Members** page. They add you by email, so sign in once first. ## 3. Check for a runner [Section titled “3. Check for a runner”](#3-check-for-a-runner) Open **Workspaces**. It lists every [workspace](/pr/2460/concepts/workspaces/) the organisation’s [runners](/pr/2460/concepts/runners/) offer, with the runner that offers it. If the list is empty, no runner has connected to this organisation yet. ## 4. Create an agent [Section titled “4. Create an agent”](#4-create-an-agent) Every task belongs to an [agent](/pr/2460/concepts/agents/): the organisation’s template for a kind of task. Open **Agents** and click **+ Agent**: * **Name** it, for example `pets-workshop`. * **Runner** and **Workspace** decide where its tasks run and what they get: the image, repositories, coding agent and tools. Pick a runner first; the workspace list shows only that runner’s workspaces. * **Auto-archive** archives each task some time after it finishes. Leave it on **Never** for now. Leave the prompt, **Follows** and **Starts on** empty: they are for tasks created from events and schedules. Click **Create agent** at the bottom of the page. ## 5. Create a task [Section titled “5. Create a task”](#5-create-a-task) Open **Tasks** and click **+ Task**. The new task’s page opens: * **Agent**, in the middle of the page, is the agent you just created. The task runs with its runner, workspace, auto-archive delay and variables. * **Name**, at the top of the sidebar, is optional. The agent names the task itself if you leave it blank. Type what you want the agent to do in the box at the bottom of the page and press Enter (Shift+Enter adds a new line): > Add a `--json` flag to the `list` command and open a pull request. Sending the first instruction creates the task. It moves to **pending** while the runner prepares its sandbox, then to **running** when the agent starts. ## 6. Watch it run [Section titled “6. Watch it run”](#6-watch-it-run) The task page has three views, in the sidebar on the left: * **Timeline**: your instructions, the agent’s reports, the links it creates (such as the pull request it opened), events from GitHub, Jira and other systems, and status changes, in order. * **Logs**: the sandbox’s log as it runs: setup commands, the agent’s messages and tool calls. * **Shell**: a terminal in the task’s sandbox, once the task has finished. When the agent is done, the task moves to **completed**, or to **failed** if a setup command, the agent or the sandbox failed. The [task lifecycle](/pr/2460/concepts/tasks/#statuses) lists every status. ## 7. Follow up [Section titled “7. Follow up”](#7-follow-up) Send another instruction from the same box: “Also update the README”. A finished task starts again, in the same sandbox, and the agent continues the same session, so it remembers what it did. If the task is still running, the instruction waits and the task runs again as soon as the current run ends. Tasks can also come back by themselves. Give the agent a [link kind](/pr/2460/concepts/agents/#link-kinds) for pull requests that lists review comments, and when it opens a pull request it links it to the task with that kind: a review comment on the pull request then wakes the task up. See [Events and links](/pr/2460/concepts/events-and-links/). ## 8. Archive it [Section titled “8. Archive it”](#8-archive-it) When you are done with the task, click **Archive** in the sidebar. The runner destroys the task’s sandbox and the task leaves the task list; turn on **Show archived** to see it again. A task can only be archived once it has finished. ## Next steps [Section titled “Next steps”](#next-steps) * [Tasks](/pr/2460/concepts/tasks/) covers statuses, restarts, cancelling and auto-archive. * [Agents](/pr/2460/concepts/agents/) create and wake tasks from [GitHub](/pr/2460/integrations/github/), [Jira](/pr/2460/integrations/jira/) and [custom events](/pr/2460/integrations/custom-events/). * [Schedules](/pr/2460/concepts/schedules/) create tasks on a cron schedule. * [The CLI](/pr/2460/using/cli/) creates and follows tasks from a terminal, and [MCP](/pr/2460/integrations/mcp/) lets Claude Code or Cursor do it for you.

# Custom events

> Send events from any system, such as an alerting tool or a deploy pipeline, to gritz so they create or wake up tasks.

GitHub and Jira events reach gritz through their own integrations. Any other system can send events too: you define a custom event type, and the system `POST`s events of that type to the custom events webhook with an API key. [Agents](/pr/2460/concepts/agents/) then decide what each event does, as they do for built-in events: create a task, wake a task that’s already working on the same resource, or both. This page uses an alerting system as its example. It posts an `alert` event when an alert fires, and gritz creates a task to investigate it. ## 1. Define a custom event type [Section titled “1. Define a custom event type”](#1-define-a-custom-event-type) Open **Events → Custom types** and add a type with **+ Type**: * **Type**: the name senders put in the envelope’s `type` field, for example `alert`. It must start with a lowercase letter, followed by up to 63 lowercase letters, digits and underscores (`^[a-z][a-z0-9_]{0,63}$`). It must be unique among your organisation’s custom types, and it can’t be renamed later: remove the type and add a new one instead. * **Label**: shown in the trigger editor and on the task’s timeline, for example `Alert`. It can’t be empty. * **Attributes**: the values triggers can match on. Every type has `body` and `url`; the form adds both and doesn’t let you remove them. Add one row per extra attribute, with a key that follows the same rules as the type name. The example declares `severity` and `service`. An attribute’s label, help and placeholder are only for display, in the trigger editor and the JSON Schema. A type’s events can also wake tasks subscribed to their `url` when the type declares the `custom.url` [link type](/pr/2460/reference/event-types/#link-types). The Web UI’s form doesn’t set it: declare it with the [`put_custom_event_type`](/pr/2460/integrations/mcp/#put_custom_event_type) MCP tool’s `link_types`. A type without it can only create tasks. The **JSON Schema** button on a type’s page shows the request body the webhook accepts for it. ## 2. Create an API key [Section titled “2. Create an API key”](#2-create-an-api-key) Senders authenticate with an API key. Create one with **+ Key** on the **Keys** page (`https://gritz.dev/ui/keys`) and copy the token: it starts with `xat_` and is shown only once. The key belongs to the organisation you create it in, and so does every event sent with it. Store the key as a secret in the sending system and send it as a bearer token: 
```plaintext
Authorization: Bearer xat_…
```
 The webhook URL is on **Settings → Organisation**, in the **Custom events** section. For gritz.dev it is `https://gritz.dev/webhook/custom`. ## 3. Send an event [Section titled “3. Send an event”](#3-send-an-event) `POST` a JSON envelope to the webhook URL: 
```bash
curl https://gritz.dev/webhook/custom \
  -H "Authorization: Bearer $GRITZ_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "alert",
    "url": "https://alerts.example.com/alerts/4211",
    "body": "checkout-api error rate above 5% for 10 minutes",
    "attrs": {"severity": ["critical"], "service": ["checkout-api"]},
    "details": {"runbook": "https://wiki.example.com/runbooks/checkout-api"}
  }'
```
 The command reads the key from a variable, so it can be shared or logged without the key’s value. * `type` names the custom type. * `description`, optional, is shown on the task’s timeline. It defaults to the type’s label. * `url` identifies the resource the event is about; see [The URL is the subscription key](#the-url-is-the-subscription-key). * `body` is the event’s text. The agent reads it, and triggers can match on it. * `attrs` holds the values of the type’s other attributes. Each value is a list of strings, even when there is only one. * `details` holds extra key/value context that is shown with the event but that triggers can’t match on. Unknown fields are rejected. The [envelope reference](/pr/2460/reference/custom-event-envelope/) lists every field and its validation. A valid event gets a `200` response with the number of tasks it created or was delivered to: 
```json
{"routed": 1}
```
 `{"routed": 0}` is still a success: the event was valid, but nothing acted on it (see [Troubleshooting](#troubleshooting)). The `test_event` [MCP tool](/pr/2460/integrations/mcp/#test_event) with `fire` set sends the same event with the sign-in or API key the MCP client already uses. It is checked the same way, and routes the same way. ## 4. Add an agent [Section titled “4. Add an agent”](#4-add-an-agent) An event does nothing until an agent acts on it. This step assumes the `alert` type declares the `custom.url` link type, as in step 1; without it, leave out the link kind and the trigger’s link and yield, and every alert creates a task. Open **Agents** and add an agent with **+ Agent**, with a runner, a workspace, and a prompt such as “Investigate this alert and report the likely cause.” Then: * **Link kinds**: add one with the link type **Custom: URL** and the claim `alert-owner`. Check `Alert` in its events, with no conditions, and turn on its **Wake** and **Public**. * **Triggers**: add one with: * **Event type**: the type’s label, here `Alert`. * **Conditions**: `severity` `equals` `critical`. A condition matches when any of the attribute’s values satisfies it, and the trigger matches when every condition does. * **Link**: `custom.url`, the link kind above. * **Yield to claims**: `alert-owner`. * **Public**: on. Custom event triggers must be public; see below. The task the trigger creates is subscribed to the event’s `url`. The next event with the same `url` wakes that task, and the trigger yields to it instead of creating another one. ### Why custom event triggers must be public [Section titled “Why custom event triggers must be public”](#why-custom-event-triggers-must-be-public) A trigger or a link kind’s event type that isn’t public only acts on events whose actor is a member of the organisation, such as a GitHub comment by a member. A custom event has no actor: it belongs to the API key’s organisation, and only that organisation’s public triggers and link kinds’ public event types are considered for it. A member-only trigger for a custom type could never fire, so gritz rejects it when you save the agent. A link kind never delivers a custom event type it doesn’t mark public. ### Follow-up events [Section titled “Follow-up events”](#follow-up-events) The trigger above only matches critical alerts, but the link kind delivers every `alert` event about the alert, whatever its severity. So when the alerting system later posts a `resolved` event for the same alert, it wakes the task. An event for an alert gritz never saw fire has no subscribed task, and matches no trigger, so it does nothing. ## The URL is the subscription key [Section titled “The URL is the subscription key”](#the-url-is-the-subscription-key) gritz decides which task an event belongs to by its `url`: an event of a type that declares `custom.url` wakes the tasks subscribed to that URL with a `custom.url` link kind. A task is subscribed to the `url` of the event that created it when its trigger has a link, and to any link its agent creates with a `custom.url` kind. gritz uses the URL exactly as sent, so every event about the same resource must send the same URL, byte for byte. A different query string, a trailing slash or a different host name is a different resource, and the event won’t wake the task the first event created. This holds for GitHub and Jira URLs too: a custom event never reaches a task’s GitHub or Jira links. Pick a URL that a person can open, such as the alert’s page in the alerting system, and send exactly that string in every event about the alert. ## Troubleshooting [Section titled “Troubleshooting”](#troubleshooting) | Status | Response body | Cause | | ------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `400` | `invalid envelope: …` | The body isn’t valid JSON, has a field the envelope doesn’t define, has a field of the wrong type (for example an attr value that is a string rather than a list), or is larger than 1 MiB. | | `400` | `unknown event type "…"` | `type` is empty or doesn’t name one of the organisation’s custom types. Check **Events → Custom types**. | | `400` | `url is required` | `url` is missing or empty. | | `400` | `url "…" must be an absolute http or https URL` | `url` is relative, has no host, or uses another scheme. | | `400` | `attr "body" must be sent as the envelope's "body" field` | `body` or `url` was sent inside `attrs`. Send it as the top-level field. | | `400` | `attr "…" not declared by event type "…"` | `attrs` has a key the type doesn’t declare. Add the attribute to the type, or drop it from the envelope. | | `401` | `bearer token required` | No `Authorization: Bearer …` header. A browser session cookie isn’t accepted. | | `401` | `invalid or expired token` | The key is wrong, deleted or expired. | | `403` | `permission denied` | The token can’t create events, for example a task’s own token. Use an API key. | | `200` | `{"routed": 0}` | No public trigger for the type matched the event, or the matching triggers yielded, and no task is subscribed to the `url` with a link kind that delivers the type and marks it public. |

# GitHub

> Install the gritz GitHub App, link your GitHub account, and route pull request, issue, push and CI events to tasks; the events gritz receives, the reactions it posts, and GitHub credentials for agents.

The GitHub integration turns activity on GitHub into [events](/pr/2460/concepts/events-and-links/): comments, reviews, assignments, labels, pull requests being opened or closed, pushes, and CI results. [Agents](/pr/2460/concepts/agents/) then decide what each event does: wake the task that opened the pull request, create a new task for an issue, or nothing. It has two halves: * **The GitHub App**, installed on your repositories, is how GitHub sends gritz events. An organisation links the installation on **Settings → Organisation**. * **Your GitHub account**, linked on **Settings → Account**, tells gritz which events are yours, so your organisation’s member-only triggers and link kinds act on them. Both need the server’s GitHub App to be configured. On a server where it isn’t, **Settings → Organisation** has no **GitHub App** section; operators, see [GitHub App](/pr/2460/operators/server/#github-app). ## Link your GitHub account [Section titled “Link your GitHub account”](#link-your-github-account) On **Settings → Account**, under **Connected accounts**, click **Link** on the **GitHub** row and approve the request on GitHub. gritz only asks to read your profile; it records your GitHub user ID and username. Once linked, events you cause on GitHub, such as your comments, reviews and assignments, count as yours in every organisation you are a member of. **Unlink** removes the link; your events then count as an outsider’s. Link your account before installing the App: linking an installation checks your GitHub identity. ## Install the GitHub App [Section titled “Install the GitHub App”](#install-the-github-app) On **Settings → Organisation**, the **GitHub App** section shows whether the organisation has an installation. **Install** opens the App’s page on GitHub. Pick the account or organisation and the repositories it may see. When GitHub sends you back to gritz, the **Link GitHub App** page shows who you are signed in as and the gritz organisation the installation will be linked to; **Approve** links it. If the App is already installed on your GitHub organisation, for example by a colleague for another gritz organisation, use **Link existing** instead and enter the installation’s ID. It is the number at the end of the installation’s settings URL on GitHub, `github.com/settings/installations/<id>` (for an organisation, `github.com/organizations/<org>/settings/installations/<id>`). gritz links an installation only if your linked GitHub account may use it: * for an installation on a GitHub organisation, you must be an active member of that organisation; * for an installation on a personal account, it must be your account. Several gritz organisations can link the same installation. Once linked, the section shows **Installed** and a **Manage** button that opens the installation’s settings on GitHub, where you change its repositories or uninstall it. Uninstalling the App on GitHub unlinks it from every gritz organisation. ## Which events reach your organisation [Section titled “Which events reach your organisation”](#which-events-reach-your-organisation) GitHub sends gritz an event for every repository where the App is installed. gritz then works out which organisations it concerns: * **Your members’ events.** If the person who caused the event has linked their GitHub account, the event goes to every organisation they are a member of. It doesn’t matter which organisation linked the installation. * **Everyone’s events on your repositories.** An event from a repository whose installation your organisation linked also goes to your organisation, whoever caused it. Only [public](/pr/2460/concepts/agents/#members-and-public) triggers and link kinds act on events from people who aren’t members. Each organisation’s own agents then decide what to do with it, as described in [Agents](/pr/2460/concepts/agents/). An organisation with no trigger or link kind for a GitHub event type ignores it. ## Events [Section titled “Events”](#events) gritz turns these GitHub webhook deliveries into events. The trigger form’s **Event type** list names them as in the second column. | GitHub delivery | Event type | Its URL | | --------------------------------------------------------------- | ------------------------------ | ------------------------------------------ | | A comment on an issue is created or edited | GitHub: Issue Comment | the comment | | A comment on a pull request’s conversation is created or edited | GitHub: PR Comment | the comment | | An inline review comment on a pull request is created or edited | GitHub: PR Review Comment | the review comment | | A pull request review is submitted with a summary | GitHub: PR Review | the review | | An issue is assigned | GitHub: Issue Assigned | the issue | | A pull request is assigned | GitHub: PR Assigned | the pull request | | A pull request is opened | GitHub: PR Opened | the pull request | | A pull request is closed or merged | GitHub: PR Closed | the pull request | | A label is added to an issue | GitHub: Issue Label Added | the issue | | A label is added to a pull request | GitHub: PR Label Added | the pull request | | Commits are pushed to a branch | GitHub: Push | the newest commit | | A check run completes | GitHub: Check Run Completed | the check run; for GitHub Actions, the job | | A check run of an open pull request completes | GitHub: PR Check Run Completed | the pull request | Every other delivery is ignored, including pushing a tag and deleting a branch. Editing a comment sends the event again, with the new text. A review submitted without a summary, such as a bare approval, is ignored, but its inline comments are still sent as review comments. GitHub sends one delivery per label, so adding two labels sends two events. A check run is one check reported through GitHub’s Checks API: for GitHub Actions, one job; other CI systems report theirs the same way. Every completed check sends GitHub: Check Run Completed, whatever its conclusion, so a trigger filters with `conclusion`. A check of a pull request also sends GitHub: PR Check Run Completed, once for each open pull request in the repository whose head is the checked commit, so it reaches the task subscribed to that pull request. A pull request opened from a fork gets no PR Check Run Completed event, and the fork’s checks carry no `branch`. A comment’s or review’s URL points at the comment itself, but gritz matches it to the issue or pull request it belongs to. So a task with a [subscribed link](/pr/2460/concepts/events-and-links/#subscriptions) to a pull request gets every comment, review and review comment on it that the link’s kind lists. Likewise, every job of a GitHub Actions workflow run, and of its re-runs, matches the workflow run. The [link types](/pr/2460/reference/event-types/#link-types) list which event types each kind of resource can receive. The attributes each type offers for conditions, such as `mention`, `user`, `label`, `branch`, `path` or `conclusion`, are listed in [Event types](/pr/2460/reference/event-types/#github). ### Pushes and agents [Section titled “Pushes and agents”](#pushes-and-agents) Agents push too, and their pushes are events like anyone else’s, from the GitHub user whose [credentials](#github-credentials-for-agents) the workspace gives them. A push trigger can therefore feed itself: the task it creates pushes a branch, and that push creates another task. Give every push trigger a `branch` condition, such as `branch equals master`, that the branches agents push don’t match. ### What the agent sees [Section titled “What the agent sees”](#what-the-agent-sees) Each event on a task’s timeline has a description, such as `octocat commented on PR #42`, its URL, and its text: the comment, review or review comment body, or the issue’s or pull request’s description for the other types. A review comment also carries where it was left: the file, the line (or the range from `start_line`), the side of the diff, and the diff hunk it is anchored to. A push has `octocat pushed 3 commits to master`, the newest commit’s message, and the repository, the branch, the commit SHAs before and after the push, the compare URL, whether it was a force push and the number of commits, so the agent can diff the push itself. A check run has `check "test" failed on master (abc1234)` (or `on PR #42`), the check’s output if the CI system reported any, and the repository, the branch, the check’s name and conclusion, the app that reported it, the commit SHA, and links to the check run and its details page, so the agent can open the failing job’s log. The agent gets all of it at the start of its next run, and through [`get_my_task`](/pr/2460/using/agent-tools/#get_my_task). ## Reactions [Section titled “Reactions”](#reactions) When a GitHub event acts on your organisation, gritz reacts to what caused it, as the GitHub App: * 🚀 when a trigger created a task for it; * 👀 when it woke one or more subscribed tasks. The reaction goes on the comment, the review, or the issue or pull request for the other event types; a push or a check run gets none. An event that neither created nor woke a task gets no reaction, including one whose trigger yielded. Reactions need the organisation to have linked an installation. A reaction is the quickest way to tell that a comment such as `gritz: fix the failing test` was picked up. ## Examples [Section titled “Examples”](#examples) Wake the task that opened a pull request whenever a member comments on it or reviews it. Give the agent a link kind: * **Link type**: GitHub: Pull Request * **Events**: GitHub: PR Comment, GitHub: PR Review, GitHub: PR Review Comment The agent links the pull requests its tasks open with that kind, `github.pr`. Start a task for every issue a member labels `gritz`, in one repository, and keep it up to date with the issue’s comments: * **Link kind**: link type GitHub: Issue, events GitHub: Issue Comment. * **Trigger**: event type GitHub: Issue Label Added, conditions `label equals gritz` and `url prefix https://github.com/example/app/issues/`, link `github.issue`. * **Prompt**: “Fix the issue and open a pull request.” To stop labelling the issue again from starting a second task, give the link kind a claim, such as `issue-owner`, and have the trigger yield to it. Start a task whenever a push to `master` changes a database migration: * **Trigger**: event type GitHub: Push, conditions `repo equals example/app`, `branch equals master` and `path glob internal/store/sql/migrations/**`. * **Prompt**: “A migration changed; check that it is safe to run on a live database.” Wake the task that opened a pull request when one of the pull request’s checks fails. Give its pull request link kind the event GitHub: PR Check Run Completed with the condition `conclusion glob {failure,timed_out,startup_failure}`, and turn on its **Public**, so the checks of pushes by agents and bots count too. Without the condition, every completed check is delivered, successes included. Start one task when a workflow run fails on `master`: * **Link kind**: link type GitHub: Workflow Run, claim `ci-fixer`, events GitHub: Check Run Completed. * **Trigger**: event type GitHub: Check Run Completed, conditions `conclusion glob {failure,timed_out,startup_failure}`, `repo equals example/app` and `branch equals master`, **Public** on, link `github.workflow_run`, yield to `ci-fixer`. * **Prompt**: “CI failed on master. Find the cause and propose a fix.” The first failing job creates the task and links it to the workflow run. The run’s other jobs, failing or not, then reach that task instead of creating another. Let anyone, members or not, ask for a change on a pull request a task opened by starting a comment with `gritz:`: turn on **Public** for the comment event types of the pull request link kind. Its tasks then also get every comment from non-members, so tell the agent in the prompt to act only on those that start with `gritz:`. ## GitHub credentials for agents [Section titled “GitHub credentials for agents”](#github-credentials-for-agents) The App’s installation is for events and reactions. What an agent can do on GitHub, such as cloning, pushing and opening pull requests, depends on the credentials its [workspace](/pr/2460/concepts/workspaces/) gives it. Operators put a token under the workspace’s `secrets:` and reference it by variable; see [`secrets`](/pr/2460/operators/secrets/). A workspace can also ask for GitHub App installation tokens with the `github_token` [capability](/pr/2460/operators/workspaces-yaml/#capabilities), which gives the agent the [`get_github_token`](/pr/2460/using/agent-tools/#get_github_token) tool. The server doesn’t issue these tokens yet: the request fails with `unimplemented`, and so do the `gritz tool git-credential` and `gritz tool github-mcp` helpers built on it. Use a token in the workspace’s secrets until it does.

# Jira

> Connect Jira to gritz with the organisation's Atlassian webhook URL and secret, link your Atlassian account, and route Jira comments, new issues, labels and assignments to tasks.

The Jira integration turns activity on Jira Cloud issues into [events](/pr/2460/concepts/events-and-links/): new comments, new issues, added labels and new assignees. [Agents](/pr/2460/concepts/agents/) then decide what each event does: wake the task working on the issue, create a new task for it, or nothing. It has two halves: * **A Jira webhook**, pointed at your organisation’s Atlassian webhook URL, is how Jira sends gritz events. It is set up once per gritz organisation. * **Your Atlassian account**, linked on **Settings → Account**, tells gritz which events are yours, so your organisation’s member-only triggers and link kinds act on them. The server must have the Atlassian integration configured; operators, see [Atlassian](/pr/2460/operators/server/#atlassian). ## Link your Atlassian account [Section titled “Link your Atlassian account”](#link-your-atlassian-account) On **Settings → Account**, under **Connected accounts**, click **Link** on the **Atlassian** row and approve the request on Atlassian. gritz only asks to read your profile; it records your Atlassian account ID and name. Once linked, your comments, labels and assignments on Jira count as yours in every organisation you are a member of. **Unlink** removes the link. ## Connect Jira [Section titled “Connect Jira”](#connect-jira) ### 1. Generate the webhook secret [Section titled “1. Generate the webhook secret”](#1-generate-the-webhook-secret) On **Settings → Organisation**, the **Atlassian webhook** section shows the organisation’s webhook URL: 
```plaintext
https://gritz.dev/webhook/atlassian?org=<org-id>
```
 Click **Generate secret**. gritz rejects every Jira event for the organisation until it has a secret. **Regenerate secret** replaces it; the old one stops working at once, so update the webhook in Jira straight after. ### 2. Create the webhook in Jira [Section titled “2. Create the webhook in Jira”](#2-create-the-webhook-in-jira) As a Jira administrator, open **Settings → System → WebHooks** and create a webhook: * **URL**: the webhook URL from that section, including `?org=`. * **Secret**: the secret from that section. * **Events**: under **Comment**, **created**; under **Issue**, **created** and **updated**. Add a JQL filter if you only want some projects’ issues. A webhook’s JQL filter applies to every event it sends. To narrow one event without narrowing the others, such as only the new issues in one project, create a second webhook with the same URL and secret, only that event, and its own JQL filter. Jira signs each delivery with the secret, and gritz checks the signature before it reads the event, so a delivery with a missing or wrong signature is refused with `403`. The URL names one gritz organisation. To send the same Jira site’s events to two organisations, create a webhook for each. ## Which events reach your organisation [Section titled “Which events reach your organisation”](#which-events-reach-your-organisation) Every event sent to your organisation’s webhook belongs to your organisation, whoever caused it: * If the person who caused it has linked their Atlassian account and is a member, your organisation’s member-only triggers and link kinds can act on it. It also goes to the other organisations they are a member of. * Otherwise, only your [public](/pr/2460/concepts/agents/#members-and-public) triggers, and link kinds that mark its event type public, act on it. ## Events [Section titled “Events”](#events) | Jira webhook | Event type | Its URL | | ---------------------------------- | -------------------- | ---------------------------------------------------------- | | Comment created | Jira: Issue Comment | the comment, as `…/browse/PROJ-123?focusedCommentId=10001` | | Issue created | Jira: Issue Created | the issue, as `…/browse/PROJ-123` | | Issue updated, with labels added | Jira: Label Added | the issue | | Issue updated, with a new assignee | Jira: Issue Assigned | the issue | Labels and an assignee set when an issue is created arrive on Issue Created, in its `label` and `assignee` attributes, not as Label Added or Issue Assigned. Other updates, such as a status change or an edited description, are ignored. One update can send two events: assigning an issue and adding a label in the same edit sends both. Adding several labels at once sends one Label Added event with all of them, and a `label` condition holds if any of them matches. Unassigning an issue sends nothing. A comment’s URL points at the comment, but gritz matches it to its issue. So a task with a [subscribed link](/pr/2460/concepts/events-and-links/#subscriptions) to `https://your-domain.atlassian.net/browse/PROJ-123`, of a kind that lists Jira: Issue Comment, gets every comment on `PROJ-123`. Jira identifies people by account ID rather than by name, and so do the `user`, `mention` and `assignee` attributes. Enter the bare ID, such as `5b10ac8d82e05b22cc7d4ef5`, not the `[~accountid:…]` form Jira uses in comment text. The account ID is at the end of the URL of the person’s Jira profile. See [Event types](/pr/2460/reference/event-types/#jira) for every attribute. Each event on a task’s timeline has a description, such as `Ada Lovelace commented on PROJ-123`, its URL and its text: the comment’s text, or the issue’s description for the other events. gritz doesn’t post anything back to Jira. ## Examples [Section titled “Examples”](#examples) Wake the task working on an issue whenever a member comments on it. Give the agent a link kind: * **Link type**: Jira: Issue * **Events**: Jira: Issue Comment Start a task for every issue in one project that is labelled `gritz`, and keep it up to date with the issue’s comments: * **Link kind**: link type Jira: Issue, claim `issue-owner`, events Jira: Issue Comment. * **Trigger**: event type Jira: Label Added, conditions `label equals gritz` and `url prefix https://your-domain.atlassian.net/browse/PROJ-`, link `jira.issue`, yield to `issue-owner`, so labelling the issue again doesn’t start a second task. * **Prompt**: “Implement the issue and open a pull request.” Start a task when an issue is assigned to a bot account, whoever assigns it: * **Trigger**: event type Jira: Issue Assigned, condition `assignee equals <the bot's account ID>`, **Public** on. Start a task for every issue an integration, such as a security scanner, files in one project: * **Trigger**: event type Jira: Issue Created, conditions `user equals <the integration's account ID>` and `url prefix https://your-domain.atlassian.net/browse/SEC-`, **Public** on, since the integration’s account isn’t linked to a member. The agent needs its own Jira credentials, from its [workspace](/pr/2460/concepts/workspaces/), to read the issue or reply to it.

# MCP

> Connect Claude Code, Cursor or any MCP client to gritz, over HTTP with OAuth or locally with gritz mcp, to create and manage tasks and administer the organisation; the tools it offers, and task notifications through Claude Code channels.

gritz is an MCP server, so the agent you work with locally, such as Claude Code or Cursor, can hand work off to gritz: list the workspaces, create tasks, follow them up with instructions, read what they did, and archive them. It can also manage the organisation’s agents and their schedules, events and custom event types, and read its members, API keys and settings. There are two ways to connect: * **Over HTTP, to `/mcp` on the server.** Nothing to install; you sign in with your browser. Use this unless you need channels. * **Locally, with `gritz mcp`.** Your client runs the `gritz` binary, which talks to the server with the CLI’s login. It is also the only way to get [channels](#channels): task updates pushed into a Claude Code session. Both offer the same [tools](#tools). Over HTTP the client acts in one organisation; `gritz mcp` can [switch](#organisations) between the organisations you’ve logged in to. This page is about the tools *you* use to drive gritz. The tools gritz gives the agents running inside tasks are in [Agent tools](/pr/2460/using/agent-tools/). ## Connect over HTTP [Section titled “Connect over HTTP”](#connect-over-http) The server’s MCP URL is on **Settings → Organisation**, in the **MCP server** section: `https://gritz.dev/mcp` for gritz.dev. It uses the Streamable HTTP transport. ### Claude Code [Section titled “Claude Code”](#claude-code) 
```bash
claude mcp add --transport http gritz https://gritz.dev/mcp
```
 Then run `/mcp` in Claude Code, pick `gritz` and authenticate. ### Cursor [Section titled “Cursor”](#cursor) Add the server to `~/.cursor/mcp.json`, or to `.cursor/mcp.json` in a project: 
```json
{
  "mcpServers": {
    "gritz": {
      "url": "https://gritz.dev/mcp"
    }
  }
}
```
 ### Other clients [Section titled “Other clients”](#other-clients) Give the client the URL. gritz supports the MCP authorization flow: OAuth 2.1 with PKCE and dynamic client registration, so a client that supports it registers itself and needs no client ID. ### Signing in [Section titled “Signing in”](#signing-in) When the client first connects, it opens gritz in your browser. Sign in if you aren’t already, check the organisation in the selector at the top, and click **Approve** on the **Authorize application** page. The page shows the account and organisation the client will act as. The client then acts as you, in that organisation: it sees and changes what you can there. To use another organisation, switch to it in the Web UI, and sign the client in again. The client keeps its access by refreshing its token. It loses it if it isn’t used for 30 days, if you leave the organisation, or if the organisation is deleted; sign in again then. ### With an API key [Section titled “With an API key”](#with-an-api-key) `/mcp` also accepts an [API key](/pr/2460/concepts/orgs-members-keys/#api-keys) as a bearer token, for clients that can’t do OAuth or that run unattended. Most clients take a header in their config, for example: 
```bash
claude mcp add --transport http gritz https://gritz.dev/mcp \
  --header "Authorization: Bearer ${GRITZ_API_KEY}"
```
 The client then acts with the key: in the key’s organisation, and recorded under the key’s name. ## Connect with `gritz mcp` [Section titled “Connect with gritz mcp”](#connect-with-gritz-mcp) `gritz mcp` is a local MCP server over stdio. Your client starts it, and it forwards each tool call to the server’s API with the CLI’s login. Install the [CLI](/pr/2460/using/cli/) and [log in](/pr/2460/using/cli/#configuration), then add it to your client. For Claude Code: 
```bash
claude mcp add gritz -- gritz mcp
```
 Or in a project’s `.mcp.json`: 
```json
{
  "mcpServers": {
    "gritz": {
      "command": "gritz",
      "args": ["mcp", "--channel"]
    }
  }
}
```
 `gritz mcp` picks its organisation, login and server as every CLI command does, from the `.gritz.yml` files of the directory the client starts it in: a repository whose `.gritz.yml` sets `org` gets that organisation with no credential in the MCP config. | Flag | | | ---------------- | ------------------------------------------------------------------------------------------------------------------------------ | | `--org` | The organisation, by its name in the `.gritz.yml` files. Defaults to `GRITZ_ORG`, otherwise their `org`. | | `--key`, `-k` | An API key to use instead of the `.gritz.yml` files. Defaults to `GRITZ_API_KEY`. The session stays in the key’s organisation. | | `--server`, `-s` | The server URL to use with `--key`, which it requires. Defaults to `GRITZ_SERVER`, otherwise `https://gritz.dev`. | | `--channel` | Push task updates into the Claude Code session. See [Channels](#channels). | ### Organisations [Section titled “Organisations”](#organisations) A session started from the `.gritz.yml` files starts in the organisation `--org` picks, and can switch to any other entry in those files, within their `allowed` list. A session started with `--key` has one entry, with an empty name, for the key’s organisation. A session acts in one organisation at a time, the current one, and every other tool acts in it. Two tools manage it: * `list_orgs` lists the entries: each one’s `name`, organisation `id`, `server`, and whether it is `current`. It doesn’t contact the server. * `switch_org` takes an entry’s `name` and makes it current. It returns the entry’s `name`, `id` and `server`. It doesn’t contact the server either: if the entry’s login doesn’t work, the first tool call after the switch fails. The entries are those in the files when `gritz mcp` started; restart it to pick up a `gritz login` made since. ## Tools [Section titled “Tools”](#tools) | Tool | | | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | | `list_orgs` | Lists the organisations a `gritz mcp` session can switch to, and marks the current one. With `--channel`, `gritz mcp` pushes the task updates of every organisation the session has been in, so your Claude hears about a task finishing without polling: 
```plaintext
<channel source="gritz" org="acme">Task 1234 created on my-runner/pets-workshop.</channel>
<channel source="gritz" org="acme">Task 1234 woken by event 567: octocat commented on PR #42 (https://github.com/…)</channel>
<channel source="gritz" org="acme">Task 1234 completed.</channel>
```
 The `org` attribute is the name of the `.gritz.yml` entry of the task’s organisation; a session started with `--key` sends `org=""`. It sends a message when a task is created (by anyone, by an agent’s trigger or by a schedule), when one is queued with new instructions, woken from a finished state by an event, completed, failed, cancelled, restarted or archived, and when a shell is opened in one. It leaves out the changes made through the same `gritz mcp` process, so your Claude isn’t told about the task it just created. It also tells your Claude when an organisation’s notification stream goes down and comes back, since it misses updates in between: 
```plaintext
<channel source="gritz" org="acme">Lost the connection: unexpected status: 502, retrying.</channel>
<channel source="gritz" org="acme">Reconnected (notifications sent while it was down were missed).</channel>
```
 A stream that can’t connect in the first place is reported as lost too. `gritz mcp` keeps retrying until it connects, and sends nothing more until the stream comes back. Channels are a Claude Code research preview, and only work over stdio, so only with `gritz mcp`. gritz isn’t on the preview’s allowlist, so start Claude Code with: 
```bash
claude --dangerously-load-development-channels server:gritz
```

After `channel_mute` with `all=true`, unmuting some tasks keeps just those on. | | `channel_muted` | Shows which tasks are muted. | Each tool takes `org`, the `org` attribute of the messages to mute, and names it in its result; in a session started with `--key` it is empty and can be left out. Muting lasts until `gritz mcp` exits. It is separate from [subscribed links](/pr/2460/concepts/events-and-links/#subscriptions), which route external events into tasks.

# API

> Call the gritz Connect API directly, with its endpoint, protocols and authentication, and the full service definition.

Everything gritz does, from the [Web UI](/pr/2460/using/web-ui/) to the [CLI](/pr/2460/using/cli/) and the runners, goes through one service, `gritz.v1.GritzService`. A program with an [API key](#authentication) can call it too. Its full definition is [at the end of this page](#service-definition). ## Endpoint [Section titled “Endpoint”](#endpoint) Every RPC is a `POST` to its own path on the server: 
```plaintext
POST https://gritz.dev/gritz.v1.GritzService/<Method>
```
 On a self-hosted server, replace `https://gritz.dev` with its base URL. ## Protocols [Section titled “Protocols”](#protocols) The server speaks the [Connect](https://connectrpc.com/docs/protocol/) protocol, gRPC and gRPC-Web, so any Connect or gRPC client generated from the service definition can call it. With Connect, a request body is the request message as JSON (`Content-Type: application/json`) or binary protobuf (`Content-Type: application/proto`). JSON field names are the camelCase form of the proto field names: `page_size` is `pageSize`. ## Authentication [Section titled “Authentication”](#authentication) Send an [API key](/pr/2460/concepts/orgs-members-keys/#api-keys) as a bearer token: 
```plaintext
Authorization: Bearer xat_…
```
 The key acts for the organisation it was created in, and can call what a member can. A request without a valid key fails with the `unauthenticated` code. ## Example [Section titled “Example”](#example) Check the connection and the server version with `Ping`, then see which organisation the key acts for with `GetCaller`: 
```sh
export GRITZ_TOKEN=xat_…


curl -sS https://gritz.dev/gritz.v1.GritzService/Ping \
  -H "Authorization: Bearer $GRITZ_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{}'


curl -sS https://gritz.dev/gritz.v1.GritzService/GetCaller \
  -H "Authorization: Bearer $GRITZ_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{}'
```
 `Ping` returns `{"version": "…"}`. An error comes back as a non-2xx status with a JSON body such as `{"code": "unauthenticated", "message": "…"}`. ## Service definition [Section titled “Service definition”](#service-definition) The full definition of `gritz.v1`: every RPC of `GritzService` and every message and enum they use, with their comments. proto/gritz/v1/gritz.proto

# CLI

> Every gritz subcommand and flag, with its environment variable and default.

The `gritz` binary holds the CLI, the server, the runner and the tools that run inside sandboxes. This page lists every subcommand and flag; [Using the CLI](/pr/2460/using/cli/) shows how to use the everyday ones. 
```plaintext
gritz [--help] [--version] <command> [flags] [args]
```
 `--help` (`-h`) works on every command, and `--version` (`-v`) prints the version, as `gritz version` does. Where a flag has an environment variable, the flag wins when both are set. ## Authentication [Section titled “Authentication”](#authentication) `gritz task`, `gritz logs`, `gritz shell`, `gritz mcp`, `gritz notify` and `gritz runner` take these flags, which pick the organisation, credential and server: | Flag | Environment | | | ---------------- | --------------- | ------------------------------------------------------------------------------------------- | | `--org` | `GRITZ_ORG` | The organisation’s name in the `.gritz.yml` files. Defaults to their `org`. | | `--key`, `-k` | `GRITZ_API_KEY` | An API key to use instead of the `.gritz.yml` files. Can’t be combined with `--org`. | | `--server`, `-s` | `GRITZ_SERVER` | The server URL to use with `--key`, which it requires. Defaults to `https://gritz.dev`. | | `--config` | `GRITZ_CONFIG` | A single `.gritz.yml` file to read instead of finding them. Can’t be combined with `--key`. | With `--config`, a command reads only that file: no `.gritz.yml` in the config directory or the working directory, and no `.gritz.local.yml`. Otherwise, without `--key`, a command merges `.gritz.yml` in the config directory with every `.gritz.local.yml` and `.gritz.yml` from the working directory up to `/`, the nearest winning and a directory’s `.gritz.local.yml` above its `.gritz.yml`, and uses the organisation it selects, on that organisation’s `server`, otherwise `https://gritz.dev`. # Custom event envelope

> The request and response of POST /webhook/custom, with every field, its validation, authentication and status codes.

The custom events webhook accepts one event per request. The [custom events guide](/pr/2460/integrations/custom-events/) shows how to set it up; this page is the precise contract. ## Request [Section titled “Request”](#request) 
```plaintext
POST /webhook/custom
Authorization: Bearer xat_…
Content-Type: application/json
```
 The full URL is on **Settings → Organisation**, in the **Custom events** section; for gritz.dev it is `https://gritz.dev/webhook/custom`. The webhook only handles `POST`. ### Authentication [Section titled “Authentication”](#authentication) * The request must carry `Authorization: Bearer <token>`. A request without it gets `401 bearer token required`, even from a browser with a signed-in session: the webhook doesn’t accept session cookies. * The token is an API key (`xat_…`) from the **Keys** page. A wrong, deleted or expired key gets `401 invalid or expired token`. * The token must hold the `event:create` scope, or the request gets `403 permission denied`. API keys hold every scope. A task’s own token does not hold `event:create`. * The event belongs to the key’s organisation and is checked against that organisation’s custom event types. It has no actor, so only the organisation’s public triggers, and link kinds that mark its type public, can act on it. ### Body [Section titled “Body”](#body) A JSON object of at most 1 MiB: 
```json
{
  "type": "alert",
  "description": "checkout-api error rate alert",
  "url": "https://alerts.example.com/alerts/4211",
  "body": "checkout-api error rate above 5% for 10 minutes",
  "attrs": {"severity": ["critical"], "service": ["checkout-api"]},
  "details": {"runbook": "https://wiki.example.com/runbooks/checkout-api"}
}
```
 Fields other than the six below are rejected, as are fields of the wrong JSON type. | Field | Type | Required | Validation | | ------------- | ----------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `type` | string | yes | Must name one of the organisation’s custom event types, as defined on **Events → Custom types**. A type named like a built-in GitHub or Jira type still only resolves to the custom one. | | `description` | string | no | The event’s description on the task’s timeline. Defaults to the type’s label. | | `url` | string | yes | Must be non-empty and an absolute `http` or `https` URL with a host. Used exactly as sent: see [`url`](#url). | | `body` | string | no | The event’s text. Defaults to the empty string. | | `attrs` | object of string → array of strings | no | Every key must be an attribute the type declares, other than `body` and `url`. | | `details` | object of string → string | no | Not validated. | #### `type` [Section titled “type”](#type) The custom type’s name, which matches `^[a-z][a-z0-9_]{0,63}$`. The type’s label becomes the event’s description on the task’s timeline when `description` is empty. #### `url` [Section titled “url”](#url) The resource the event is about, and the key that routes it. If the type declares the `custom.url` [link type](/pr/2460/reference/event-types/#link-types), an event wakes the tasks subscribed to its `url` with a `custom.url` link kind, and a task created by a trigger with a link is subscribed to it. The URL is used exactly as sent, GitHub and Jira URLs included, so events about the same resource must send the same URL byte for byte. #### `body` [Section titled “body”](#body-1) The event’s text, passed to the agent. Triggers match on it through the `body` attribute every custom type declares. #### `attrs` [Section titled “attrs”](#attrs) The values trigger conditions match on, keyed by attribute. Each value is a list of strings; a condition matches when any value in the list satisfies it. An attribute the type declares may be omitted, in which case conditions on it don’t match. Sending `body` or `url` here is an error: send them as the top-level fields, from which their attributes are derived. #### `details` [Section titled “details”](#details) Free-form key/value strings stored with the event and shown with it to the agent and in the Web UI. Triggers can’t match on them. ## Response [Section titled “Response”](#response) A valid event gets `200 OK` with a JSON body: 
```json
{"routed": 1}
```
 `routed` is the number of tasks the event reached: tasks created by agents’ triggers, and existing tasks subscribed to the event’s `url`. It is `0` when no public trigger for the type matches, or every matching trigger yields, and no task is subscribed to the `url` through a link kind that delivers the type and marks it public. Errors are plain text. ## Status codes [Section titled “Status codes”](#status-codes) | Status | Body | Cause | | ------ | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | | `200` | `{"routed": n}` | The event was valid and routed to `n` tasks, possibly none. | | `400` | `invalid envelope: …` | The body is not a JSON object matching the envelope: invalid JSON, an unknown field, a field of the wrong type, or more than 1 MiB. | | `400` | `unknown event type "…"` | `type` is empty or not one of the organisation’s custom types. | | `400` | `url is required` | `url` is missing or empty. | | `400` | `url "…" must be an absolute http or https URL` | `url` is relative, has no host, or has another scheme. | | `400` | `attr "…" must be sent as the envelope's "…" field` | `attrs` has a `body` or `url` key. | | `400` | `attr "…" not declared by event type "…"` | `attrs` has a key the type doesn’t declare. | | `401` | `bearer token required` | No `Authorization: Bearer` header. | | `401` | `invalid or expired token` | The bearer token is not a valid, unexpired API key or gritz token. | | `403` | `permission denied` | The token lacks the `event:create` scope. | | `500` | `internal error` | The server failed to load the custom types or to route the event. |

# Event types

> Every built-in GitHub and Jira event type, with its source and type, its label in the Web UI, and the attributes trigger conditions can match, and the link types each can deliver to.

Every event has a source and a type, such as `github` and `issue_comment`. An agent’s [trigger](/pr/2460/concepts/agents/#triggers) matches one `(source, type)` pair, which the trigger form’s **Event type** list shows by its label, such as **GitHub: Issue Comment**. Its conditions then test the event’s attributes. A [link kind](/pr/2460/concepts/agents/#link-kinds) delivers the event types that can name its link type; see [Link types](#link-types). This page lists the built-in types, from the [GitHub](/pr/2460/integrations/github/) and [Jira](/pr/2460/integrations/jira/) integrations. An organisation’s own types have the source `custom` and the attributes their schema defines; see [Custom events](/pr/2460/integrations/custom-events/). ## Attributes [Section titled “Attributes”](#attributes) Every type has two attributes: * `body`: the event’s text. For a comment or a review it is that text; for a push it is the newest commit’s message; for a check run it is the check’s output; for the other types it is the description of the issue or pull request. * `url`: the event’s own URL. For a comment or a review it is the comment’s or review’s URL; for a push it is the newest commit’s URL; for a check run it is the check run’s or the pull request’s URL; for the other types it is the issue’s or pull request’s URL. Each type adds others. An attribute can hold several values, such as every user mentioned in a comment, and a condition holds if any of them satisfies it. Conditions compare exactly and are case-sensitive; see [Matching](/pr/2460/concepts/agents/#matching). A check run is one check reported through GitHub’s Checks API: for GitHub Actions, one job of a workflow run; other CI systems, such as CircleCI or Buildkite, report theirs the same way. | Attribute | Label | Value | | ------------ | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | | `body` | Check Output | The title and summary of the check’s output, often empty for GitHub Actions. | | `url` | Check Run URL | The check run’s URL; for GitHub Actions, the job’s, such as `https://github.com/owner/repo/actions/runs/123/job/456`. | | `repo` | Repository | The repository the check ran in, such as `owner/repo`. | | `branch` | Branch | The branch the check ran on, such as `master`. Absent for a commit pushed to a fork. | | `conclusion` | Conclusion | How the check finished: `success`, `failure`, `cancelled`, `timed_out`, `action_required`, `neutral`, `skipped`, `stale` or `startup_failure`. | | `check` | Check Name | The check’s name; for GitHub Actions, the job’s name, such as `test` or `build (linux, 1.26)`. | | `app` | App | The GitHub App that reported the check, such as `github-actions` or `circleci-checks`. | | `user` | User | The username GitHub attributes the run to. | Every completed check sends this event, including the checks of a pull request and the successful ones, so a trigger usually has a `conclusion` condition. To match any failure, use `conclusion glob {failure,timed_out,startup_failure}`. A matrix job’s name carries its axes, so match `check` with `prefix` or `glob`, such as `check glob build*`. A trigger for this type, or a link kind’s entry for it, is therefore usually [public](/pr/2460/concepts/agents/#members-and-public); its `branch` condition keeps it to branches only people with push access to the repository can update. The event carries the same extra details as `check_run_completed`, and the pull request’s number (`pull_request`). ## Jira [Section titled “Jira”](#jira) Source `atlassian`. People are identified by their Atlassian account ID, such as `5b10ac8d82e05b22cc7d4ef5`. Enter the bare ID, not the `[~accountid:…]` form Jira uses in comment text. ### `comment_created` [Section titled “comment_created”](#comment_created) **Jira: Issue Comment.** A comment is added to an issue. | Attribute | Label | Value | | --------- | ------------ | ------------------------------------------------------------------------------------------------------ | | `body` | Comment Body | The comment’s text. | | `url` | Comment URL | The comment’s URL, such as `https://your-domain.atlassian.net/browse/PROJ-123?focusedCommentId=10001`. | | `mention` | Mention | The account ID of each person @-mentioned in the comment. | | `user` | User | The account ID of the commenter. | ### `issue_created` [Section titled “issue_created”](#issue_created) **Jira: Issue Created.** An issue is created. A push and a check run also have `repo`, so `repo equals owner/repo` does the same. To find subscribed tasks, gritz reduces the URL to the resource it belongs to, in the forms above, so an event about a comment reaches the tasks subscribed to its issue or pull request. A GitHub Actions job’s URL reduces to its workflow run, so every job and re-run of one workflow run reaches the tasks subscribed to the run. A check run reported by another CI system names no workflow run, so it reaches no subscribed task. See [Subscriptions](/pr/2460/concepts/events-and-links/#subscriptions).

# gritzrpc

> The protocol between gritz and a gritzrpc agent, newline-delimited JSON-RPC 2.0 over the agent's stdio, with its three methods, their JSON, cancellation and event redelivery.

gritzrpc is the protocol gritz speaks to a workspace agent of [`type: gritzrpc`](/pr/2460/operators/workspaces-yaml/#gritzrpc-agent): your own program, run once per run of a task. gritz sends it one request carrying the task, the typed events that started the run and the agent’s MCP servers; the program does its work, may send log lines while it does, and its response ends the run. The protocol only starts and ends runs. Everything the agent does to its task (reporting, creating and subscribing to links, renaming the task, reading it) goes through the `gritz` MCP server, whose config arrives in `run/start`. See [Agent tools](/pr/2460/using/agent-tools/). ## Transport [Section titled “Transport”](#transport) * gritz starts the workspace’s `gritzrpc.command` with `gritzrpc.args`, in its own process group. The working directory is the agent `cwd`, and the environment is the same one the other agents get (see [Environment](/pr/2460/operators/workspaces-yaml/#environment)), secrets included. * **stdin** carries messages from gritz to the agent. * **stdout** carries messages from the agent to gritz, and nothing else. * **stderr** is free-form. It goes to the task’s log as written, with [secrets](/pr/2460/operators/secrets/) masked in the shipped copy. Each message is one JSON-RPC 2.0 object, encoded on a single line and ended with `\n`. There are no `Content-Length` headers, and no limit on a line’s length. JSON escapes newlines inside strings, so a message never spans lines. A new process starts for every run, and it handles exactly one `run/start`. Once the agent has responded, gritz closes its stdin, and the agent should exit. If it is still running 5 seconds later, gritz sends SIGTERM to its process group, and SIGKILL 5 seconds after that. ### stdout is strict [Section titled “stdout is strict”](#stdout-is-strict) Every line the agent writes to stdout must be a JSON-RPC 2.0 message: a JSON object whose `jsonrpc` is `"2.0"`. Any other line fails the run with 
```plaintext
gritzrpc agent: invalid stdout line: <line>
```
 with the line cut to its first 256 bytes, and gritz stops the agent as on [cancel](#cancellation). A stray `console.log` from a dependency is enough, so send diagnostics to stderr or as [`log`](#log) notifications. Once the agent has responded, an invalid line is only logged as a warning. ## Methods [Section titled “Methods”](#methods) | Direction | Method | Kind | Purpose | | ------------- | -------------------------- | ------------ | ------------------------------------ | | gritz → agent | [`run/start`](#runstart) | request | Start the run. The response ends it. | | gritz → agent | [`run/cancel`](#runcancel) | notification | Ask the agent to stop gracefully. | | agent → gritz | [`log`](#log) | notification | Write one line to the task’s log. | ### `run/start` [Section titled “run/start”](#runstart) The first message on stdin, always with `id` `1`. Shown here over several lines for reading; on the wire it is one line. 
```json
{"jsonrpc":"2.0","id":1,"method":"run/start","params":{
  "protocolVersion": 1,
  "resume": false,
  "cwd": "/workspace",
  "task": {"id":"2283","name":"Ship the release","workspace":"mastra",
           "status":"TASK_STATUS_RUNNING","version":"1","agentId":"7",
           "createdAt":"2026-11-02T19:50:00Z","url":"https://gritz.dev/ui/tasks/2283?org=12"},
  "events": [
    {"id":"9101","taskId":"2283","wake":true,"createdAt":"2026-11-02T19:50:00Z",
     "instruction":{"text":"Open a PR that bumps the version."}}
  ],
  "links": [
    {"id":"881","taskId":"2283","relevance":"Issue","url":"https://github.com/acme/app/issues/12",
     "kind":"github.issue","createdAt":"2026-11-02T19:50:00Z"}
  ],
  "mcpServers": {
    "gritz": {"type":"stdio","command":"/gritz/bin/gritz","args":["tool","agent-mcp","…"]},
    "github": {"type":"http","url":"https://api.githubcopilot.com/mcp/"}
  }
}}
```
 | Field | | | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | `protocolVersion` | The protocol’s version, `1`. An agent that doesn’t support it responds with error code `-32000`. | | `resume` | `false` on the task’s first run, and on the first run after a [sandbox reset](/pr/2460/concepts/tasks/#resetting-the-sandbox). It stays `false` until a run succeeds, and is `true` on every run after that, wakes and restarts alike. | | `cwd` | The agent’s working directory, the expanded agent `cwd`. | | `task` | The task. | | `events` | The task’s instruction and external events that this run is for, oldest first. Always present; empty on a run with nothing new, such as a restart. | | `links` | The task’s links. Sent only while `resume` is `false`, and omitted when the task has none. A later run that needs them calls `get_my_task`. | | `mcpServers` | The agent’s MCP servers by name: the workspace’s [`mcp_servers`](/pr/2460/operators/workspaces-yaml/#mcp_servers) and the `gritz` server. Each has `type` and, as for the workspace config, `command`, `args` and `env`, or `url` and `headers`. | On the first run, `events` and `links` together are the task’s brief, so the agent learns its task without calling `get_my_task`. On a wake, `events` holds the events that woke the task, such as an `external` event for a review comment on a pull request the task subscribed to. #### Encoding of `task`, `events` and `links` [Section titled “Encoding of task, events and links”](#encoding-of-task-events-and-links) `task`, the entries of `events` and the entries of `links` are the `Task`, `Event` and `TaskLink` messages of the [API](/pr/2460/reference/api/#service-definition), in the standard JSON mapping of protocol buffers: * Field names are lowerCamelCase: `taskId`, `createdAt`, `agentId`. * 64-bit integers, such as `id`, `taskId` and `version`, are JSON **strings**. * Timestamps are RFC 3339 strings, durations strings such as `"3600s"`, and enums their value’s name, such as `"TASK_STATUS_RUNNING"`. * Fields with their zero value are omitted. * An event’s kind is the one key it carries for it: `"instruction"`, with `text` and `url`, or `"external"`, with `description`, `url`, `source`, `type`, `details` and `data`. An event has no separate type field; the `type` inside `external` is the source’s own event type, such as `pull_request_review_comment`. See [Event types](/pr/2460/reference/event-types/). 
```json
{"id":"9120","taskId":"2283","wake":true,"createdAt":"2026-11-02T20:31:00Z",
 "external":{"description":"review comment","url":"https://github.com/acme/app/pull/14#discussion_r1",
             "source":"github","type":"pull_request_review_comment",
             "details":{"path":"main.go","line":"12"}}}
```
 Ignore fields you don’t know, and skip events of a kind you don’t know: new fields and kinds don’t change `protocolVersion`. #### Result [Section titled “Result”](#result) A successful response ends the run successfully: 
```json
{"jsonrpc":"2.0","id":1,"result":{}}
```
 The result has no fields; gritz ignores any it carries. Success means this run’s work is done, which includes a workflow that is now suspended until an event arrives. The task is completed, and a subscribed link wakes it with a new run when a matching event comes in. #### Error [Section titled “Error”](#error) An error response fails the run: 
```json
{"jsonrpc":"2.0","id":1,"error":{"code":-32001,"message":"step deploy failed","data":{"step":"deploy"}}}
```
 The run’s error, shown on the task’s timeline, is `gritzrpc agent: step deploy failed (code -32001)`. `data`, if present, is written to the task’s log. Apart from `-32000`, an unsupported `protocolVersion`, the codes are yours to choose; gritz doesn’t interpret them. ### `run/cancel` [Section titled “run/cancel”](#runcancel) 
```json
{"jsonrpc":"2.0","method":"run/cancel"}
```
 No params. gritz sends it when the task is cancelled or restarted, when the sandbox shuts down, and when the agent writes an invalid stdout line. The agent should wind down, checkpointing a workflow for example, respond to `run/start` with a result or an error, and exit. See [Cancellation](#cancellation). ### `log` [Section titled “log”](#log) 
```json
{"jsonrpc":"2.0","method":"log","params":{"level":"info","msg":"step finished","attrs":{"step":"plan","ms":1532}}}
```
 | Field | | | ------- | --------------------------------------------------------------------------------------------------- | | `level` | `debug`, `info`, `warn` or `error`. Missing or any other value is `info`. | | `msg` | The message. | | `attrs` | Optional. A flat object of attributes. A string value is logged as is; any other value as its JSON. | gritz writes the line to the task’s log, with the attribute `agent=gritzrpc` added. A log line is not a task event: it doesn’t show on the timeline. Use the `report` tool of the `gritz` MCP server for a message the user should see. ### Anything else [Section titled “Anything else”](#anything-else) * A request from the agent, any message with both `id` and `method`, gets a `-32601` method-not-found error: gritz offers no methods. * An unknown notification, a response with an `id` other than `1`, or a second response is logged as a warning and ignored. * If the agent exits without responding to `run/start`, the run fails with `gritzrpc agent exited without responding: <exit status>`. * If the agent responds and then exits with a non-zero status, the response stands, and the exit status is logged as a warning. ## Cancellation [Section titled “Cancellation”](#cancellation) When a run is cancelled, gritz: 1. Sends `run/cancel`. 2. Sends SIGTERM to the agent’s process group if it is still running 10 seconds later. 3. Sends SIGKILL to the group 5 seconds after that. A cancelled run never counts as successful, whatever the agent responded, including a successful result sent before it exited. Its events are delivered again on the next run. An invalid stdout line stops the agent the same way, and the run fails with that line’s error. ## Events are delivered at least once [Section titled “Events are delivered at least once”](#events-are-delivered-at-least-once) gritz records a run’s events as handled only after the run succeeds. When a run fails, is cancelled, or its sandbox dies, the next run receives the same events again, followed by any new ones. Rarely, an event is delivered again even after a successful response. **Deduplicate by event `id`.** A workflow resumed twice with the same event has to recognise the second time as already applied, for example by saving the ids of the events it handled next to its own state. ## State between runs [Section titled “State between runs”](#state-between-runs) The process is new on every run, so an agent that has to remember something from one run to the next saves it itself: in the sandbox, or in an external database. A task’s sandbox and its files are kept between runs, until the sandbox is [reset](/pr/2460/concepts/tasks/#resetting-the-sandbox) or [gone](/pr/2460/concepts/tasks/#a-gone-sandbox).

# Agent tools

> The gritz tools every agent gets (get_my_task, update_my_task, create_link, report and get_github_token), what gritz tells agents to do with them, and how to write instructions that use them.

gritz adds an MCP server named `gritz` to every agent it runs, alongside the MCP servers in the task’s [workspace](/pr/2460/concepts/workspaces/). Its tools let the agent read and update its own task, and nothing else: they work with a token that only grants access to that task (see [Task tokens](/pr/2460/concepts/orgs-members-keys/#task-tokens)). ## What agents are told [Section titled “What agents are told”](#what-agents-are-told) On a task’s first run, before your instructions, gritz tells the agent to: * name the task with `update_my_task` if it has no name; * create a link with the fitting link kind of the task’s agent for each resource it creates, such as a pull request, an issue or a comment, so replies reach the task even after it finishes, and with no kind for reference links it didn’t create. gritz lists the agent’s link kinds, each with its link type and claim, or says the agent has none; * prefer URLs a person can open over API URLs; * use `report` for anything you should see, since its text replies aren’t shown; * answer questions or problems on the platform the latest instruction or event came from, such as the pull request, and say which task it is from; * call `get_my_task` if it needs to check for updates mid-run. Then it gives the agent the task: its instructions, events and links, so it doesn’t need a tool call to start. On later runs the agent gets only what is new. See [Instructions and runs](/pr/2460/concepts/tasks/#instructions-and-runs). ## Tools [Section titled “Tools”](#tools) ### `get_my_task` [Section titled “get_my_task”](#get_my_task) Returns the task: its ID, name, status, workspace and URL, its links with their kinds and claims, and its instructions and events in order. Reports and status changes aren’t included. ### `update_my_task` [Section titled “update_my_task”](#update_my_task) Renames the task. It takes `name`, the new name. Agents can’t change anything else about their task, including its auto-archive delay. ### `create_link` [Section titled “create_link”](#create_link) Links the task to an external resource, and appears on the task’s timeline and in its sidebar. | Parameter | | | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `url` | The resource’s URL. | | `relevance` | How the resource relates to the task, such as “PR implementing the fix”. | | `title` | Optional. A title to show for the link. | | `kind` | Optional. A link kind of the task’s agent, such as `owned-pr`. The link then receives the events that kind lists. Omit it for a plain reference link, which receives no events. | A link with a kind is how a task hears about review comments on its pull request, or replies on its Jira issue. Which events reach it is up to the kind, as defined on the task’s [agent](/pr/2460/concepts/agents/#link-kinds). The URL must be a resource of the kind’s link type, such as a pull request for a `github.pr` kind, and the link stores the resource’s own URL; an unknown kind fails, listing the agent’s kinds. See [Events and links](/pr/2460/concepts/events-and-links/). ### `report` [Section titled “report”](#report) Posts `message` to the task’s timeline. This is how an agent tells you what it did, what it found or what is blocking it: the agent’s own replies only appear in the task’s log. ### `get_github_token` [Section titled “get_github_token”](#get_github_token) Meant to return a short-lived GitHub token for the organisation’s GitHub App installation. Only tasks whose workspace has the `github_token` [capability](/pr/2460/operators/workspaces-yaml/#capabilities) get this tool, and the server doesn’t issue these tokens yet, so the tool always fails. Agents get GitHub access today from their workspace instead: a token under `secrets:`, such as `GH_TOKEN`, which `gh`, git and the GitHub MCP server can use. See [`secrets`](/pr/2460/operators/secrets/). ## Writing instructions that use them [Section titled “Writing instructions that use them”](#writing-instructions-that-use-them) The agent already uses these tools as above without being asked. Mention them when you want something specific: * **To get a summary where you’ll see it**: “When you’re done, report a summary of the changes and anything you couldn’t do.” * **To keep a task listening**: “Open a draft pull request and link it with the `owned-pr` kind.” The task finishes, and a review comment on the pull request wakes it if the kind lists that event. * **To link context you gave it**: “Link the incident page as a reference, with no kind.” * **To name it predictably**: “Name this task `deps: bump <package>`.” The agent’s other tools, such as for GitHub or Jira, come from the MCP servers and credentials in its workspace. Ask your operator what a workspace provides, or see [`workspaces.yaml`](/pr/2460/operators/workspaces-yaml/).

# CLI

> Use the gritz CLI to create, list and update tasks, read a task's log, open a shell in its sandbox and get desktop notifications, and log in to one or more organisations.

The `gritz` binary is the CLI as well as the runner and server. ## Install [Section titled “Install”](#install) `gritz` runs on Linux and macOS, on amd64 and arm64. Install it in one of three ways. ### Install script [Section titled “Install script”](#install-script) 
```bash
curl -fsSL https://docs.gritz.dev/install.sh | sh
```
 The script downloads the archive for your platform from the latest [GitHub release](https://github.com/gritzapp/gritz/releases), checks it against the release’s `checksums.txt`, and installs `gritz` into `~/.local/bin`. Two environment variables change that: | Variable | Default | | | ------------------- | ------------------ | ----------------------------------------- | | `GRITZ_VERSION` | the latest release | The release to install, such as `v4.7.0`. | | `GRITZ_INSTALL_DIR` | `~/.local/bin` | The directory to install into. | 
```bash
curl -fsSL https://docs.gritz.dev/install.sh | GRITZ_VERSION=v4.7.0 GRITZ_INSTALL_DIR=/usr/local/bin sh
```
 `~/.local/bin` isn’t on your `PATH` by default on macOS, and on some Linux distributions. If it isn’t on yours, the script says so; add it in your shell profile: 
```bash
export PATH="$HOME/.local/bin:$PATH"
```
 To update, run the script again. ### mise [Section titled “mise”](#mise) With [mise](https://mise.jdx.dev/): 
```bash
mise use -g github:gritzapp/gritz
```
 To update, run `mise upgrade github:gritzapp/gritz`. ### Manual download [Section titled “Manual download”](#manual-download) Each [GitHub release](https://github.com/gritzapp/gritz/releases) has an archive per platform, `gritz_<os>_<arch>.tar.gz` (`os` is `linux` or `darwin`, `arch` is `amd64` or `arm64`), holding the `gritz` binary, and a `checksums.txt` with their SHA-256 sums. Download the archive for your platform, extract `gritz`, and put it in a directory on your `PATH`: 
```bash
curl -fsSLO https://github.com/gritzapp/gritz/releases/latest/download/gritz_linux_amd64.tar.gz
tar -xzf gritz_linux_amd64.tar.gz gritz
mv gritz ~/.local/bin/
```
 To update, download the new release’s archive and replace the binary. ## Configuration [Section titled “Configuration”](#configuration) Log in with your browser: 
```bash
gritz login
```
 
```plaintext
Opening https://gritz.dev/ui/oauth/authorize?... in your browser.
Logged in to Acme Labs (org 12) as "acme-labs"
```
 `gritz login` opens the gritz Web UI in your browser, signed in as you, and waits for you to approve. It logs in to the organisation selected in the Web UI at that moment; to log in to another, switch to it in the Web UI before you approve. If the browser doesn’t open, open the printed URL yourself, on the same machine: the browser hands the login back to `gritz login` there. It gives up after 10 minutes. The CLI then acts as you, with what a member can do in that organisation. `gritz login` saves the login under a name in `.gritz.yml` in the gritz config directory. The name is the organisation’s name in lowercase with dashes, unless `--name` gives another, and the first organisation you log in to becomes the selected `org`. Log in once for each organisation you work in: 
```yaml
org: acme-labs
orgs:
  acme-labs:
    id: 12
    refresh_token: eyJhbGciOiJFZERTQSIs...
    server: https://gritz.dev
  personal:
    id: 3
    refresh_token: eyJhbGciOiJFZERTQSIs...
    server: https://gritz.dev
```
 A login lasts as long as you keep using it: it expires after 30 days in which the CLI didn’t use it, and stops working once you are removed from the organisation or it is deleted. The CLI renews the saved `refresh_token` in the file it came from about once a day while you use it. When a login has expired, commands fail with: 
```plaintext
login expired or revoked: run `gritz login`
```
 Run `gritz login` again to replace it. A login isn’t tied to the machine, so an entry copied into another machine’s `.gritz.yml` works there too. ### Logging in with an API key [Section titled “Logging in with an API key”](#logging-in-with-an-api-key) Where no browser can reach `gritz login`, such as a remote machine over SSH, or for a program rather than a person, log in with an [API key](/pr/2460/concepts/orgs-members-keys/#api-keys) instead. Create one on the **Keys** page and pass it with `--key` (`-k`): 
```bash
gritz login --key xat_...
```
 `gritz login` asks the server which organisation the key belongs to and saves the key in place of a `refresh_token`: 
```yaml
orgs:
  acme-ci:
    id: 12
    key: xat_...
    server: https://gritz.dev
```
 A key doesn’t expire. Logging in again to the same organisation and server replaces the entry’s credential, key or browser login. The config directory is `GRITZ_CONFIG_DIR` if set, otherwise `gritz` under your user config directory: `~/.config/gritz` on Linux, `~/Library/Application Support/gritz` on macOS. ### Choosing an organisation [Section titled “Choosing an organisation”](#choosing-an-organisation) Every command acts in one organisation: the one `--org` (or `GRITZ_ORG`) names, otherwise the `org` of the `.gritz.yml` files. 
```bash
gritz task list --org personal
```
 A `.gritz.yml` file can also live in any directory, such as a repository or a folder of checkouts. A command reads every `.gritz.yml` from the directory it runs in up to `/`, on top of the one in the config directory, and the nearest file wins. Organisations of the same name replace each other whole. A repository can pick its organisation without holding a login: 
```yaml
org: acme-labs
allowed: [acme-labs]
```
 `allowed` lists the organisations that can be used below the file; a command run there with any other `--org` fails, and so does every command if the `org` isn’t allowed. Every field is optional, and an unknown field is an error. A `.gritz.local.yml` beside a `.gritz.yml` holds local overrides, such as a different `org` or `allowed`, or organisations with their keys. It has the same format and wins over the `.gritz.yml` in its directory. Add it to `.gitignore` to keep it out of the repository: 
```bash
echo .gritz.local.yml >> .gitignore
```
 `gritz login --list` shows the organisations you can pick from the current directory, with `*` marking the one selected by default: 
```plaintext
   NAME      ID  SERVER             LOGIN
   acme-ci   12  https://gritz.dev  key
*  personal  3   https://gritz.dev  oauth
```
 ### Server [Section titled “Server”](#server) Every command talks to the organisation’s `server`, or to `https://gritz.dev` if it has none. `gritz login` saves the server you give it with `--server` (`-s`) or the `GRITZ_SERVER` environment variable: 
```bash
gritz login --server https://gritz.example.com
```
 Without `--server`, it uses the top-level `server` of the nearest `.gritz.yml` that sets one, otherwise `https://gritz.dev`, so a repository can name the server its organisation lives on: 
```yaml
server: https://gritz.example.com
```
 The top-level `server` is read only by `gritz login`. ### Key without a config file [Section titled “Key without a config file”](#key-without-a-config-file) `--key` (`-k`) or the `GRITZ_API_KEY` environment variable gives a command its key directly, for CI and other places with no config file. The command then reads no `.gritz.yml` files, fails if `--org` is also given, and talks to `--server`, `GRITZ_SERVER` or `https://gritz.dev`. Other than in `gritz login`, `--server` and `GRITZ_SERVER` need a key this way, since an organisation in a `.gritz.yml` carries its own server: 
```bash
GRITZ_API_KEY=xat_... gritz task list
```
 ### A single config file [Section titled “A single config file”](#a-single-config-file) `--config` or the `GRITZ_CONFIG` environment variable names the one `.gritz.yml` file a command reads, with the same format. No other `.gritz.yml` or `.gritz.local.yml` is read, from the config directory or the working directory. `--org` or the file’s `org` picks the organisation, and `--key` can’t be given with it: 
```bash
gritz login --config ./ci.gritz.yml --key xat_...
GRITZ_CONFIG=./ci.gritz.yml gritz task list
```
 `gritz login --config` saves the organisation in that file, creating it if needed, takes its default server from the file’s top-level `server`, and `--list` shows only that file’s organisations. ## Tasks [Section titled “Tasks”](#tasks) ### `gritz task create` [Section titled “gritz task create”](#gritz-task-create) Creates a task and starts it straight away, then prints it as JSON. 
```bash
gritz task create --agent 7 \
  -i "Add a --json flag to the list command and open a pull request."
```
 | Flag | | | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `--agent`, `-a` | The ID of the [agent](/pr/2460/concepts/agents/) the task belongs to. The task runs with the agent’s runner, workspace, auto-archive delay, variables and features. Required. | | `--instruction`, `-i` | An instruction. Repeat it for several. | | `--name`, `-n` | The task’s name. The agent names it if you don’t. | An agent’s ID is at the end of its page’s URL in the Web UI, such as `https://gritz.dev/ui/agents/7`. Agents are created and changed in the Web UI and through the [MCP tools](/pr/2460/integrations/mcp/#agents). ### `gritz task list` [Section titled “gritz task list”](#gritz-task-list) Prints the organisation’s 50 newest unarchived tasks as JSON, with their status, agent ID, runner, workspace and URL. ### `gritz task update` [Section titled “gritz task update”](#gritz-task-update) Changes a task. 
```bash
gritz task update 1234 --start -i "Also update the README."
```
 | Flag | | | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | | `--add-instruction`, `-i` | Add an instruction. Repeat it for several. | | `--start`, `-r` | Start the task, as the Web UI does when you send an instruction. A running task isn’t interrupted: it runs again when its current run ends. | | `--name`, `-n` | Rename the task. | | `--auto-archive` | Set the auto-archive delay. Left out, the task keeps the delay it has. | An instruction added without `--start` waits on the task until something else starts it, such as an event or a later `--start`. Cancelling, restarting and archiving tasks, and resetting their sandboxes, are done in the [Web UI](/pr/2460/using/web-ui/#the-task-page). ## `gritz logs` [Section titled “gritz logs”](#gritz-logs) Prints a task’s log: the setup commands, the agent’s output and gritz’s own lines, as the Web UI’s **Logs** view shows them. It works for any task in the organisation, including tasks whose sandbox is gone. 
```bash
gritz logs 1234     # print the log so far
gritz logs -f 1234  # and keep following it
```
 `--interval` sets how often `-f` checks for new output, `2s` by default. ## `gritz shell` [Section titled “gritz shell”](#gritz-shell) Opens an interactive shell in a finished task’s sandbox, to look at what the agent left behind: 
```bash
gritz shell 1234
```
 The runner starts the sandbox again with a shell in place of the agent. It works whatever the runner’s backend and wherever it runs: the server relays the session, so you need no access to the runner. See [A shell in the sandbox](/pr/2460/operators/debugging/#a-shell-in-the-sandbox). ## `gritz notify` [Section titled “gritz notify”](#gritz-notify) Stays running and shows a desktop notification each time one of the organisation’s tasks completes, fails or is cancelled. 
```bash
gritz notify
```
 Run one `gritz notify --org <name>` for each organisation to watch several. `--title` sets the notifications’ title, `gritz` by default. It uses `notify-send` on Linux and the system notifications on macOS and Windows. ## Other commands [Section titled “Other commands”](#other-commands) * `gritz mcp` runs a local MCP server that lets Claude Code, Cursor and other MCP clients create and manage tasks; see [MCP](/pr/2460/integrations/mcp/). * `gritz runner`, `gritz download`, `gritz workspaces` and `gritz containers` are for running a runner; see [Runner](/pr/2460/operators/runner/) and [Debugging](/pr/2460/operators/debugging/). * `gritz version` prints the CLI’s version. [CLI reference](/pr/2460/reference/cli/) lists every command and flag.

# Web UI

> A tour of the gritz Web UI, the task list and task page, agents and their schedules, events, workspaces, members, keys and settings.

The Web UI is served by the gritz server under `/ui/`, for example `https://gritz.dev/ui/`. It updates live: task statuses, timelines and logs change as they happen, without reloading. The dot next to the organisation selector shows whether the live connection is up. The bar at the top links to every page, and holds the organisation selector, the light and dark theme toggle, the **Settings** gear and **Logout**. Press Ctrl+K (⌘K on a Mac) anywhere to jump to one of the recent tasks by name. ## Tasks [Section titled “Tasks”](#tasks) **Tasks** lists the organisation’s tasks, newest first: each one’s name, ID, runner and workspace, its [agent](/pr/2460/concepts/agents/), its [status](/pr/2460/concepts/tasks/#statuses) and when it was created. Click the agent to open its page. A `command:` badge next to the status is an action the runner hasn’t carried out yet. Check one or more agents in the agent filter to list only their tasks, or pick **All agents** for every task. Turn on **Show archived** to include archived tasks, and archive or unarchive a task from its row. The filters are remembered per organisation. **+ Task** opens the page of a new task. Pick its [agent](/pr/2460/concepts/agents/); the name is optional. The task runs with the agent’s runner, workspace, auto-archive delay, variables and features. Sending the first instruction creates the task and starts it. An agent’s **Run** button, on the **Agents** page or the agent’s page, opens it with that agent picked and its prompt in the instruction box. ## The task page [Section titled “The task page”](#the-task-page) The sidebar on the left holds the task’s status, its agent, name, ID, runner and workspace, its three views, its created and updated times, its variables, the links it **Follows** with their [kind and claim](/pr/2460/concepts/agents/#link-kinds), and its actions: * **Archive** or **Unarchive**. When an auto-archive delay is counting down, the time left shows next to it. * **Cancel**, while the task is pending or running. * **Restart**, once it is running or finished. * **Reset sandbox**, once it is finished, to delete its sandbox so the next run starts in a new one. See [Resetting the sandbox](/pr/2460/concepts/tasks/#resetting-the-sandbox). * **Auto-archive**, to change the delay: never, immediately, 1 hour, 6 hours, 24 hours or 7 days. The arrow at the top collapses the sidebar to icons. ### Timeline [Section titled “Timeline”](#timeline) The timeline is everything that happened to the task, in order: your instructions, events from GitHub, Jira and custom sources, the agent’s reports, links it created, and status changes with who caused them. It opens at the latest entry and loads older ones as you scroll up. The box at the bottom sends an instruction: Enter sends it, Shift+Enter adds a new line. An archived task has no box. A finished task starts again with it; a running task picks it up when its current run ends. See [Instructions and runs](/pr/2460/concepts/tasks/#instructions-and-runs). ### Logs [Section titled “Logs”](#logs) The task’s log, as the sandbox writes it: setup commands, the agent’s messages and tool calls, and gritz’s own lines. It follows new output while the task runs. Declared [secrets](/pr/2460/operators/secrets/) are masked. ### Shell [Section titled “Shell”](#shell) A terminal in the task’s sandbox, for looking at what the agent left behind. It can be opened once the task has finished, and works like [`gritz shell`](/pr/2460/using/cli/#gritz-shell): the runner starts the sandbox again with a shell in place of the agent. ## Agents [Section titled “Agents”](#agents) **Agents** lists the organisation’s [agents](/pr/2460/concepts/agents/), each with its runner and workspace, what it **Starts on** (its triggers and [schedules](/pr/2460/concepts/schedules/), or **Manual only**), what it **Follows** (its link kinds) and how **Recent** its newest task is. **Recent** links to the [task list](#tasks) filtered to that agent. **List**, **Cards** and **Routing** switch between the table, a card per agent with everything written out, and a diagram of which events reach which agents and link types. **+ Agent** creates an agent. Each row has a **Run** button, which opens a [new task](#tasks) of the agent with its prompt as the first instruction, and a **⋯** menu to **Edit** or **Delete** it; clicking the name also opens it. An agent’s page is its form, with **Run**, **Test event** and **⋯** (Delete) at the top. It has three sections: * **Template**: name, runner, workspace, variables, [features](/pr/2460/concepts/agents/#the-template), prompt and auto-archive delay. * **Follows**: the [link kinds](/pr/2460/concepts/agents/#link-kinds), each with a link type, a kind name, a claim, and a switch per event type it delivers. A switched-on event type has its conditions, **Public** and **Wake**. * **Starts on**: **Add trigger** and **Add schedule**. * Each [trigger](/pr/2460/concepts/agents/#triggers) has an event type, conditions, a link kind, claims to yield to, a prompt and **Public**. Triggers are checked from the top; the arrows reorder them. * Each schedule has a name, a cron expression, a timezone and a prompt, and an on/off switch on its header. A saved schedule shows its next run and its last run, with a link to the task it created. The bar at the bottom saves the agent, or discards the changes. **Test event**, on the **Agents** page, the **Events** page or an agent’s page, composes an event and shows what each agent would do with it, or fires it. See [Testing with a test event](/pr/2460/concepts/agents/#testing-with-a-test-event). ## Events [Section titled “Events”](#events) **Events** has two tabs: * **Recent**: the latest events delivered to the organisation’s tasks. Open one to see its description, URL, body, details and the task it was delivered to, and whether it woke that task. * **Custom types**: the organisation’s custom event types. **+ Type** adds one. See [Custom events](/pr/2460/integrations/custom-events/). **Test event** opens the [test event](/pr/2460/concepts/agents/#testing-with-a-test-event) form. ## Workspaces [Section titled “Workspaces”](#workspaces) **Workspaces** lists the [workspaces](/pr/2460/concepts/workspaces/) the organisation’s [runners](/pr/2460/concepts/runners/) have registered, with their runner and description, the [features](/pr/2460/operators/workspaces-yaml/#features) and [variables](/pr/2460/operators/workspaces-yaml/#variables) they declare, the agents that use them and when they were last registered. Filter by runner, and **Clear** to remove the listed runner’s workspaces, or every runner’s. A workspace’s page lists its features and variables with their descriptions, and the agents that use it and each of its features. ## Members and Keys [Section titled “Members and Keys”](#members-and-keys) **Members** lists the organisation’s members and their role. The owner adds members by email here, and removes them from a member’s **⋯** menu. **Keys** lists the organisation’s API keys. **+ Key** creates one and shows its token once, and a key’s **⋯** menu deletes it. See [Organisations, members and API keys](/pr/2460/concepts/orgs-members-keys/). ## Settings [Section titled “Settings”](#settings) **Settings** has two tabs: * **Account**: **My organisations**, the organisations you own, where you create new ones and delete them, and **Connected accounts**, your linked [GitHub](/pr/2460/integrations/github/#link-your-github-account) and [Atlassian](/pr/2460/integrations/jira/#link-your-atlassian-account) accounts. Linking them lets [agents](/pr/2460/concepts/agents/#members-and-public) recognise your comments as a member’s. * **Organisation**: the URLs and settings that connect the organisation to other systems: the [MCP server URL](/pr/2460/integrations/mcp/) for MCP clients, the [custom events](/pr/2460/integrations/custom-events/) webhook URL, the [GitHub App installation](/pr/2460/integrations/github/#install-the-github-app), and the [Atlassian webhook](/pr/2460/integrations/jira/#connect-jira) URL and secret. The server’s version is at the bottom of the page.
