docs.gritz.dev docs site

Issue: https://github.com/gritzapp/gritz/issues/2034

Problem

Section titled “Problem”

gritz has no user documentation. What exists is spread across README.md (runner quick start, secrets, debugging, events), CLAUDE.md, skills, the gritzapp/workspaces repo and implemented proposals. Proposals describe designs for contributors, not how to use a feature. A user who wants to route alerts from their monitoring system into gritz has to read proposals/implemented/custom-external-events.md and internal/server/customserver/webhook.go to find the envelope format and the rule that custom rules must be public.

Agents have the same problem, and they are a large share of gritz’s readers: the agents gritz runs, and the agents users drive gritz from over MCP.

#2034 asks for a public, static docs site at docs.gritz.dev, written as Markdown in this repo. These decisions are already made, and this proposal designs within them:

  • Generator: Starlight (Astro). Source is Markdown in docs/, built with pnpm like webui/ and diagrams/.
  • Hosting: GitHub Pages from the existing gh-pages branch. Docs publish to the root and docs.gritz.dev becomes the Pages custom domain. The docs build also builds the Motion Canvas diagrams into /diagrams/, so a docs PR preview carries its own diagrams. Old gritzapp.github.io/gritz/<diagram> URLs may break.
  • Audience: users of a gritz deployment first, plus a separate operators section. Contributor docs stay in CLAUDE.md, skills and proposals/.
  • Agent accessible: llms.txt and llms-full.txt, raw Markdown for each page, and static HTML that needs no JS. Serving the docs through the gritz MCP server is a later layer.
  • First content: custom events.

Design

Section titled “Design”

Layout of docs/

Section titled “Layout of docs/”

docs/ is a standalone pnpm project, set up like diagrams/: its own package.json, pnpm-lock.yaml and pnpm-workspace.yaml (with the allowBuilds: esbuild: true that Astro needs too).

astro.config.mjs sets these:

  • site: 'https://docs.gritz.dev', used for absolute URLs in llms.txt, the sitemap and canonical links.
  • base: process.env.DOCS_BASE ?? '/'. PR previews build with DOCS_BASE=/pr/<n>/. Unlike diagrams/site.ts, Astro writes absolute URLs, so a preview needs its own base rather than relative links.
  • sidebar: written out explicitly, one group per section. Each group uses autogenerate: { directory }, so a page shows up in its group as soon as its file lands, and a group without pages yet is left out.
  • editLink.baseUrl: 'https://github.com/gritzapp/gritz/edit/master/docs/'.
  • Plugins: starlight-llms-txt, and starlight-links-validator so a broken internal link fails the build.
  • When DOCS_BASE is set (a preview), head adds <meta name="robots" content="noindex">.

Pages are .md by default. .mdx is allowed only on pages that need a component (today, only the diagram embed). This keeps the raw Markdown we serve to agents as close as possible to what they would read on GitHub.

Page list and sidebar

Section titled “Page list and sidebar”

Sections are listed in sidebar order. The slug is the file path under src/content/docs/ and the URL path. ★ marks the first content to land.

Start here

  • index — what gritz is: agents running in sandboxes, driven by tasks and events. Links to each section, and to llms.txt for agents.
  • getting-started — using a deployment: sign in, pick an org, create a task from the Web UI, watch it run, follow up with another instruction, archive it.

Concepts (concepts/)

  • tasks — instructions, the task lifecycle and statuses, restarts, auto-archive, archived tasks, the task log.
  • workspaces — the user’s view: what a workspace provides (image, repos, agent, MCP servers), how to pick one, and that operators define them.
  • runners — the user’s view: where a task runs, and choosing a runner.
  • events-and-links — links, subscribe=true, how an event on a linked URL wakes a task, and the event timeline. Moved from the README’s ## Events, with images/events.svg.
  • routing-rules — event source and type, conditions (equals/prefix/contains), first match wins, wake versus create, public, the test-event form.
  • namespaces — task namespaces and how they scope routing.
  • schedules — scheduled tasks and “run now”.
  • orgs-members-keys — orgs, members, API keys and what they can do.

Using gritz (using/)

  • web-ui — a tour of the task list, task page, events, routing and settings.
  • cli — gritz task, gritz logs, gritz shell, gritz notify, and how to configure a server URL and API key (~/.config/gritz/config.yaml).
  • agent-tools — the tools gritz injects into every agent (get_my_task, update_my_task, create_link, report), so users can write instructions that use them.

Integrations (integrations/)

  • github — installing the GitHub App, linking accounts, PR and issue comment events, reactions, and agent GitHub tokens.
  • jira — linking Atlassian, and issue and comment events.
  • custom-events ★ — custom event types (Custom Schemas), the /webhook/custom endpoint, API keys, the envelope, public rules, the subscription URL, and troubleshooting by HTTP status.
  • mcp — connecting Claude Code, Cursor or any MCP client to /mcp (OAuth), or to gritz mcp (stdio). Covers the tools (list_workspaces, create_task, get_task, list_tasks, update_task, archive_task) and channels.

Reference (reference/)

  • custom-event-envelope ★ — the POST /webhook/custom request and response: fields, limits (1 MiB), status codes.
  • event-types — the built-in (source, type) pairs and their attrs, for writing conditions.
  • cli — every gritz subcommand and flag.

Operators (operators/)

  • overview — server, runner, driver and sandbox, with images/architecture.svg. Who talks to whom, and what each needs to reach.
  • server — running gritz server: Postgres, auth, the GitHub App and Atlassian config, base URL, and the server’s MCP and OAuth endpoints.
  • runner — running gritz runner: API key, gritz download, the config file. Moved from the README’s Quick Start.
  • backends — Docker and Lambda MicroVMs, and when to use which. local is left out because it is for tests and development.
  • workspaces-yaml — a workspaces.yaml reference: container, commands, agent (type, verbose), MCP servers, and ${env:}/${sh:} expansion. Links to gritzapp/workspaces for examples.
  • secrets — the secrets: map and what is masked where. Moved from the README’s ## Secrets.
  • deployment — the published GHCR images, running the runner as a Docker Compose service (links gritzapp/workspaces/runner), upgrades (server, runner and driver ship together).
  • debugging — gritz logs, verbose: true, gritz shell, gritz containers and prune. Moved from the README’s ## Debugging.

This list is the target. The layers below bring it in a few pages at a time, and because of autogenerate the sidebar never links to a missing page.

Hosting on gh-pages

Section titled “Hosting on gh-pages”

One branch is served by Pages, written by two workflows. The docs build also builds the Motion Canvas projects in diagrams/: pnpm build in docs/ first runs pnpm diagrams, which installs diagrams/ and runs its Vite build into docs/public/diagrams/ (gitignored), and Astro then copies it to dist/diagrams/ like any public file. So one build publishes both, and the diagrams sit under the same base as the pages that play them.

Workflow Trigger Writes clean-exclude
docs-pages.yml push to master, docs/**, diagrams/** / pr/
docs-preview.yml PR, docs/**, diagrams/** /pr/<n>/ —

How the two avoid clobbering each other:

  • Both keep concurrency: group: gh-pages, cancel-in-progress: false, so pushes to the branch are serialized. GitHub keeps only one pending run per group and cancels it when another queues, which is why the diagrams don’t have workflows of their own: with four workflows, one merge touching both trees queued several runs and a deploy was silently dropped.
  • JamesIves/github-pages-deploy-action only cleans inside its target-folder, and clean-exclude is relative to that folder. The root deploy is the only one that cleans /, and it excludes the previews. A preview cleans only its own pr/<n>/.
  • .nojekyll comes from docs/public/, so every root deploy writes it again. GitHub manages the root CNAME (see Custom domain). The action never deletes CNAME or .nojekyll, so previews strip .nojekyll from their build: otherwise their removal would leave it behind.
  • docs-preview.yml builds with DOCS_BASE: /pr/<n>/. Astro writes absolute URLs, so a preview needs its own base; diagrams/site.ts writes only relative URLs, so the diagrams work under any base unchanged. A preview shows the PR’s own diagrams, at /pr/<n>/diagrams/.
  • The build runs for fork PRs as well, as a check. Only the deploy, removal and comment steps keep the same-repo condition, since a broken docs link should fail a fork PR too.
  • The preview comment URL comes from gh api repos/$GITHUB_REPOSITORY/pages --jq .html_url, which returns https://docs.gritz.dev/ with the custom domain set.

Moving off the old layout. The diagrams used to have their own deploy to /diagrams/ and previews under /diagrams/pr/<n>/, both excluded from the root deploy’s clean. The first root deploy after the merge replaces the /diagrams/ subtree with the one from the docs build and deletes /diagrams/pr/*; an open PR touching diagrams/ gets its preview back at /pr/<n>/diagrams/ on its next push.

Custom domain.

  • The custom domain docs.gritz.dev is set in the repo’s Pages settings. For a branch-based Pages source, GitHub commits the matching CNAME file to the gh-pages root itself, so the repo doesn’t ship one.
  • After that, gritzapp.github.io/gritz/... redirects to docs.gritz.dev/.... A redirected old diagram URL like /create-task/ will 404. That breakage is accepted.
  • After GitHub has issued the certificate, HTTPS is enforced through the API (gh api -X PUT repos/gritzapp/gritz/pages -F https_enforced=true) or with the checkbox in repo settings.

The one manual step outside the repo is a DNS record in the gritz.dev zone:

It has to exist before the custom domain is set. Otherwise Pages redirects the working github.io URL to a host that doesn’t resolve, and certificate issuance stalls. Verifying gritz.dev for the gritzapp org (a TXT record) protects against subdomain takeover. It’s recommended but not required; see Open Questions.

Embedding diagrams

Section titled “Embedding diagrams”

Docs pages can show diagrams. The diagrams are their own Vite project, built into the docs output (see Hosting), so the docs’ Astro build never bundles Motion Canvas, but a page can play a diagram from the same build.

  • Links. A page links to /diagrams/<slug>/, which is an ordinary Markdown link. It works without JS, in raw Markdown and in llms.txt. base-links prefixes it in a preview like any other root-relative link. The links validator only knows the docs pages, so a link under /diagrams/ is checked against the files in public/diagrams/ instead.
  • Inline player. Diagram.astro renders <figure><motion-canvas-player data-src="<base>diagrams/<slug>/project.js"></motion-canvas-player><figcaption><a href="<base>diagrams/<slug>/">…</a></figcaption></figure> and loads <base>diagrams/controls.js. site.ts gives every project bundle the fixed name <slug>/project.js and the controls controls.js, so the component needs only the slug, and it fails the build when the project doesn’t exist. The player fills the content column and waits for play; its keys work while it or its controls have focus. The controls take their colors from --mc-* properties, which the component maps to Starlight’s, so they follow the light/dark theme; the canvas is the scene’s own and stays dark. Without JS, or in raw Markdown, the reader gets the caption link. Pages that embed a diagram are .mdx. Their raw Markdown keeps the <Diagram slug="create-task" /> line, which an agent can read as a reference.

Agent access

Section titled “Agent access”

  • Static HTML. Starlight renders every page as static HTML. JS is only needed for search (Pagefind), the theme toggle and tabs, and none of these gate any content. The rule: no content may depend on a client-side component.

  • Raw Markdown per page. src/pages/[...slug].md.ts is a static Astro endpoint. It runs getStaticPaths over getCollection('docs') and returns # ${entry.data.title}\n\n${entry.body} with Content-Type: text/markdown. Pages pick the type up from the .md extension.

    • The URL rule: take the page URL, drop the trailing slash, and append .md. For example, https://docs.gritz.dev/integrations/custom-events/ → https://docs.gritz.dev/integrations/custom-events.md. The root page is /index.md.
    • A Starlight Head override adds <link rel="alternate" type="text/markdown" href="….md"> to each page, so a crawler on the HTML page can find the source.

  • llms.txt / llms-full.txt. We adopt starlight-llms-txt. It generates /llms.txt, /llms-full.txt (every page, concatenated) and /llms-small.txt (minified) from the same content collection, and respects site and base. We configure it like this:

    • projectName: 'gritz' and a description that says what gritz is, for the llms.txt header.
    • customSets for Users (everything except operators/**) and Operators (operators/**), so an agent can fetch only the half it needs.
    • promote: ['index', 'concepts/**'], so llms-full.txt starts with the mental model.

    What to check when adopting it (layer 7): llms.txt should link each page’s .md URL as well as the sets. If the plugin’s llms.txt lists only the sets, we turn its llms.txt off and write src/pages/llms.txt.ts, about 40 lines over the same collection, in the llmstxt.org format. Each section heading gets a list of [title](….md): description entries. We keep the plugin’s llms-full.txt and llms-small.txt either way.

  • Every page has a description in its frontmatter. Starlight puts it in the HTML meta tag, and llms.txt uses it for each entry.

Docs through the gritz MCP server (later layer, sketch)

Section titled “Docs through the gritz MCP server (later layer, sketch)”

The server’s user-facing MCP server (internal/server/mcpserver, served at /mcp and proxied by gritz mcp) gets two read-only tools. That way an agent driving gritz can read the docs for the server it’s talking to without leaving MCP.

  • The Markdown is embedded in the binary instead of fetched from docs.gritz.dev. Server, runner and driver ship together, so docs embedded at build time match that server’s version exactly. It also needs no network access and works for air-gapped deployments.
  • A Go package in docs/ embeds src/content/docs. node_modules is never matched, because the embed pattern is that one directory.
  • list_docs returns slug, title and description for every page. That’s llms.txt as structured data.
  • read_doc(slug) returns the same text as the .md endpoint.
  • No search tool at first, because the docs are small enough to list. Revisit if they grow.

How it fits: docs.Pages parses the frontmatter of each embedded file once. AddTools registers list_docs and read_doc, which call docs.Pages and docs.Lookup and never touch the GritzServiceHandler. Before that layer, nothing on the Go side changes.

First content: custom events

Section titled “First content: custom events”

The first pages are integrations/custom-events and reference/custom-event-envelope. Both stay generic: the running example is an alerting system posting an alert type, not any particular vendor. Examples use https://gritz.dev/... URLs, which is the deployment users read about; a self-hosted deployment finds its own URL in the same place in its Web UI.

integrations/custom-events shows how to get events from any system into gritz:

  1. Define a type on Events → Custom Schemas. It has a type name matching ^[a-z][a-z0-9_]{0,63}$, a label, and attrs that must include body and url. The example is alert, with the attrs body, url, severity and service.

  2. Create an API key (/ui/keys/new). The webhook takes it as Authorization: Bearer xat_…. The webhook URL is on Settings → Organisation, in the Custom Events card (GetOrgSettingsResponse.custom_webhook_url). For gritz.dev it is https://gritz.dev/webhook/custom.

  3. POST the envelope (type, body, url, attrs, details; unknown fields are rejected) and read {"routed": n} from the response:

    The key is referenced by variable, so the command can be shared or logged without the value.

  4. Add a public rule for the type: custom/alert, severity equals critical, wake + create in a workspace and runner, with a prompt such as “Investigate this alert and report the likely cause.” Custom events have no actor, so a member-only rule is rejected when saved. Rules are checked in order and the first match wins, so a second, condition-free wake-only rule lets follow-up events (for example a “resolved” post) reach the task without creating tasks for alerts gritz never saw fire.

  5. url is the subscription key. Every event about the same resource must send the same URL, byte for byte, or it won’t wake the task the first event created.

The page ends with a troubleshooting table taken from webhook.go’s errors:

  • 400 unknown type, missing or relative url, undeclared attr, body/url sent as attrs, invalid JSON
  • 401 bad key
  • 403 a token without the event:create scope (for example a task token)
  • routed: 0: no matching public rule, or no subscribed link and no create action

reference/custom-event-envelope is the precise contract: each envelope field and its type, the 1 MiB limit, the response body, and every status code.

Keeping docs in sync with code

Section titled “Keeping docs in sync with code”
  • Same PR. A PR that changes behaviour a user or operator can see (a flag, a workspace field, an envelope field, a routing semantic, an MCP tool) also updates the matching page under docs/. Reviewers ask for it the same way they ask for tests. A new ## Docs section in CLAUDE.md says this, lists which areas map to which docs sections, and repeats the secrets: rule for examples. Agents writing PRs read CLAUDE.md, so they pick the rule up there.
  • The build is the check. docs-preview.yml builds every PR that touches docs/, and starlight-links-validator fails it on a broken internal link or anchor. That catches renamed pages and stale cross-links, but not stale content.
  • Previews make review cheap. The sticky comment links the rendered pages, so a reviewer reads the docs as users will see them.
  • Generated reference later. reference/cli and reference/event-types are handwritten at first. Both have a source of truth in code (the urfave/cli command tree; eventrouter.DefaultSchemaRegistry). Generating them is an open question, not a first-layer requirement.

API

Section titled “API”

Nothing in Go changes until the MCP layer, which is sketched above with its API. The other layers only add docs/, workflows, mise.toml entries, the CLAUDE.md section and the README edit.

Trade-offs

Section titled “Trade-offs”
  • Subtree ownership versus separate branches or Pages artifacts. Only one Pages site per repo is possible. Switching to actions/deploy-pages artifacts would mean every deploy rebuilds the whole site, including all live previews, from a single workflow. Keeping gh-pages with per-subtree target-folder and clean-exclude keeps the root deploy and the previews independent.
  • Docs previews at /pr/<n>/, not /docs/pr/<n>/. Docs own the root, so their previews sit next to it. Prefixing /docs/ would just add path noise.
  • DOCS_BASE versus relative URLs. Astro and Starlight write absolute, base-prefixed URLs. A build-time base is the supported way to serve under a subpath. Rewriting the output to relative URLs, as diagrams/site.ts does, would fight the framework.
  • Raw Markdown as an endpoint, not by copying src/. Copying the sources into public/ would publish frontmatter and the content-collection layout unchanged. The endpoint serves exactly the page set Starlight renders, under the same slugs, with the title as a heading.
  • starlight-llms-txt over a handwritten generator. It’s maintained by a Starlight core contributor, already does the full/small variants and the custom sets, and follows content changes. The only gap we might hit (per-page links in llms.txt) has a small fallback that doesn’t drop the plugin.
  • Embedding docs in the binary for MCP, not fetching from the site. The version always matches, it works offline, and the tools need no HTTP client. The cost is that the binary’s docs are as of its build. Since server and runner ship together, that’s correct anyway.
  • No docs-diff CI gate. A rule like “this PR touches internal/server/customserver but not docs/” would mostly flag refactors. The CLAUDE.md rule plus review is cheaper, and starlight-links-validator catches the structural breakage mechanically.

Open Questions

Section titled “Open Questions”
  • Where is gritz.dev DNS managed, and who adds the record? It’s probably in gritzapp/infra, next to the dokku host. Should we also verify gritz.dev for the gritzapp org (TXT record) to rule out subdomain takeover? That’s a second record, but also outside the repo.
  • Generated reference pages. Should reference/cli (from the urfave/cli tree) and reference/event-types (from DefaultSchemaRegistry) be generated by a go generate step that writes Markdown into docs/, with CI checking that it’s current? Then they can’t drift.
  • Search for agents. Is list_docs plus read_doc enough over MCP, or do agents need a search_docs (over the embedded text) from the start?
