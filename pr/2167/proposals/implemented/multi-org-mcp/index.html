Multi-org gritz mcp

Issue: https://github.com/gritzapp/gritz/issues/2122

Problem

Section titled “Problem”

gritz mcp calls configfile.Resolve once at startup (internal/command/mcp.go), builds one gritzclient for the selected entry, and hands it to mcpserver.AddTools. With --channel it also opens one NotificationClient for that entry. Everything the session does, every tool call and every channel message, is in that one org.

A user with several entries in their merged .gritz.yml files (see Multi-org CLI auth) has to register one gritz mcp per org in their MCP client, which multiplies every tool by the number of orgs, or restart the server with another --org to switch.

Decided in the issue: the session gets tools that list the available orgs and switch the current one, and the existing tools act in the current org. They do not take an org argument. The server’s /mcp endpoint is out of scope: its caller (an OAuth token or an API key) is already bound to one org.

Design

Section titled “Design”

Overview

Section titled “Overview”
  • Two new tools on gritz mcp, list_orgs and switch_org. A --key session has them too: its config is one entry, named "".
  • The session has one current org. Every other tool, the existing task tools and the MCP admin tools alike, acts in it. switch_org replaces the current org’s client with a new one.
  • With --channel, the session follows every org it has used: the startup org, plus each org it switches to. Each channel message carries the org’s entry name as a tag attribute, and mute sets are kept per org.

list_orgs

Section titled “list_orgs”

Lists the entries the session can switch to: merged.Entries(), every entry in the merged orgs that allowed permits, sorted by name, each mapped to {name, id, server, current}. No arguments, ReadOnlyHint.

  • server is the entry’s own server, else https://gritz.dev; never empty.
  • Keys are never returned.
  • The list is the merged files as loaded at startup. An entry added with gritz login while the session runs shows up after a restart.
  • It makes no server call, so it never fails on a stale key; neither does switch_org, so a bad key surfaces on the first tool call after the switch.

This is how the current org is shown: the entry with current: true here, and the result of switch_org. No other tool result names the org; task results already carry a Web UI url with ?org=<id>.

switch_org

Section titled “switch_org”

Makes the named entry the current org.

Argument
name An entry name from list_orgs. Required.
  1. Look the entry up with merged.Lookup(name) on the *configfile.Merged loaded at startup: the same rules as --org at startup, so a name outside allowed or with no entry fails with the same error message.
  2. Build a gritzclient for it from entry.TokenSource(ctx) (see Credentials) with the session’s client id. This makes no server call.
  3. Make the client current. With --channel, start following the org (see Channel notifications).
  4. Return the new current org:

Switching to the current org replaces its client with an equivalent one and is otherwise a no-op.

How the tools pick up the current org

Section titled “How the tools pick up the current org”

mcpserver.AddTools takes a function returning the service instead of the service itself:

Each handler calls it once, at its start, and uses that value for every RPC it makes. Handlers that make several calls (update_task and its follow-up GetTask; the admin tools’ read-modify-write put_custom_event_type, update_schedule, set_routing_rules) therefore stay in one org even if a switch_org runs concurrently. The server’s /mcp handler passes mcpserver.Static(apiServer), so it doesn’t change behaviour; gritz mcp passes OrgSwitcher.Service.

Clients are created lazily, on switch, and only the current one is kept. gritzclient.New builds an http.Client and a Connect client and makes no connection, so there’s nothing worth caching or creating up front; switching back to an org builds a fresh one. One client id (uuid.NewString() at startup, as now) is shared by every client the session builds, so the notification streams filter out the session’s own changes in every org.

Credentials

Section titled “Credentials”

Every client and NotificationClient the session builds gets its credentials from the entry’s token source, entry.TokenSource(ctx), as every command does since CLI OAuth login, never from entry.Key. A key entry gives a static token, and a refresh_token entry exchanges and rotates its refresh token, so both kinds work for the startup org, for switch_org and for Channel.Follow. --key is a static token too.

ctx is the process context, not the tool call’s: the token source outlives the switch_org call that built it, and refreshes the access token on later calls and on each SSE reconnect.

Channel notifications

Section titled “Channel notifications”

Follow every org the session has used. The startup org is followed from the start; switch_org starts a NotificationClient for the new org if it isn’t followed yet. Streams are never stopped before the process exits.

Following only the current org would be simpler, but an agent that creates a task in acme, switches to local and does work there would never hear that the acme task finished, which is what channels are for. Following every entry at startup would open a stream per entry, including entries the user never touches in this session and stale keys that only fail and log. Following the orgs the session has used covers exactly the tasks the agent can have acted on.

Followed orgs are identified by entry name, "" in --key mode. Two entries for the same org (acme and acme-ci) get separate streams and mute sets, so a session that switches between them hears each notification once per entry. That takes two entries for one org and a switch between them, which is rare enough not to need deduplicating.

Telling tasks apart. Task ids are a BIGSERIAL per server, so two orgs on one server never share an id, but the same id can exist on two servers (acme on gritz.dev and local on localhost). Every channel message carries the entry name in mcpchannel.Params.Meta, which Claude Code renders as a tag attribute:

The message text is unchanged. A --key session’s entry is named "", so it sends org="". The attribute is always set, not only once a second org is followed, so the format doesn’t change mid-session.

Mute sets per org. Channel keeps one TaskFilter per entry name. Forward checks the filter of the entry whose stream delivered the notification. channel_mute, channel_unmute and channel_muted take an org argument, an entry name as shown in the org="..." channel attribute, and act on that org’s set, including all=true. --key’s entry is named "", so org can be left out there; an org that isn’t followed is an error result (not following org "x"). Their results gain an org field naming it:

Muting doesn’t depend on the current org, so switch_org doesn’t change which tasks are muted. Mute sets reset when the process exits.

Flags

Section titled “Flags”

The startup selection is unchanged: --key, --org and their env vars resolve as in every other command. Every entry, at startup and on switch_org, uses its own server, else https://gritz.dev.

  • --org / GRITZ_ORG picks the startup current org; otherwise it’s the merged org, and with neither the command fails as now. switch_org can then move to any entry list_orgs shows.
  • allowed limits list_orgs and switch_org exactly as it limits --org. A repo whose .gritz.yml pins allowed: [acme] gets a session that can’t leave acme.
  • --key / GRITZ_API_KEY (with --server, which only applies to --key) is a single raw key: Resolve returns a one-entry config whose entry is named "". list_orgs lists that entry and switch_org can only switch to it, so the session stays in the key’s org.

Instructions

Section titled “Instructions”

gritz mcp appends to mcpserver.Instructions:

This session acts in one gritz organisation at a time. list_orgs lists the organisations and marks the current one; switch_org changes it. Every other tool acts in the current organisation. Check it with list_orgs before changing anything if you’re not sure which organisation you’re in.

/mcp keeps mcpserver.Instructions as is.

Composing with the MCP admin tools

Section titled “Composing with the MCP admin tools”

The MCP admin tools are registered by mcpserver.AddTools, so they get the ServiceFunc and the once-per-call rule with no extra work: list_members, get_org_settings, set_routing_rules, schedules and events all act in the current org. Two consequences:

  • The name list_orgs doesn’t clash with any admin tool, and switch_org stays out of mcpserver: it only exists in the stdio bridge, because /mcp callers can’t switch.
  • The admin tools never create or delete orgs. An org created in the Web UI becomes switchable after gritz login and a session restart.

API

Section titled “API”

gritz mcp calls Resolve as every command does and keeps the *Merged for the session.

How it fits: gritz mcp calls Resolve once, with or without --key, builds mcpbridge.NewOrgSwitcher with an OnSwitch that calls ch.Follow (nothing without --channel), passes switcher.Service to AddTools, calls switcher.AddTools, and appends OrgsInstructions. The NotificationClient setup moves from mcp.go into Channel.Follow. list_orgs maps merged.Entries() to its result, with no second lookup; switch_org calls merged.Lookup, gritzclient.New with Options{TokenSource: entry.TokenSource(ctx)} and OnSwitch; Channel’s tools pick the mute set by their org argument.

Implementation Plan

Section titled “Implementation Plan”
  1. Merged.Entries and the Lookup server default — Delivers: (*Merged).Entries; Lookup sets DefaultServer on an entry without a server, and Resolve stops doing it. Depends on: nothing. Verifiable by: the existing configfile tests pass; tests that Entries filters by allowed, sorts by name and returns each entry as Lookup would (Name set, Server defaulted), and that Lookup keeps an entry’s own server and fills in DefaultServer when it has none.
  2. mcpserver.ServiceFunc — Delivers: ServiceFunc, Static, AddTools taking a ServiceFunc, every handler snapshotting the service once; /mcp and gritz mcp pass Static. No behaviour change. Depends on: nothing. Verifiable by: the existing mcpserver tests pass with Static(mock); one test where the ServiceFunc returns a different mock on each call and update_task sends both its RPCs to the first. Admin-tool slices that land after this one follow the same rule.
  3. Per-org channel — Delivers: Channel.Follow owning the NotificationClient, per-org mute sets, the org meta attribute on .gritz.yml sessions, and the org field in the channel tools’ results; gritz mcp follows only its startup org. Updates the Channels section of integrations/mcp. Depends on: (1). Verifiable by: mcpbridge tests that Forward uses the delivering org’s mute set, that the meta carries the name, that a second Follow for the same entry starts no stream, and that the mute tools edit the set org names.
  4. list_orgs and switch_org — Delivers: mcpbridge.OrgSwitcher, the two tools, OrgsInstructions, the gritz mcp wiring, and following each switched-to org. Updates integrations/mcp (a section on orgs, the tool table). Depends on: (1), (2), (3). Verifiable by: mcpbridge tests for switch_org (the switched-to entry becomes current and is followed, list_orgs marks it; an unknown entry leaves the current org); an e2e test that logs in to two orgs, starts gritz mcp --channel in-process, creates a task in org A, switches to org B and creates a task there; then list_tasks shows only org B’s task, and cancelling the org A task from another client delivers its channel message with org="a".

Slices 1 and 2 are independent.

Trade-offs

Section titled “Trade-offs”
  • Switch tools vs. an org argument on every tool. Decided in the issue. An argument on 30-odd tools costs context on every call and has to be threaded through every handler; a current org costs one tool call per switch and the risk of acting in the wrong org, which list_orgs, the switch result, the instructions and the ?org= in task URLs keep visible.
  • Follow used orgs vs. only the current one vs. all. See Channel notifications: current-only loses completions of tasks the agent started; all-entries opens streams nobody asked for. Used orgs costs one stream per org switched to, never torn down.
  • org as a tag attribute vs. a prefix in the text. Meta is what the channel protocol offers for structured context, and it leaves the message text and its tests unchanged.
  • Fresh client per switch vs. a client cache. Clients hold no connection state worth keeping; a cache would be a map with no benefit.
  • Trusting the entry vs. GetCaller on switch. A round trip per switch would catch a dead key before the first real call, and a key that belongs to another org than the entry’s id. gritz login already records the id from GetCaller, so the entry is trusted and a switch makes no server call; a dead key fails the first tool call instead.
  • Snapshot of .gritz.yml at startup vs. reloading on each call. Reloading would pick up gritz login without a restart, but would let the current entry’s key or allowed change under a running session. Logins are rare; a restart is fine.
  • Startup error vs. starting with no current org. A session with no merged org and no --org fails at startup, as today, rather than starting with only list_orgs and switch_org working until the first switch.
  • No org field on state-changing results. Results stay unchanged; list_orgs, the switch_org result and the ?org= in task URLs show the current org.
