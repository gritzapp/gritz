End-to-end tests on a local backend

Issue: https://github.com/gritzapp/gritz/issues/1890 (related)

Problem

Section titled “Problem”

No test runs the server, the runner and the driver together. The apiserver tests (internal/server/apiserver/*_test.go) use a real Postgres store but stop at the RPC handlers. The runner tests (internal/runner/*_test.go) run a real TaskManager, but against testrunner.Server, an in-memory stand-in for ListRunnerEvents, and a gritzclient.ClientMock that accepts every runner event and reports every task COMPLETED. Their sandboxes come from backend/fake, and the drivers are either real driverservers served in-process by testrunner.NewDriver (with their own ClientMock) or scripted stubs. The only test that uses a real backend, TestTaskManagerStart, needs a Docker daemon and still talks to a mocked server.

The bugs that matter live in the seams between those pieces. The run boundary in #1868 was a server bug that only showed up once the runner consumed the server’s command events. Neither side’s tests could see it, because each side tested against its own idea of the other. The runner-event-replica work (proposals/implemented/runner-event-replica.md) moves behaviour across those seams one slice at a time, and each slice has rebuilt the test plumbing to keep the existing tests passing. #1890 lists what that has left behind: testrunner grown piecemeal, polling helpers that only exist for intermediate designs, follower and handled tests that slices 8–9 make obsolete, and driverserver and fake backend tests reworked twice.

The many small runner tests are also hard to trust. They assert on WaitHandled, the outbox’s length, fake-backend counters (Boots, Runs) and AssertTracked’s probe Boot, which is the runner’s internal bookkeeping rather than what a user sees. When the runner’s design changes they all change with it, so they don’t tell us whether behaviour survived the change.

We want a few real end-to-end tests over many small, questionable ones. They should exercise the real server, runner and driver, use fakes only where there is no other way, and assert only what a user can observe. Then we want to port the existing tests onto them and delete what they cover.

Design

Section titled “Design”

Only two things are fake:

  • The sandbox is a directory on the runner host, and the driver is an ordinary child process. The local backend provides it.
  • The agent is a new puppet agent (below). It has no behaviour of its own: it forwards each Prompt call to the harness, and the test decides when and how the run ends.

Everything else is production code: the apiserver behind its real auth, the runner’s real wiring on its own SQLite runner.db, the prebuilt driver binary the Docker backend ships, the real driver.v1 transport over a Unix socket, the injected gritz MCP server, log shipping and secret masking.

The driver is a black box. It has no public API of its own: the runner and the API server configure it, and the harness has no handle on it and no mocks of it. Tests see it only through its effects:

  • the files its setup commands write in the sandbox directory;
  • the runs it gives the agent: each Prompt call, with its prompt, and whether it is cancelled;
  • what it reports to the server: runner events with their versions, log chunks, and the events its tool calls create.

Tests interfere with it only from outside: its calls to the server through h.Server.Mock, and its sandbox through h.Backend, including KillDriver.

Faults are injected at the seams, with moq mocks rather than hand-written fakes. A mock installed on the server or the backend replaces the methods it sets, for every caller, until it is removed. Every other method reaches the real implementation.

Local backend

Section titled “Local backend”

internal/runner/backend/local implements backend.Backend by using the runner host as the sandbox, with no isolation. It is for tests and development (gritz runner --backend local), never for running untrusted agents.

Each sandbox is a directory Root/<task id>. The handle is backend.Handle{Type: "local", ID: "<task id>"}, so the harness can find a task’s directory without reading the runner’s records. Naming by task id mirrors Docker’s gritz-<task id> container names.

Operation Local backend
Create mkdir Root/<id> (fails if it exists, as a Docker name clash does). Nothing is copied: the driver binary is run in place.
Boot No-op if up; ErrGone if the directory is missing. Otherwise starts Binary driver --addr unix://DIR/gritz/driver.sock --prefix DIR as a child process and writes its pid to DIR/gritz/driver.pid. The process runs with working directory DIR and environment Environ plus HOME=DIR/home, in its own process group (Setpgid), with stdout and stderr appended to DIR/gritz/driver.out. Boot returns once the process has started; driver readiness stays the runner’s job, as with Docker.
Dial A driver client over the socket: unencrypted HTTP/2 with prior knowledge and the JWT as bearer, the same transport the Docker backend uses minus the exec tunnel.
Suspend SIGTERM to the driver, which stops its run and reports it, as docker stop does. Waits for it to exit, then SIGKILLs the process group after suspendTimeout. The directory stays, so the next Boot finds the driver’s files where it left them.
Destroy SIGKILL the process group, then remove the directory. A missing directory is not an error.
Kill (local only) SIGKILL the process group and leave the directory. Not part of backend.Sandbox; h.Backend.KillDriver uses it to produce a real lost run.
Status gone if the directory is missing; up if the pid file names a live process whose /proc/<pid>/cmdline carries --prefix DIR; suspended otherwise.
Open Rehydrates from the handle, with no I/O.
Close Does nothing. Drivers outlive the backend, as containers outlive a Docker client.
ValidateWorkspace Accepts every workspace. The local backend reads no runtime section (container:, lambda_microvm:).

Who reaps the driver. Boot starts a goroutine that Waits for the process and then removes the pid file. That goroutine belongs to the OS process, not to the Backend value, so after h.Runner.Restart() the old backend’s goroutine still reaps a driver that a new backend instance in the same test process suspends. A zombie therefore never looks up. In development, a restarted gritz runner process leaves its drivers to init. They are in their own process group, so a Ctrl-C to the runner doesn’t reach them, and the new runner finds them through the pid file.

Socket path length. A Unix socket path is limited to 107 bytes, and t.TempDir() paths with long test names exceed that. New rejects a Root whose longest socket path would be too long, and the harness puts its root under os.MkdirTemp("", "gritz-e2e-") rather than t.TempDir().

The injected MCP server’s binary. The runner points the injected gritz MCP server at backend.BinaryPath (/usr/local/bin/gritz), which is where Docker copies the binary and where the Lambda image has it (TaskManager.spec). On the local backend the binary is wherever Options.Binary says. A new method on backend.Backend lets every backend say where; Docker and Lambda return backend.BinaryPath:

TaskManager.spec uses it for McpServer.Command.

Most of this already exists. driverserver.Options and ExecutorOptions have RecordPath, EventsPath, LogPath, Config and FileRoot, but only the tests set them (testrunner.NewDriver and driverserver_test.go’s setup), and they build the same layout by hand. These five options are replaced by one:

gritz driver gains --prefix to set it. It is only a path prefix, not a chroot: nothing is isolated. A sandbox’s paths are its in-container paths under PrefixPath, so the runner keeps sending absolute paths in RunSpec.files and needs no change. Docker and Lambda keep the default /.

The puppet agent

Section titled “The puppet agent”

The test needs per-run control of what the agent does: keep run 1 going until the test has cancelled it, let run 2 finish, make run 3 fail. Doing that with scripts (a fenced block in the instructions that the dummy agent parses and runs) or with timed sleeps makes scenarios depend on timing and on a script format, and the dummy’s workspace-level DummyOptions can’t vary per run at all.

Instead, a new agent type, puppet, has no behaviour of its own. It forwards each Agent.Prompt call to the harness, and the test answers it. It lives in its own package, internal/runner/agent/puppet, which holds both sides: the client puppet.Agent the driver runs, and the puppet.Server the harness serves. The package doesn’t import agent; agent.NewAgent builds a puppet.Agent for TypePuppet, and agent.Config holds *puppet.Options.

  • One HTTP request per Prompt. The workspace points the puppet at the harness (agent: puppet: url: …). Under the local backend the driver runs on the runner host, so it can reach an httptest endpoint in the test process. Prompt(ctx, prompt, resume) posts {task_id, prompt, resume}, with the task id from GRITZ_TASK_ID, and holds the request open until the harness replies with success or an error message. Prompt returns nil or that error.
  • Each request is a puppet.Run. puppet.Server queues a task’s runs in arrival order and holds each open until Complete or Fail answers it, or until the request’s context ends, which closes Cancelled(). Close fails every open run (and any that arrive later), so drivers can shut down.
  • Cancellation is the request ending. When the driver cancels ctx (a stop, a restart, a shutdown), the request is aborted and Prompt returns an error wrapping context.Canceled, as the Agent contract requires. The server sees the request’s context end and closes the run’s Cancelled(). A killed driver closes the connection, which the harness sees the same way.
  • Runs are identified by order. Prompt carries no run version, and nothing else exposes one to the agent. The harness queues a task’s runs in the order they arrive; the task’s version is checked through the API (COMPLETED at v2), not through the agent.
  • No tool calls. The test answers in the test process, which can’t reach the injected gritz MCP server inside the sandbox. Calling a tool from a run is a possible later command on Run (Open Questions).
  • The driver stays a black box. The puppet is just the agent the real driver runs; nothing reaches into the driver.
  • The dummy agent is unchanged and keeps its existing uses.

The test side is h.Agent (below): h.Agent.WaitRun(taskID) returns the task’s next run, and the run stays open until the test ends it with Complete or Fail, or the driver cancels it. “Cancel mid-run” is therefore guaranteed to be mid-run, and the prompt each run received is captured for assertions.

Harness

Section titled “Harness”

internal/e2e stands the system up per test; it holds only the harness and its own tests. The tests built on it live in two test-only packages beside it: internal/e2e/api for the API tests (one file per area, such as task_test.go or taskscope_test.go) and internal/e2e/scenario for the runner scenarios (one file per area, such as start_test.go or faults_test.go). A Harness exposes one handle per component it owns:

The runner is opt-in. Options.Runner (a *RunnerOptions) turns on the backend, the runner and the agent. Without it, h.Backend, h.Runner and h.Agent stay nil and the harness is a server and its orgs. Server-only tests (scope checks, the RPCs’ own behaviour) leave it off and act as the runner themselves with Org.SubmitRunnerEvents, on the org’s runner key. A test must not do both: with the runner on, hand-submitted runner events race the real runner’s, so a test that enables the runner reaches every status through it.

Org isn’t a component but a caller: an org and the user who owns it, with that user’s client. Tests that need several orgs on one server (permissions, cross-org, org membership) create more with h.Server.CreateOrg().

Each handle holds t, and its methods fail the test with t.Fatal instead of returning errors. None of them exposes its real instance. The escape hatches go through the same path as everything else:

  • h.Org.Client is a real API client, and h.Server.Client(token) makes one for any other credential.
  • h.Backend is itself a backend.Backend.
  • Mocks (h.Server.Mock, h.Backend.Mock, h.Backend.MockSandbox) replace methods for every caller, and apply to those escape hatches too.

There is no driver handle (see above).

Setup and teardown

Section titled “Setup and teardown”

e2e.New(t, opts) builds the following, and tears it all down with t.Cleanup:

  1. Server. server.New(server.Options{...}).Handler() on httptest.NewServer, over teststore.New(t). It uses apiauth.New with server.NewStoreKeyValidator, a fresh app key from apiauth.CreateAppPrivateKey() (user and task tokens), and a local pubsub feeding notifyserver, so SSE notifications are live. apiauth.New gets a DevUser, as --no-auth does, so it skips OIDC discovery; like the --no-auth dev user it has no org and no scopes, so a request without a token is authenticated but allowed nothing. h.Server’s mock router goes in server.Options.Wrap. The archiver and scheduler aren’t started; no scenario needs them.
  2. Default org. h.Server.CreateOrg() makes h.Org (below). Isolation comes from the org, as for every teststore test.
  3. Agent (only with Options.Runner). A puppet.Server on its own httptest.NewServer, behind h.Agent.
  4. Backend (only with Options.Runner). A local.Backend on a fresh root, wrapped by h.Backend, running prebuilt/gritz-linux-$GOARCH. The runner is given the wrapper.
  5. Runner (only with Options.Runner). runner.Serve (below) with a gritzclient on h.Org’s runner key, the backend wrapper, runner.db in a temp directory, runner id e2e, and one workspace e2e whose agent is the puppet, pointed at h.Agent’s endpoint, with RunnerOptions.Commands and Secrets. The runner registers that workspace with the server itself (RegisterWorkspaces), so CreateTask finds it through the production path. The runner subscribes to the harness server’s notifications, so commands reach the runner without waiting for the poll.
  6. Cleanup, in reverse order: remove the mocks; fail every run the test left open; stop the runner and wait for it; Destroy every sandbox under the root, which kills the drivers; remove the root; close the agent’s endpoint and the server; teststore drops the org. Without Options.Runner only the mocks and the server are torn down.

runner.Serve (internal/runner/serve.go, landed in #1912) is gritz runner’s wiring. It builds the runnerstore, taskevents.Log, RunnerEventOutbox and TaskManager, then runs RegisterWorkspaces, Load, the outbox, the notification client and Run, in that order. The command keeps flag parsing, config loading and backend selection, and calls Serve; the harness calls the same function, not a copy of it. Serve returns when ctx ends and leaves sandboxes up, as a shutdown does today. Before h.Runner.Restart() can call it again on the same runner.db, Serve must also wait for the outbox and notification goroutines it starts, which it doesn’t yet (slice 5).

One harness per test. Each harness has its own org, server, runner, runner.db and sandbox root, so tests can call t.Parallel(). They share one Postgres. The xid watermark is cluster-wide, so another test’s open transaction can delay this test’s events for as long as that transaction stays open. That is real behaviour, and short transactions bound it.

Org

Section titled “Org”

An org and its owner. CreateTask, WaitTask and WaitEvent live here rather than on h.Server because they act as a caller, and the caller decides what is visible.

Users are explicit: a Member is a user acting in an org, with UserID, Email, a Client and, when AddOrgMember added it, the Resp. Users come from orgs. Every CreateOrg provisions a user with a unique email, so a test adds another org’s owner by email; there is no separate user-provisioning method:

Shorthand methods mirror their RPC. A method that is one RPC takes that RPC’s request, so a test can set any field and the harness never grows parameter lists. It returns what the test works with: a wrapper when there is behaviour to attach (*Task, *Key, *TaskToken and *Member with their Client), otherwise the unwrapped value (the task, the keys). A wrapper built from one RPC carries that RPC’s response in Resp (Task.Resp is the CreateTaskResponse, Key.Resp the CreateKeyResponse, TaskToken.Resp the CreateTaskTokenResponse, Member.Resp the AddOrgMemberResponse), so a test can reach anything the shorthand didn’t pick out. A *Key from CreateScopedKey has a nil Resp, since no RPC made it, and neither has an org’s Owner. Methods that aren’t a single RPC (CreateScopedKey, WaitTask, WaitEvent, Server.CreateOrg) keep their own shapes.

Setup goes through methods; Client is for the call under test. A call that arranges the test, or reads state to assert on, goes through an Org (or Server) method that returns the useful value and fails the test with t.Fatal itself. A test calls Client directly only for the call under test, whose result or error it asserts. Methods are added when a test first needs them, not ahead of it.

A Member’s Client carries the app JWT /auth/token issues the web UI (apiauth.NewAppClaims, signed with the harness’s app key), not a key: keys carry no user, and the org and profile RPCs act on the caller’s user id. The JWTs live for apiauth.AppTokenTTL (5 minutes), which bounds a test’s length.

The runner registers its workspaces with the server (below). h.Org’s runner key is the one the runner is given; it stays internal. Without Options.Runner (and until h.Runner lands), CreateOrg registers the DefaultWorkspace on DefaultRunner itself with that key, so every org can CreateTask, and Org.SubmitRunnerEvents uses the same key to act as the runner.

The mock type. gritzclient.Client is gritzv1connect.GritzServiceClient, and buf.gen.yaml generates with connect’s simple option. The client and handler interfaces therefore have the same 52 methods, with the same request and response types (SubmitRunnerEvents(context.Context, *v1.SubmitRunnerEventsRequest) (*v1.SubmitRunnerEventsResponse, error) in both). So the existing gritzclient.ClientMock (client_moq.go) already implements GritzServiceHandler, and Mock takes it. No new mock is generated.

How it works:

  • A router, not an interceptor. An interceptor can’t answer for a mock: it would have to return a *connect.Response[Res], connect.NewResponse is generic, Res is only known by reflection there, and connect.AnyResponse can’t be implemented outside connect. So Mock is backed by a router that wraps the RPC implementation instead. server.Options.Wrap hands the harness the apiserver, and the harness returns a ClientMock whose every <Method>Func is a reflect.MakeFunc that routes the call. The wrapped implementation sits behind the Connect interceptors and the /mcp endpoint, so callers are still authenticated, and a bad token is still rejected, before a mock answers. Authorization is not: scopes are checked inside each handler (AllowOp, Allow), so a mocked method answers callers the real one would deny.
  • Routing. For each call, the router checks the installed mock’s <Method>Func field by reflection. That is fine in test code, and keeps working as RPCs are added.
    • If the field is set, the router calls the mock’s method, SubmitRunnerEvents(ctx, req), and the generated handler wraps its result.
    • Otherwise it calls the real handler.
  • Typed, with no generics. Each <Method>Func has the method’s real request and response types, so a mock needs no type assertions.
  • Replace, not wrap. A mocked method replaces the real one for every caller (the runner, the driver, the injected MCP server and the test itself) until the mock is replaced or removed. It doesn’t call the real method; there is no next. To make a call fail once and then behave, the test calls h.Server.Mock(nil) once it sees the failure in m.<Method>Calls(), and the real method answers again. Call-through is a possible later addition (Open Questions), not part of this design.
  • The harness’s own calls too. Task methods and the waits use the org’s Client, so they see the mock as well. WaitTask reads GetTask, so a test that mocks GetTask removes the mock before waiting.
  • Free call recording. The router calls the mock’s method, not the bare Func field, so m.<Method>Calls() records every request sent while the mock was installed, whoever sent it.
  • One mock at a time. Mock returns nothing. A second Mock(m2) replaces the first, and it is m2’s methods that are mocked from then on. A test that wants to change one method copies the fields it keeps. Cleanup removes any mock still installed.
  • Streaming RPCs. GritzService has none today (/events SSE is plain HTTP), so there is nothing to mock. With simple, a streaming method’s client and handler signatures differ (*connect.ServerStreamForClient[Res] versus a *connect.ServerStream[Res] argument), so ClientMock won’t fit one. See Open Questions.

h.Backend

Section titled “h.Backend”

h.Backend is a backend.Backend, and it is what the runner is given. It wraps the local.Backend, which it doesn’t expose: like h.Org.Client, the handle itself is the escape hatch (h.Backend.Open(handle)), and it goes through the same mocks the runner sees. Its Create and Open return wrapped sandboxes, so mocks also apply to sandboxes the runner restores at Load.

Method What it does
Dir(taskID) the task’s sandbox directory, Root/<id>
WaitSandbox(taskID, state) polls the sandbox’s Status() until it is backend.StatusUp, StatusSuspended or StatusGone. A task that never had a sandbox reports gone
KillDriver(taskID) SIGKILLs the driver’s process group through local.Backend.Kill, leaving the directory: a real lost run
Mock(m) installs m, replacing any previous mock: the Backend methods whose <Method>Func is set (Create, Open, ValidateWorkspace) go to it. Mock(nil) removes it
MockSandbox(taskID, m) replaces the methods of the task’s sandbox whose <Method>Func is set (Boot, Dial, Status, Suspend, Destroy, Handle), replacing the task’s previous sandbox mock; MockSandbox(taskID, nil) removes it. It applies to whichever sandbox the task has or gets, created or opened

These use the moq mocks backend already generates (backend_moq.go), with the same rules as h.Server.Mock: a mocked method replaces the real one, there is no call-through, a new mock replaces the previous one, nil removes it, calls are recorded, and cleanup removes any mock left installed. There are only a handful of methods, so the wrapper checks each Func field directly rather than by reflection. Backend operations are plain calls with no streams, so there is no streaming question here.

h.Runner

Section titled “h.Runner”

Restart() stops the runner and waits for runner.Serve to return. It then starts a new one on the same runner.db and the same h.Backend, so installed mocks stay in place.

The runner has no escape hatch. No client path leads into it, and its internals are what the tests must not depend on. If a setup need appears that only the runner can meet, one can be added then.

h.Agent

Section titled “h.Agent”

The test’s side of the puppet agent, a thin wrapper over puppet.Server that fails the test where the server returns errors. Every Prompt call the puppet forwards is a Run, queued per task in arrival order and held open until it ends.

Method What it does
WaitRun(taskID) waits for the task’s next run, the first one no earlier WaitRun returned, and returns it. A second WaitRun returns run 2
Runs(taskID) every run the task has had so far, in order, without waiting: cmp.Len(h.Agent.Runs(id), 1) asserts that no second run happened
Run What it does
Prompt, Resume the arguments the driver passed to Prompt
Complete() ends the run: Prompt returns nil
Fail(msg) ends the run: Prompt returns an error with msg
WaitCancelled() waits until the driver cancels the run (its request ends)

Complete and Fail fail the test if the run has already ended. A run the test never ends stays open until the driver cancels it, or until cleanup fails it so the drivers can shut down. Further commands, such as calling a tool from the run, are later methods on Run.

Task

Section titled “Task”

A Task holds its Org and the task id. Its methods are implemented through the org’s Client and h.Backend, and the commands go through the RPCs the web UI uses (webui/src/routes/tasks.$id.tsx, tasks.new.tsx):

Method Through
Update(req) UpdateTask, with req.id filled with the task’s id
Cancel(), Restart(), Archive(), Unarchive() CancelTask, RestartTask, ArchiveTask, UnarchiveTask
Get(), Events() GetTask; ListEventsByTask, every page
Links(), Log() ListLinks; ListLogChunksByTask, concatenated
WaitStatus(status) Org.WaitTask
WaitEvent(match) Org.WaitEvent
ReadFile(name) a file in h.Backend.Dir(id), as the workspace’s setup commands wrote it

A scenario creates a started task with h.Org.CreateTask and its Instructions, as the new-task page does. A wake or restart is one Update{start: true, add_instructions: ...}, as the composer sends it. A task that must start later, such as one whose sandbox is mocked by task id, is created with Draft: true and started with Update{start: true}. Driving the agent’s runs is h.Agent.

Waits and assertions

Section titled “Waits and assertions”

Waits poll every 20ms until Options.Timeout (default 30s), then fail through t with the last state they saw:

  • WaitTask reports the status, version and command, plus the last few events.
  • WaitEvent reports every event.
  • WaitSandbox reports the last status.
  • WaitRun reports the task’s runs so far and the task’s status.
  • WaitCancelled reports the run’s prompt and the task’s status.

Only observable outcomes. Tests assert on:

  • task status and version;
  • the event timeline, links and the shipped log;
  • sandbox state through the backend;
  • the runs the agent got, and their prompts;
  • the files the setup commands wrote.

Tests never open runner.db or call into the driver. The driver’s own files in the sandbox directory (gritz/run.json, gritz/events.jsonl, gritz/log) are its internals, so tests don’t read them either. This is what lets the tests survive runner-event-replica slices 9–11 unchanged.

Options:

Everything that only means something with a runner is in RunnerOptions, so a test can’t set it without turning the runner on. &e2e.RunnerOptions{} is a runner with defaults. The harness sets the runner’s LostTimeout and ReadyTimeout (runner.ServeOptions) to 2s, so scenarios about lost or unready drivers don’t wait out the 10s defaults.

The driver binary is prebuilt/gritz-linux-$GOARCH, which the tests already require (mise run build, as TestTaskManagerStart and the Docker backend tests do). A developer who changes the driver and runs the scenarios without rebuilding tests the old driver; that is accepted (Trade-offs).

Porting the existing tests

Section titled “Porting the existing tests”

The categories:

  • (a) Covered. A scenario covers it. Delete it once the scenario lands.
  • (b) Keep. It covers tricky local logic that end-to-end tests can’t pin precisely or can’t reach (broken disks, encoding edge cases). Keep it as a focused unit test.
  • (c) Intermediate. It tested a design that runner-event-replica slices 9 and 11 removed. Where the behaviour lives on, a scenario takes over.

runner-event-replica has landed (slice 10, suspend_after, was split out into #1888), and so have the scenarios below except TestSuspendAfter* and TestRestart_CancelledBeforeStart. The port pass deleted every (a) and (c) test that a scenario on master covers, after reading each one against its scenario. A test whose scenario isn’t written, or that a scenario doesn’t really cover, was kept; the tables say why. “Deleted” names the covering scenario; “kept” gives the reason.

Two checks went into the “really covers” calls. Running the scenarios with -coverpkg=./internal/runner/... showed which TaskRunner paths they reach: the runner never reports stopped itself (next’s stop branch), it reopens a stream after an early Idle only in about two of five runs of TestRunnerRestart_PendingWake, and it never sees a driver that ran a version it didn’t boot for. The driver runs as a separate process, so its code isn’t measured: those calls come from reading the scenario. For example, a wake mid-run is a start at the version already running, which the driver must ignore. That is the stale-start rule, and TestWake_MidRun would see a third run if it broke.

API

Section titled “API”

CLI: gritz driver --prefix DIR. gritz runner --backend local --local-root DIR, where the local backend’s binary is the running executable.

How it fits:

  • Setup. e2e.New serves server.New(...).Handler() on httptest, with h.Server’s mock router in Options.Wrap, and creates h.Org and its keys in teststore. With Options.Runner, it serves h.Agent’s endpoint, wraps a local.Backend on a fresh root in h.Backend, and runs runner.Serve with that wrapper on a goroutine.
  • The runner. gritz runner calls Serve after parsing its flags. The runner’s TaskRunners create and boot local sandboxes through h.Backend and its mocks. Boot starts gritz driver --prefix DIR from prebuilt/.
  • Inside the sandbox. The driver resolves every path under --prefix, runs the setup commands, and prompts the puppet agent, which forwards the Prompt to h.Agent and returns whatever the test answers.
  • Every call to the server comes from the harness’s Client, the runner, the driver or the MCP server. Each passes the mock router, which sends it to the installed ClientMock or to the real handler.
  • The test drives tasks through Task, which calls the user-facing RPCs and reads the sandbox directory through h.Backend, and drives the agent’s runs through h.Agent.

Trade-offs

Section titled “Trade-offs”
  • The Docker backend instead of a local one. It is more realistic, but it needs a daemon in CI, takes seconds per container (#1859: ~9.5s to boot four), and its isolation is exactly what the scenarios don’t test. The Docker backend keeps its own contract tests. The local backend runs the same prebuilt driver binary, so only the container boundary is missing.
  • An in-process driver (as testrunner.NewDriver does). It is faster, but it can’t die, be suspended or survive a runner restart the way a process does. It shares the test’s HOME and working directory, and it never runs the gritz driver command or the socket transport. TestRunnerRestart_MidRun and TestDriverDies_MidRun need a real process.
  • A Driver handle, or mocks of the driver. These would reach the driver’s internals, which runner-event-replica keeps moving, and the driver has no public API to wrap. Everything a driver can see go wrong reaches it from outside, through the server’s RPCs and the sandbox, so mocks there can inject every fault without opening it up.
  • Hand-written fakes for fault injection (backend/fake, testrunner.Server). A fake restates the real component, and drifts from it. A moq mock replaces only the methods a test sets, for only as long as it is installed. It is generated, so it can’t drift, and it records its calls.
  • Untyped hooks with call-through (a next handler, connect.AnyRequest). Hooks would need a type assertion each and a second, untyped API next to the mocks the repo already generates. Mocks are typed with no generics. Their only loss is call-through, which “remove the mock once the failure is seen” covers for every scenario but a stream cut mid-flight.
  • Exposing the real instances (Real on each handle). Tests that hold the apiserver or the backend directly bypass the mocks, and drift towards asserting on internals. h.Org.Client and h.Backend itself give the same reach through the same path every other caller takes.
  • testrunner.Server and ClientMock instead of the apiserver. They miss command events, the xid watermark, the run boundary and the server’s version guards: everything #1868 was about. They also make every test restate the server’s behaviour, which is how the two sides drifted apart.
  • The dummy agent running a script from its instructions (a fenced block of steps such as sh, sleep, block, tool, error). It gives per-run behaviour through the real prompt path, but scenarios then depend on timing (sleeps, polling files to know where a run is) and on a script format shared by the test and the agent. The puppet gives the same per-run control explicitly, with no timing.
  • The dummy dumping its prompts to a file. Enough to assert which instructions reached which run, but it can’t control how long a run lasts or how it ends. The puppet captures prompts as well.
  • The workspace-level dummy config (DummyOptions). Fixed per runner, so run 1 and run 2 can’t differ.
  • A puppet driven by a command protocol (it reports each run, then long-polls the harness for commands such as “call this tool”, “complete”, “fail”). It could call tools from inside the sandbox, but it is a second protocol to design and keep in step with the test API. Forwarding Prompt as it is called needs no protocol beyond the call itself, and new commands can still be added to Run when a scenario needs one.
  • GRITZ_RUN_VERSION in every run’s environment, so the agent can report which run version it is in. It would let the harness tell a repeated v1 run from a new v2, but it puts a variable in every real agent’s environment for the tests’ sake. Runs are identified by order instead, and the task’s version is checked through the API.
  • Building the driver per test run (go build once per test process, on the first runner-enabled harness) instead of the prebuilt. The driver under test would always be the current source, but it departs from how every other test gets its binaries (mise run build). The prebuilt is used, and a stale one is the developer’s to rebuild.
  • Asserting on runner internals (runner.db, fake-backend counters). That is more precise, but those are exactly the assertions that churn with every runner-event-replica slice. Observable state is what has to survive them.
  • A harness-local copy of the runner wiring instead of runner.Serve. It is less churn now, but it would drift from gritz runner, and the harness would stop testing the real assembly order (RegisterWorkspaces before Load, Load before Run).

Open Questions

Section titled “Open Questions”
  • Tool calls from a run. The puppet answers in the test process, so a run can’t call the injected gritz MCP server, and TestTools (the injected server, the task token, the Backend.BinaryPath() path) has no scenario. A later Run.CallTool(name, args) would need the puppet to receive the command and call the tool inside the sandbox, which brings back a small command protocol. Add it when a scenario needs it, or cover the injected server elsewhere?
  • A run that outlives its cancellation. TestRestart_CancelledBeforeStart needs run 1 to keep going after the driver cancels it, so a cancel can land before run 2 starts. (TestRunnerRestart_RestartCancelled reaches the same state by stopping the runner before the restart and the cancel, which covers the runner’s side without this.) The puppet’s Prompt returns as soon as ctx is cancelled. A later Run method could hold the return until the test releases it (the request would then stay open after cancellation, and the puppet would report the cancellation instead of aborting). Worth it for one scenario?
  • Call-through. A mocked method replaces the real one. Some cases need to wrap the real one instead, for example a submit that fails only for stopped. (Cutting the real Run stream mid-flight didn’t need it: Backend.CloseRunStream wraps the client Dial returns.) Would a later Mock option make the real implementation reachable from the mock, for example a Real passed to the Func?
  • Streaming RPCs. GritzService has none, so Mock covers every RPC today. With connect’s simple option, a streaming method’s client signature (it returns a *connect.ServerStreamForClient) differs from its handler’s (it takes a *connect.ServerStream), so ClientMock can’t stand in for one. When the first streaming RPC arrives, either generate a moq mock of gritzv1connect.GritzServiceHandler for Mock to take instead (its fields then carry the handler’s streaming signatures, which WrapStreamingHandler can route to), or leave streaming RPCs unmockable until a scenario needs one.
  • Gaps from porting driverserver. Keep-alives matter only for streams quiet for longer than the runner’s 45s idle timeout, and no scenario is that slow. Provisioning failures are unreachable from outside. The port pass kept TestRun_KeepAlive and TestRun_ProvisionFailure for now. Accept both gaps in the delete pass, or add one slow scenario (skipped under -short) for keep-alives?
  • Amending runner-event-replica. Slice 9 and 10’s “Verifiable by” lists name runner_test cases on the fake backend. Should that proposal be edited to point at the scenarios once slice 7 here lands?
  • gritz runner --backend local for users. It runs agents with the runner’s own privileges and filesystem. Should the flag be hidden, or refuse to start without an explicit --local-unsafe-style acknowledgement?
  • Workspace environment on the local backend. It ignores container:, so container.environment doesn’t reach the run. Secrets and setup commands cover the scenarios; should the local backend apply container.environment through RunEnv, as Lambda applies its section?
  • CI time. About thirty scenarios of a few seconds each, run in parallel, should add about a minute. If the suite grows, should it get its own mise task and CI job?
