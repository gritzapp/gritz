MCP

gritz is an MCP server, so the agent you work with locally, such as Claude Code or Cursor, can hand work off to gritz: list the workspaces, create tasks, follow them up with instructions, read what they did, and archive them.

There are two ways to connect:

  • Over HTTP, to /mcp on the server. Nothing to install; you sign in with your browser. Use this unless you need channels.
  • Locally, with gritz mcp. Your client runs the gritz binary, which talks to the server with an API key. It is also the only way to get channels: task updates pushed into a Claude Code session.

Both offer the same tools, and act in one organisation.

This page is about the tools you use to drive gritz. The tools gritz gives the agents running inside tasks are in Agent tools.

Connect over HTTP

Section titled “Connect over HTTP”

The server’s MCP URL is on Settings → Organisation, in the MCP Server card: https://gritz.dev/mcp for gritz.dev. It uses the Streamable HTTP transport.

Other clients

Section titled “Other clients”

Give the client the URL. gritz supports the MCP authorization flow: OAuth 2.1 with PKCE and dynamic client registration, so a client that supports it registers itself and needs no client ID.

Signing in

Section titled “Signing in”

When the client first connects, it opens gritz in your browser. Sign in if you aren’t already, check the organisation in the selector at the top, and click Approve on the Authorize Application page. The page shows the account and organisation the client will act as.

The client then acts as you, in that organisation: it sees and changes what you can there. To use another organisation, switch to it in the Web UI, and sign the client in again.

The client keeps its access by refreshing its token. It loses it if it isn’t used for 30 days, if you leave the organisation, or if the organisation is deleted; sign in again then.

Connect with gritz mcp

Section titled “Connect with gritz mcp”

gritz mcp is a local MCP server over stdio. Your client starts it, and it forwards each tool call to the server’s API with an API key. Install the CLI, create an API key on the Keys page, and add it to your client.

Or in a project’s .mcp.json:

gritz mcp takes the key from --token or GRITZ_TOKEN, not from the CLI’s config.json, and talks to https://gritz.dev unless --server says otherwise:

Flag
--token The API key. Required; defaults to GRITZ_TOKEN.
--server, -s The server URL. Defaults to https://gritz.dev. GRITZ_SERVER isn’t read.
--auto-archive The auto-archive delay for tasks created without an auto_archive argument, such as 1h.
--channel Push task updates into the Claude Code session. See Channels.

Tools

Section titled “Tools”
Tool
list_workspaces Lists the workspaces runners offer: each one’s name, description and runner ID.
create_task Creates a task and starts it.
list_tasks Lists the organisation’s 50 newest unarchived tasks: ID, name, workspace, status and URL.
get_task Gets a task with its links and its full timeline: instructions, events, reports and status changes.
update_task Adds an instruction to a task, and optionally starts it.
archive_task Archives a finished task.

You don’t call these yourself: ask your agent, for example “Create a gritz task in the pets-workshop workspace to add a --json flag, then tell me when it has opened a pull request.” It calls list_workspaces to find the runner, then create_task.

create_task

Section titled “create_task”
Argument
workspace The workspace. Required.
runner The runner that offers it. Required.
instruction The task’s instruction. Required.
name A name for the task. The task’s agent names it if this is empty.
auto_archive The auto-archive delay, such as 30m or 24h. 0 is never; a negative value, such as -1s, archives the task as soon as it finishes.

It returns the task’s ID, name, workspace, status and URL.

update_task

Section titled “update_task”
Argument
id The task ID. Required.
instruction The instruction to add. Required.
url A URL the instruction is about, such as an issue.
start Start the task. A running task isn’t interrupted: it runs again when its current run ends.

An instruction added without start waits until something else starts the task.

get_task, list_tasks, archive_task

Section titled “get_task, list_tasks, archive_task”

get_task and archive_task take the task’s id. archive_task only archives a task that has completed, failed or been cancelled; archiving destroys its sandbox. Cancelling and restarting tasks are done in the Web UI.

Channels

Section titled “Channels”

Channels let an MCP server push messages into a running Claude Code session. With --channel, gritz mcp pushes the organisation’s task updates, so your Claude hears about a task finishing without polling:

It sends a message when a task is created (by anyone, by a routing rule or by a schedule), when one is queued with new instructions, woken from a finished state by an event, given an event without being woken, completed, failed, cancelled, restarted or archived, and when a shell is opened in one. It leaves out the changes made through the same gritz mcp process, so your Claude isn’t told about the task it just created.

Muting tasks

Section titled “Muting tasks”

With --channel, three more tools let your Claude choose which tasks it hears about. Every task is on by default.

Tool
channel_mute Stops messages for the tasks in task_ids, or for every task with all=true.
channel_unmute Resumes messages for the tasks in task_ids, or for every task with all=true. After channel_mute with all=true, unmuting some tasks keeps just those on.
channel_muted Shows which tasks are muted.

Muting lasts until gritz mcp exits. It is separate from subscribed links, which route external events into tasks.
