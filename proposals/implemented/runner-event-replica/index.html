Runner and driver as replicas of the task event log

Issue: https://github.com/gritzapp/gritz/issues/1818

Problem

Section titled “Problem”

The runner reads the current state of each task, not what changed. TaskManager.Poll (internal/runner/taskmanager.go) calls ListRunnerTasks, which returns every task with command != NONE, and acts on each command. A command stays set until a later runner event (started / stopped / failed) clears it in Task.ApplyRunnerEvent, so the runner sees the same command on every poll until then. Much of the runner exists only to cope with that repeated delivery:

  • the restart guard that compares the record’s version with task.Version (#1520);
  • restart taking several poll passes: kill, ErrRunning, release the slot, retry on the next poll;
  • a stop whose kill failed being retried on every poll, with no limit (#1742);
  • a restart stuck in Restarting, waiting for a started that never arrives (#1763).

The task already has an append-only history, the events table, but it can’t be followed with a cursor today. events.id comes from a sequence and is assigned when the row is inserted, while the row becomes visible only when its transaction commits. Two transactions can therefore commit out of id order:

time Tx A (task 42) Tx B (task 43) reader polls gets
t1 INSERT, gets id 10
t2 INSERT, gets id 11
t3 COMMIT
t4 id > 9 [11], cursor = 11
t5 COMMIT
t6 id > 11 []

Row 10 commits behind the cursor and is never read. The driver already has this bug: Driver.drainEvents (internal/runner/agent/driver.go) follows the task’s stream with Config.NextEventToken and assumes “because event ids are monotonic, every future injectable event has a higher id than the saved token”. Ids are monotonic in insert order, not commit order, so an instruction committed late can be skipped and never reach the agent.

Design

Section titled “Design”

Treat the task event log as the source of truth, and make the runner and the driver replicas of it:

  • The server writes every change to a task, including every command, as an event, and serves events below a commit-safe watermark.
  • The runner copies the events of its tasks into its SQLite database, in the order the server returns them. Its cursor is an opaque token the server hands back with each page, stored with that page, so the server keeps no state about runners and the runner never sees how the log is ordered. A new package, taskevents, owns the copying and gives each task a stream with no missing history, in order. Each task’s TaskRunner acts only on sandbox lifecycle: it brings the sandbox up when the task wants a run, forwards the stream to the driver, and suspends the sandbox once the driver goes idle.
  • The driver receives its task’s events over the Run stream, stores them in the sandbox, and owns all run behaviour: start, restart, stop, and the instructions and external events it hands to the agent.

Each hop works the same way: the reader says where it is, and the writer sends what comes after.

Server: a commit-safe read with an xid watermark

Section titled “Server: a commit-safe read with an xid watermark”

Each event records the transaction that wrote it:

Adding the column with a volatile default rewrites the table. Every existing row gets the migration’s own xid, which is below every later xid, so existing history sorts before everything written afterwards.

xid8 (Postgres 13+) is the 64-bit transaction id: the 32-bit xid plus its wraparound count. It only increases, so <, ORDER BY and the index work. Rows written by one transaction share an xid; id orders the rows within it.

The runner’s read returns only rows from transactions older than the oldest transaction still running:

pg_snapshot_xmin is the oldest running transaction. Every transaction below it has committed or rolled back, so the rows below it can no longer change. Rows from newer transactions are held back until everything older has finished. With the example above, the poll at t4 returns nothing, because row 11’s xid is not below Tx A’s, and once Tx A commits the poll returns (A, 10), (B, 11).

  • Order is the order transactions first wrote, not the order they committed. It is stable once rows are below the watermark, which is all a cursor needs.
  • Rollbacks need nothing. A rolled-back transaction stops holding back the watermark when it ends, and its rows were never visible. There is no gap detection and no timeout.
  • Writers have no rules. Every insert gets its xid from the column default; nothing takes a lock in a particular order.

Server: an opaque cursor

Section titled “Server: an opaque cursor”

The (xid, id) pair stays on the server. ListRunnerEvents is paginated with internal/x/pagination, the same keyset plumbing as ListTasks and ListEventsByTask, and the runner’s cursor is its opaque page token:

  • The source (runnerEventSource) serves only the backward (live-follow) walk: ascending (xid, id) after the token’s cursor, below the watermark. The forward walk returns pagination.ErrUnsupportedDirection, the mirror of ListTasksPage, which serves only the forward walk.
  • The request’s page_token is empty for the start of the log, and otherwise the next_page_token of the previous page. The store substitutes a cursorless backward token for an empty one.
  • The response’s next_page_token is the page’s PrevToken: it resumes after the page’s last row, and an empty page returns the request’s token unchanged. more reports whether another page is available now, so the runner pages until more is false.
  • The token’s encoding (pagination.Token[runnerEventCursor], base64 JSON) is the server’s, and the server may change it. The runner stores and returns the string without decoding it.

Event carries no xid on the wire, and neither the runner nor the driver orders anything by it. A token names a position in the runner’s own tasks’ log, and the read is scoped by the runner’s identity, so a forged token can only skip or repeat that runner’s events.

Server: command events

Section titled “Server: command events”

The runner can only replicate what is in the log. Today a command is set in places that write no event, or an event that doesn’t say so: a start through UpdateTask is recorded as Updated, and the wake from the event router, CreateTask, and the server-issued stops in ApplyRunnerEvent set the command with no event at all.

A sixth event type carries the command:

The workspace is there so the runner can boot a sandbox from its replica without asking the server. A workspace edit with no command change writes no event: the workspace only matters at boot, and every boot is driven by a command event that carries the current one. Command events written before the field was added carry an empty workspace.

Every site that changes a task’s command writes a command event in the same transaction, next to the lifecycle event it already writes, the same way lifecycle events are written. A model method, shaped like RunnerEvent.LifecycleEvent, builds it:

Each site snapshots the task with from := task.Clone() before the mutation (Start, Restart, Cancel, ApplyRunnerEvent, the event-router wake) and passes from.Command; a site that creates a task with a command passes TaskCommandNone. The store is unchanged. Two cases fall out of the rule:

  • Withdrawals. Cancelling a PENDING task writes a none command event for that version, so a runner that already acted on the start learns it was withdrawn.
  • Clears. When a runner event consumes the command, a none event is written too.

Lifecycle events don’t change; they remain the history users see. A restart writes both. ListEventsByTask callers that show history (the web UI timeline, get_my_task) filter command events out.

Runner: taskevents, a per-task stream over a replica

Section titled “Runner: taskevents, a per-task stream over a replica”

Replication is hidden from the rest of the runner. A new package, internal/runner/taskevents, copies the runner’s events from the server into SQLite and exposes each task’s events as a stream. A TaskRunner reads one task’s stream and never sees the cursor or duplicates.

taskevents guarantees:

  • A stream has the task’s whole history. Log replicates from an empty cursor, so by the time a task’s first event is stored, nothing earlier is missing. The stream keeps growing for as long as the task exists.
  • Positions are event ids. A reader keeps its own position as an events.id and passes it to Read. How an id maps to a place in the log stays inside taskevents. Ids are stable across a rebuilt runner database, so the driver’s Hello.last_event_id goes straight into Read.
  • Read is stateless. The reader keeps its position, so a reader that reconnects or restarts resumes wherever it says. The only reader is TaskRunner.drive, forwarding from the driver’s position; the runner keeps no position of its own.
  • Read blocks until there is at least one event after the position, and wakes when new events for the task are stored.

Log.Tasks() is how the runner learns which tasks it should have a TaskRunner for, so there is no second source of truth such as ListRunnerTasks. Log folds each task’s command events and archive lifecycle events (Archived, AutoArchived, Unarchived) into a TaskChange{ID, Command, Version, Workspace, Archived}: the task’s full state, not a delta.

  • After each stored page, every task with a command or archive event in it is reported with its state after the page. TaskManager hands it to the task’s TaskRunner, creating one for an unarchived task that has none.
  • At boot, Log reports every stored task that isn’t archived. Archived tasks get no TaskRunner.
  • Reports may repeat the state a task is already in (a boot report of a task the consumer already has, a page with a command that doesn’t change it), so the consumer applies them idempotently.

An archived task’s events are still replicated and stored, so unarchiving needs no fetch and the cursor stays simple.

Bootstrap is the same loop from an empty database: the cursor starts empty and the runner replicates the whole history of its tasks, archived ones included. There is no snapshot and no separate fill-in path.

No compaction. Replicated events are never deleted. The row any reader last saw is always there for Read to resume from.

No task reassignment. tasks.runner is set when the task is created and never changes. ListRunnerEvents joins on it, so a task’s whole history goes to one runner.

Inside taskevents

Section titled “Inside taskevents”

The replica lives in runnerstore (internal/runner/runnerstore), the runner’s SQLite database. internal/x/sqlite opens it (WAL, synchronous = FULL) and applies the schema from migrations embedded in the package; queries are generated with sqlc.

The events table has one row per replicated event, in the order it arrived, with the event’s id, task_id and the event, protobuf-encoded. seq is the local position: arrival order is the server’s log order, so seq increases along the log with no gaps. A single-row replication table holds the cursor. The tasks table projects each task’s last command and archive state from its events, so Tasks() reports and boot need no fold over the log.

Slice 6 added tasks.handled and tasks.command_event_id so the runner could act on each command once. They go once the driver acts on commands, in a new migration:

Replication. Log.Run is a loop that replaces Poll:

  1. At boot, report every stored task that isn’t archived on Tasks().
  2. Read the cursor with EventReplicationCursor (empty when none is stored).
  3. Call ListRunnerEvents(page_token: cursor).
  4. Store each non-empty page with AppendEvents: in one transaction, insert the page’s events, upsert the tasks row of every task with a command or archive event in it, and set cursor to the response’s next_page_token.
  5. Repeat while the response’s more is true, then wait for a wake or the poll interval (30s by default). The runner SSE notification (proposals/implemented/runner-sse-events.md) triggers a sync sooner. The interval is not only a fallback for a lost notification: more == false means nothing is readable right now, not that the replica is caught up. The server’s xid watermark can hold committed events back and release them later with no notification, and the interval picks them up.

A failed fetch is logged and retried at the next wake or interval; a store error ends Run.

The events, the task projection and the cursor commit together, so the cursor never runs ahead of the stored events and no stored event sits behind a stale cursor. A crash before the commit loses all three, and the next fetch repeats the page. Every fetched event is stored, including ones the runner has no use for.

After storing a page, Log wakes the blocked Reads of the tasks in it and sends the TaskChanges AppendEvents returned on Tasks(). The upsert returns each touched task’s whole row, so a report is the task’s full state whatever the page held: a command-only page keeps the archive state, and an archive-only page keeps the command.

Stream.Read(after) reads:

Position 0 returns the task’s whole log. An after that isn’t stored yet returns nothing rather than the whole log, so a position that outlives the database (a driver’s last event id after the runner’s database was rebuilt) resumes once that event is replicated. When there is nothing to return, Read waits for the next page with an event for the task. It takes that wake-up signal before reading, so a page stored between the read and the wait isn’t missed.

Runner: TaskManager and TaskRunner.RunLoop

Section titled “Runner: TaskManager and TaskRunner.RunLoop”

TaskManager owns the Log: TaskManager.Run runs Log.Run (a store error terminates the runner through die) and consumes Log.Tasks(). It also owns what the task runners share: the Slots, the runner-event queue (RunnerEventOutbox) and the spec builder (specs). It has no command logic.

  • One TaskRunner per task. For a report of an unarchived task with no TaskRunner, the manager creates one, starts its RunLoop on its own goroutine, and calls tr.Change(c). Every later report for the task goes to the same tr.Change(c), archived ones included. A report of an archived task with no TaskRunner is dropped.
  • RunLoop is the runner’s lifetime. When RunLoop returns nil (the task was archived and its sandbox destroyed), the manager removes the TaskRunner; a later unarchive report creates a fresh one. When it returns an error, the manager dies with it (die). On shutdown RunLoop returns with the context and leaves the sandbox up for the next boot.
  • Load creates the TaskRunner of each sandbox record the same way: Restore adopts the record, the manager starts RunLoop, and calls Change with the task’s stored state (runnerstore.Store.Task), so a record left behind by an archived task is destroyed too. Up sandboxes are counted into Slots.Set, as today, and the lost-run backstop for suspended and gone sandboxes (failIfTaskRunning) stays.
  • No Prune. Tasks are never deleted, and archiving writes an event that reaches RunLoop, so nothing needs to ask the server whether a task still exists.

Change(c) stores c as the task’s latest report, replacing the one before it, and wakes RunLoop. Commands are a desired state: RunLoop only ever looks at the latest report, so a command superseded before RunLoop got to it is never acted on.

RunLoop is straight-line:

  1. Wait for a change that needs the driver: the latest command is start or restart for a version newer than the last one RunLoop drove, booted or failed. A TaskRunner that Load restored with its sandbox up skips to step 4 with the slot Load counted for it.
  2. Take a slot (Slots.Acquire). This is the only wait a newer change can preempt: a change that arrives while waiting is looked at again from step 1, so a cancel that lands while a start waits for a slot means the start never runs.
  3. Boot or resume the sandbox for the change’s workspace, with the spec from specs. A failure enqueues failed for the version, releases the slot and goes back to step 1.
  4. Block in drive until the driver is idle.
  5. Release the slot.
  6. Suspend the sandbox and go back to step 1.

Two changes are handled wherever RunLoop waits (steps 1 and 2):

  • Archived. The server archives only finished tasks, or drafts with no pending command, so archiving never cancels a run. An archive that arrives during step 3 or 4 waits for that busy period to end. Then RunLoop destroys the sandbox, deletes its record and returns nil.
  • Stop with no Run open. There is no driver to report it, so the runner enqueues stopped for the version itself. During drive the stop is just another event on the stream, and the driver acts on it.

The versions RunLoop has handled are kept in memory only. A runner that restarts may see a start it already carried out (its none not yet replicated) and boot the sandbox for it again. That is harmless: the driver has already acted on the start, finds nothing to run, and goes idle at once, and a duplicate stopped or failed is rejected by the server’s status and version guards.

drive

Section titled “drive”

drive holds the driver’s Run stream for one busy period:

  1. Open the bidirectional Run stream and send the RunSpec first, built from the latest change’s workspace.
  2. Receive Hello, which carries the id of the last event the driver stored.
  3. Forward the task’s stream from that position: loop on Stream.Read(ctx, pos) and send each batch as TaskEvents, while reading the driver’s responses on the same stream.
  4. Return when the driver sends Idle. If Idle.reported is false, the driver’s terminal runner event for Idle.version didn’t reach the server, and drive enqueues failed for it. If the latest change wants a version newer than Idle.version (the driver went idle before that command reached it), drive reopens the stream instead of returning.

A dropped stream is reopened with backoff. If the sandbox is gone, or reopening keeps failing for LostTimeout, drive suspends a sandbox that is still there, enqueues failed for the latest start or restart version, and returns. TaskLostEvent goes: drive enqueues the runner event itself.

After a runner restart, a sandbox Load finds up goes straight to drive: whatever the driver was doing it is still doing, and Hello says where to resume forwarding.

suspend_after

Section titled “suspend_after”

Split out into https://github.com/gritzapp/gritz/issues/1888: a workspace setting that keeps a sandbox up for a while after drive returns, so a follow-up start skips the boot. In this effort the runner suspends as soon as drive returns.

Slots

Section titled “Slots”

A slot counts an active driver Run, that is, a busy period: it is taken before the boot and released when drive returns, however many run versions the driver ran in between.

What goes away

Section titled “What goes away”

With the driver acting on commands, the runner’s command handling goes:

  • handled and command_event_id (dropped in a new migration), Store.Handled/SetHandled, and TaskChange.CommandEventID;
  • the start, restart and stop handlers and command();
  • the restart version guard (#1520), the ErrRunning and “earlier version” retries, and restart’s kill-then-start;
  • TaskRunner.Kill and Stop, and the driver Stop RPC;
  • TaskLostEvent.

Driver: Run becomes a bidirectional stream

Section titled “Driver: Run becomes a bidirectional stream”

Run no longer starts anything by itself. It is the connection the runner forwards the task’s events over, and the driver acts on the commands among them:

  1. The runner opens the stream once the sandbox is up, and sends the RunSpec as its first message.
  2. The driver sends Hello with the id of the last event it has stored.
  3. The runner sends the events after that position as TaskEvents: first one batch, possibly empty, with every event it has stored, then new ones as they are replicated. The driver doesn’t go idle before that first batch, so it never goes idle on a stream whose command it hasn’t received.
  4. The driver stores each batch, then acts on it.

The driver’s position is an events.id; 0 means “send everything”. At most one Run stream is open at a time; a second one is rejected with Unavailable, and drive retries it.

The RunSpec is sent on every stream. Env, secrets, files and the token come from the runner’s workspace config, not from events, so the runner sends them as the first message each time it opens Run. The driver keeps the latest one in memory and uses it for any run it starts on that stream. The spec arrives before any event, so the secrets are known before a run starts and before its log ships a byte. A workspace config change reaches the driver the next time the stream opens.

Driver storage. The driver appends every received event to /gritz/events.jsonl and fsyncs before acting on it, skipping events it has already stored. Its position is the id of the last line, read back on boot. The file lives next to /gritz/run.json, so it survives a driver restart and a suspended sandbox being booted again.

Acting once. After each stored batch, and when a stream opens, the driver looks at the latest command event in its file and compares it with its run record (/gritz/run.json, written before a run starts):

Latest command in the file Driver
start v, v newer than the run record, nothing running Start run v
restart v, v newer than the run record Stop the running run with ErrStop, if any, then start run v
stop v, a run in progress Stop it with ErrStop
anything else Nothing

A command the run record has already passed does nothing, so a resent stream, a crash between storing and acting, and a stale start that made the runner boot the sandbox are all harmless. A fresh sandbox receives the task’s whole log and acts only on its latest command, so it doesn’t replay history.

One Run stream covers a busy period. The driver runs consecutive versions without the runner reconnecting: when run v ends and a newer start or restart is pending, it starts the next one on the same stream. A start that arrived for the running version v (a wake on a running task) is pending too: once the driver’s stopped for v is accepted, the server moves it to start v+1 at the run boundary (#1868), and the driver waits on the stream for that event. The driver sends Idle and closes the stream only when its current run has ended and no newer start or restart is pending in its event file.

Idle replaces Finished. It carries the version of the last run and whether its terminal runner event was accepted (reported); the runner reports an unreported run failed. A newer start or restart still pending after an unreported run is started on the same stream all the same: it is a restart, or a run boundary the server did accept, and going idle would leave it to a reopen.

The prompt reads from the local file. drainEvents, the ListEventsByTask walk and Config.NextEventToken go away. The driver keeps a “prompted up to” id in its config and renders the instruction and external events stored after it. That fixes the skipped-instruction bug above, because the file’s order comes from the runner’s commit-safe replication.

Runner events still go to the server directly. The driver keeps calling SubmitRunnerEvents with the task token for each started / stopped / failed, as today, and records whether the terminal one was accepted in the run record’s reported flag. Moving runner events onto the Run stream is out of scope.

Keep-alives stay: the driver sends KeepAlive every 15s and driverclient cancels a stream that goes quiet (DefaultIdleTimeout).

The task token is still needed by the driver for SubmitRunnerEvents, log shipping (logship) and the agent’s gritz MCP server, which all talk to the server directly.

Status and Stop are removed. Opening Run with backoff is the readiness check, and a stop is a command event on the stream.

Inside the driver

Section titled “Inside the driver”

driverserver splits into four parts:

  • Transport (Server): the bidirectional Run, Hello and Idle, and keep-alives. It claims the one open stream, appends each batch to the event file, and hands the newly stored events to the driver loop. It holds no run state: once it has the first batch, it waits for the loop to be idle, sends Idle and closes the stream.
  • Event file (eventfile): the stored log. Append skips events already stored and returns the ones it stored, so a resent event never reaches the loop a second time.
  • Driver loop: lives as long as the driver process, across streams. It keeps the latest command event and the latest RunSpec, and decides what to do whenever a stream opens, a batch is stored or a run ends.
  • Executor: the agent process and the run record. It starts the run the loop names, provisioning the spec’s files inside the run, so a run that fails to provision finishes unreported rather than not starting. It decides nothing.

The loop’s rules:

  • Latest command wins. Only the latest command event in the file counts; earlier ones are superseded, not queued. A fresh file holding a task’s whole log acts only on its latest command.
  • start v: if v is newer than the run record, start it once no run is in progress. A busy period runs consecutive versions on one stream: run 5, then a pending start of 6 once 5 has finished. If v is not newer, it is stale, and does nothing. The run record, written before a run starts, is the only “already started” marker.
  • restart v, v newer than the record: stop the run in progress, wait for it to finish, start v.
  • stop: stops whatever run is in progress, with ErrStop. A stop older than that run is asserted against: the server stops only the current version. A stop newer than it is a restart cancelled before the driver started it (the restart moved the task’s version on). It stops the run in progress and supersedes the restart, and since no run will report the stopped version, the runner reports it stopped once the driver is idle with an older version.
  • Idle is no run in progress and no newer start or restart pending, or none that can start: the driver is shutting down, or has no spec yet.
  • Driver restart: the loop rebuilds from disk, from the reconciled run record (a run cut short is finished and unreported) and the latest command in the event file, and acts on it when the next stream opens.

Transport

Section titled “Transport”

Connect bidi streams need HTTP/2. The driver server already accepts unencrypted HTTP/2 (driverserver.ListenAndServe). The Docker backend’s client transport (docker.sandbox.Dial) is HTTP/1.1 and needs Protocols.SetUnencryptedHTTP2(true). The Lambda MicroVM proxy supports bidi streams, but forwards to the plaintext driver over HTTP/1.1 — on which connect-go rejects bidi with 505 — unless the request carries X-aws-proxy-force-h2: true. The backend’s tokenTransport sets that header on every request rather than relying on an upstream h2c connection, once opened, carrying later requests.

Proto

Section titled “Proto”

driver.v1:

RunRequest.version, Accepted, Finished, StatusRequest, StatusResponse, StopRequest and StopResponse are removed; Idle takes Finished’s place. RunSpec itself is unchanged; it moves into the RunRequest oneof as the stream’s first message. RunRecord stays the driver’s on-disk record and leaves the wire.

API

Section titled “API”

How it fits: the server’s call sites that change a task’s command write command events, and ListRunnerEvents serves them. gritz runner constructs a taskevents.Log on the runnerstore.Store, which TaskManager runs. The runner’s SSE notification calls Log.Wake. Log.Run pages events into the store and wakes blocked Reads. TaskManager creates a TaskRunner with Log.Stream(id) for each unarchived task from Log.Tasks() (and each sandbox record at Load), starts its RunLoop, passes it every report with Change, and removes it when RunLoop returns. RunLoop takes a slot from Slots, boots the sandbox with the spec from the manager, and calls drive, which opens Run, forwards Stream.Read(hello.last_event_id) and returns on Idle. driverserver writes each batch to eventfile.File and acts on its latest command against the run record. The driver submits runner events to the server itself, as today; the runner enqueues only stopped for a stop with no Run open and failed for a boot failure, a lost driver or an unreported run.

Implementation Plan

Section titled “Implementation Plan”
  1. events.xid — Delivers: the migration, and reading it in the store. Depends on: nothing. Verifiable by: migration up and down; store test that rows carry the inserting transaction’s xid.
  2. Command events — Delivers: EventTypeCommand, CommandPayload, the proto arm, Task.CommandEvent, and every call site that changes a task’s command writing one; history views filter them out. Depends on: nothing. Verifiable by: caller tests (apiserver RPCs, event router, runner events) for each command path (start, restart, cancel of PENDING, wake, server-issued stop, clear, and an unchanged command writing none).
  3. ListRunnerEvents — Delivers: the query and RPC, with the watermark and the opaque page token. Depends on: (1). Verifiable by: a store test with two concurrent transactions that commit out of id order; neither row is returned until both have committed, and then both are, in xid order; an empty page returns the request’s page token.
  4. taskevents — Delivers: runnerstore with its events, replication and tasks tables, Log replicating into them, Tasks() and Stream.Read. Nothing constructs a Log yet; Poll still drives behaviour. Depends on: (3). Verifiable by: taskevents tests against a fake server: the local events match the server’s, a restart resumes from the stored cursor, Tasks() reports command, archive and unarchive changes, boot skips archived tasks, Read blocks until an event after the position is stored, and the poll interval picks up events with no wake.
  5. Driver HTTP/2 — Delivers: unencrypted HTTP/2 on the Docker driver client, and X-aws-proxy-force-h2: true on every Lambda MicroVM driver request. Depends on: nothing. Verifiable by: the existing Docker and Lambda MicroVM backend tests.
  6. Runner acts on events — Delivers: gritz runner constructing a taskevents.Log on its runnerstore, which TaskManager owns and runs; a follower per unarchived task, started and stopped from Log.Tasks() (full-state reports, applied idempotently), acting on the last command in what it reads through the existing driver Run and Stop RPCs, so the driver protocol is unchanged; the follower’s position in tasks.handled, advanced only once a command is carried out, with retries on a released slot, a new event or a backoff; Poll and the ListRunnerTasks RPC removed (proto, handler, store query and client); TaskManager.Start taking a runnerstore.TaskChange; a shared fake server for runner tests that serves ListRunnerEvents from an in-memory log. Depends on: (2), (4). Verifiable by: runner_test with the fake backend and the fake server for start, restart, stop, stop with no sandbox, a start waiting for a slot, a stop superseding a waiting start, archive retiring the TaskRunner, and a restarted runner resuming from handled without acting again.
  7. Driver event file and bidi Run — Delivers: eventfile; Run as a bidi stream whose first message is the RunSpec and the version to start or attach to (attach-or-start as today); Hello with the driver’s last stored event id; the runner forwarding Stream.Read from that position on the stream it already holds for the run; Idle in place of Accepted and Finished, sent when that run ends; Status removed, with opening Run under backoff as the readiness check. The driver stores events but doesn’t act on them; the runner still issues start, restart and stop. Depends on: (5), (6). Verifiable by: driverserver tests: events are stored in order and survive a driver restart, a reopened stream resends only what the file lacks, Idle.reported mirrors the terminal submit; the existing runner tests pass on the bidi stream.
  8. Driver acts on commands — Delivers: the driver acting once on the latest command in its file against its run record; busy periods that run consecutive versions (a restart mid-run, a wake on the running version followed by its run boundary) on one stream, ending in Idle only when nothing newer is pending; RunRequest.version and the Stop RPC removed. On the runner, the start and restart handlers take a slot, boot the sandbox and start a Run goroutine that holds the stream until Idle, and the stop handler reports stopped only when no Run is open; the restart version guard, restart’s kill-then-start, the “earlier version” retry, and TaskRunner.Kill/Stop go. Depends on: (7). Verifiable by: driverserver tests per command, a resent stream and a stale start doing nothing, a fresh file with the whole log acting only on the latest command, v5 then a pending v6 on one stream, and Idle after an unreported run; the runner’s restart and stop tests against the fake backend.

Trade-offs

Section titled “Trade-offs”
  • A per-task row lock instead of the watermark. Lock the task row (FOR UPDATE) before inserting any event, so id order matches commit order within a task, and keep one cursor per task. Rejected: it only holds if every event insert takes the lock, and the runner would keep a cursor per task instead of one.
  • A sequence per runner. A counter row per runner, incremented in each command write, so the runner can follow seq > N. Rejected: it needs a runners table and serializes command writes per runner.
  • Gap detection on events.id (Marten’s high water mark). Rejected: a gap from a rollback and a gap from a slow transaction look the same, so it needs either a timeout, which can skip a slow commit, or inspection of running sessions. The xid watermark gets that answer from Postgres directly.
  • The runner follows (xid, id) itself. ListRunnerEvents takes and returns the pair, and the runner stores each event’s xid and finds its cursor in the newest row. Rejected: it spreads the server’s ordering into the proto, model.Event and the runner’s schema, and every local read has to compare pairs. With an opaque cursor the runner sees a plain sequence.
  • A server-assigned, commit-ordered seq. A sequencer numbers rows below the watermark under a transaction-level advisory lock, so every consumer could follow seq > N. Rejected for now: ListRunnerEvents becomes a write (or a sequencer loop has to run), all runners contend on one lock, and every event row is updated once. The opaque cursor allows it later without a runner change.
  • The server tracks each runner’s position (acked command queue). Rejected: the runner owns its position; the server read stays stateless.
  • The driver reads from the server itself. The driver already has a task token and could follow ListEventsByTask with the watermark. Rejected: two paths into the sandbox, and the runner would still need the events to manage lifecycle. One stream keeps the runner as the sandbox’s only peer.
  • Runner events over the Run stream. The driver could send started / stopped / failed to the runner instead of calling SubmitRunnerEvents. Out of scope: without the RPC’s response the driver would need acks or sequence numbers to know an event was stored, and the driver keeps a direct connection to the server for log shipping and MCP anyway.
  • The runner keeps carrying out commands (slice 6’s follower, with handled and the driver’s Run/Stop RPCs). Rejected: acting once is needed in two places, the runner and the driver, and the runner’s handlers carry the restart guard, kill-then-start and ErrRunning retries only because they act on a run the driver owns. With the driver acting on its own file, the runner’s only decisions are lifecycle ones.
  • One Run stream per run version. The driver would go idle after every run, and the runner reconnect for the next. Rejected: at a run boundary the next start is written as the previous run ends, so the runner would release the slot and suspend between two runs of one busy task, and another task could take the slot in between. A busy period keeps one slot and one stream for as long as the task has work.
  • Suspend as soon as the driver is idle. Chosen for now: a follow-up instruction shortly after a run pays a full boot. suspend_after (https://github.com/gritzapp/gritz/issues/1888) would trade a few minutes of an idle sandbox for that, per workspace, holding no slot while it waits.
  • Cost of the watermark. It is cluster-wide: the oldest writing transaction anywhere holds back every runner. A slow migration or a session idle in a transaction delays delivery until it ends. idle_in_transaction_session_timeout and statement timeouts bound it. Read-only transactions have no xid and don’t hold it back.

Open Questions

Section titled “Open Questions”
  • Reads on a standby. Not checked how pg_current_snapshot() behaves on a hot standby; ListRunnerEvents may need to run on the primary.
  • Live delivery to a running agent. The driver now receives instructions while a run is active. Handing them to the agent mid-run (channels) is left to a follow-up.
  • The sandbox record’s version. Once the runner stops starting runs by version (slice 9), sandboxes.version is read only by Load’s lost-run backstop for suspended and gone sandboxes. The driver’s Idle.reported covers an up sandbox; whether the backstop can use the task’s latest command version instead, and the column go, is left open.
